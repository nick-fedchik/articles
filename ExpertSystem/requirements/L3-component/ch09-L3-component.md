## REQ-L3-09-01

- **Вимога:** Вилучення зв'язків у графі повинно виконуватися детермінованим конвеєром із чотирьох джерел: нормативна БЗ, сканер абстрактного синтаксичного дерева (AST) коду, парсер регістрів SVD і завантажувач звітів JUnit. На першому проході статистичні моделі не використовуються.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §3 «Автоматизоване вилучення артефактів та конструювання графа» (чотири джерела і чотири аналізатори).
- **Батьківська вимога:** REQ-L2-09-01.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.

## REQ-L3-09-02

- **Вимога:** Пропозиція нового ребра графа на основі метрики Адамік-Адар `AA(x, y)` допускається лише за значення 1,00 або більше. Пропозиція не має статусу підтвердженого ребра.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §4.2 «Евристичне прогнозування пропущених зв'язків за мірою Адамік — Адара».
- **Батьківська вимога:** REQ-L2-09-02.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.
- **Перевірка:** Для визначеного простого неорієнтованого графа оцінка 1,49 надходить до черги перегляду, а 0,48 не надходить; пропозиція в черзі не зараховується як підтверджене ребро. Для однакового означення сусідства перестановка вузлів не змінює оцінки; за відсутності спільних сусідів сума дорівнює нулю. Якщо вибране означення дає для спільного сусіда степінь 1, формула не визначена і порівняння числового результату з порогом не проводиться.
- **Примітка:** У напрямленому графі означення сусідів і степеня, спосіб повідомлення невизначеного результату та критерії перевірки порога 1,00 потребують погодження. Для різних вузлів простого неорієнтованого графа спільний сусід має щонайменше двох сусідів; напрямок запропонованого ребра визначають окремо.

## REQ-L3-09-03

- **Вимога:** Шлюз CI/CD повинен блокувати злиття гілки, коли нова функція не має ребра `satisfies` до вимоги або валідованого шляху виклику.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §5.2 «Шлюз якості в CI/CD».
- **Батьківська вимога:** REQ-L2-09-06.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.

## REQ-L3-09-04

- **Вимога:** Модуль аналізу впливу повинен для зміни вимоги обходити ребра `satisfies` і `verifies` проти їхнього напрямку, `configures` за напрямком та `exercises` проти напрямку, згідно з правилами типів ребер.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §4.4 «Алгоритми аналізу впливу змін (Change Impact Analysis)».
- **Батьківська вимога:** REQ-L2-09-05.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.
- **Перевірка:** У графі «код satisfies вимогу», «код configures регістр», «тест exercises код» для зміни вимоги результат містить код, регістр і тест.
- **Примітка:** Повний набір правил для інших типів ребер і типів зміни та включення початкового вузла потребують погодження. Неповний граф не гарантує повноти результату.

## REQ-L3-09-05

- **Вимога:** Модуль обліку свідчень повинен прив'язувати кожен результат тестового запуску до перевіреної версії артефакту та зберігати попередній результат при додаванні нового запуску.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §5.2, правило версійної актуальності свідчень.
- **Батьківська вимога:** REQ-L2-09-07.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.
- **Перевірка:** Запуск для версії `V1` не подається як запуск для зміненої версії `V2`; після запису результату для `V2` запит історії зберігає і результат для `V1`.

## REQ-L3-09-06

- **Вимога:** Шлюз якості повинен зіставляти кожен визначений критичний вузол із множини впливу з актуальними залікованими свідченнями для цільової версії.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §5.2, правило відсутності неперевіреної регресії.
- **Батьківська вимога:** REQ-L2-09-08.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.
- **Перевірка:** Вузол із результатом для попередньої версії та вузол без результату залишаються непідтвердженими; вузол із придатним результатом для цільової версії проходить зіставлення. Граничний випадок порожньої множини критичних вузлів розглядається окремо й не є доказом повноти графа.
- **Примітка:** Це перевірка наявності свідчень для вузлів, а не метрика покриття коду або MC/DC. Критерії придатності, джерело критичності й обробка неповного графа не затверджені.

## REQ-L3-09-07

- **Вимога:** Журнал фактів графа повинен зберігати суб'єкт, тип зв'язку, об'єкт і контекст походження, включно з ревізією, автором, часом і підписом інструмента вилучення.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §5.1, поля незмінного факту.
- **Батьківська вимога:** REQ-L2-09-09.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.
- **Перевірка:** Для двох версій одного зв'язку журнал повертає обидва записи з відповідними контекстами; запис без потрібного поля не вважається повним доказовим записом.
- **Примітка:** Наявність підпису не замінює перевірки підпису, уповноваження ключа або змісту твердження; криптографічний протокол потребує погодження.

## REQ-L3-09-08

- **Вимога:** Модуль перевірки графа повинен перевіряти напрямок ребра `mitigates` від нормативного вузла до вузла визначеної небезпеки відповідно до типів кінцевих вузлів.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §2.2 «Семантична класифікація ребер та правила цілісності».
- **Батьківська вимога:** REQ-L2-09-01.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.
- **Перевірка:** Для нормативного вузла і вузла небезпеки ребро `mitigates` від першого до другого відповідає сигнатурі; зворотне ребро не відповідає сигнатурі, якщо початковий вузол не є нормативним, а кінцевий не є вузлом небезпеки. Якщо обидва вузли належать обом класам, обидва напрямки відповідають сигнатурі. Відповідність сигнатурі не підтверджує самого твердження про мітигацію.
- **Примітка:** Перетин класів і повний набір типів вузлів та ребер не визначені. Дія після виявлення невідповідності сигнатурі потребує погодження.

## REQ-L3-09-09

- **Вимога:** Модуль прив'язки нормативного вузла до джерела повинен зберігати байтові межі цитати та обчислений за цитованими байтами хеш SHA-256 разом із посиланням на файл джерела.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §2.1 «Типологія вузлів: від системних вимог до апаратних регістрів».
- **Батьківська вимога:** REQ-L2-09-10.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.
- **Перевірка:** Для цитати з багатобайтовими символами незалежно визначені байти вказаного файла відтворюють збережений хеш SHA-256; після зміни одного цитованого байта хеш перерахованого фрагмента не збігається зі збереженим. Відсутній файл або межі не дають перевіреної прив'язки.
- **Примітка:** Конвенція меж інтервалу, кодування джерела і правила ідентифікації версії файла потребують визначення; хеш не доводить достовірності змісту.

## REQ-L3-09-10

- **Вимога:** Модуль перевірки графа повинен зіставляти тип і напрямок кожного з восьми відношень таблиці §2.2 з визначеними для нього класами початкового та кінцевого вузлів.
- **Джерело:** [ch09](../../ch09-engineering-knowledge-graph-traceability.md), §2.2 «Семантична класифікація ребер та правила цілісності».
- **Батьківська вимога:** REQ-L2-09-01.
- **Пов'язана вимога:** REQ-L3-09-08 окремо перевіряє `mitigates`, включно з можливим перетином класів.
- **Метод верифікації:** Тест.
- **Статус:** Проєкт.
- **Перевірка:** На тестових вузлах, які належать лише зазначеним класам, `satisfies` від коду до вимоги і `verifies` від тесту до вимоги відповідають таблиці; зворотні напрямки не відповідають. Для всіх восьми відношень перевіряються заданий напрямок і несумісна пара класів.
- **Примітка:** Таблиця не визначає сигнатур усіх можливих типів ребер. Невідомий тип, перетин класів і наслідки невідповідності потребують погодження; перевірка типів не доводить істинності чи походження зв'язку.
