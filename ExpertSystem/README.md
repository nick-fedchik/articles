# Експертні системи для R&D

Україномовна серія про те, як перетворити розрізнені інженерні артефакти на перевірювані знання й доказові висновки. Вона проходить шлях від визначення експертної системи та її математичного фундаменту до архітектури, інфраструктури, здобуття знань, розуміння тексту, пояснення, контрольованої дії, діагностики, навчання на досвіді та роботи з фізичними системами.

## Чотири рівні серії

### 01–10 — інженерна основа для розробника

Цей блок розрахований на software engineer, технічного ліда або архітектора, який знайомий із кодом, Git, HTTP, SQL і базовими структурами даних, але не зобов'язаний бути ML-фахівцем. Нове поняття тут проходить послідовність: практична проблема → інтуїтивна модель → дані або алгоритм → технічне обмеження → перевірюваний результат. Український термін є основним; англійський відповідник і скорочення вводяться при першій появі.

Технічна насиченість цього блоку означає не більше жаргону, а більше робочих артефактів: схеми даних, контракти, псевдокод, формули з розбором змінних, метрики, інваріанти й режими відмови. Після 10-ї статті читач має вміти зібрати мінімальний knowledge pipeline та аргументовано вибрати, де потрібні правила, пошук, вектори або LLM.

### 11–15 — прикладний ML і knowledge engineering

Цей блок адресований ML / NLP / Knowledge Engineer рівня middle і вище. Він передбачає впевнене володіння Python, SQL, базовою лінійною алгеброю, ймовірностями, IR-пайплайнами та експериментальним оцінюванням. Тут допустимі усталені англіцизми на кшталт *representation*, *inference*, *grounding*, *calibration*, *ablation*, *retrieval* і *evaluation* — але кожен має бути прив'язаний до формату даних, механізму, метрики або інваріанту.

У цьому блоці замість загальних аналогій пріоритет мають формальні припущення, проміжні представлення, протоколи перевірки, контроль витоку, регресійні набори, аналіз відмов і відтворювані експерименти. Мета — розуміти мовні моделі та проєктувати перевірюваний процес роботи зі знаннями й текстом.

### 16–19 — operational knowledge engineering

Цей блок зосереджений на життєвому циклі рішення. Він розрахований на інженерів моделей, знань, платформ і безпеки та показує, як пояснювати фактичне виведення, здобувати неявні знання людей, переходити від рекомендації до контрольованої дії й перевіряти базу знань разом із механізмом виведення.

Матеріали 16–19 описують навчальні інженерні рішення, а не універсально перевірену виробничу систему. Кожна стаття починається з конкретної проблеми, пояснює потрібні артефакти й обмеження та закінчується вимірюваними критеріями, режимами відмови й шляхом до першої реалізації.

### 20–22 — діагностика, навчання на досвіді та кіберфізичні системи

Цей спеціалізований блок показує експертну систему в динаміці. Стаття 20 пояснює, як відрізняти симптом від причини, працювати з кількома гіпотезами й вибирати наступну перевірку. Стаття 21 розрізняє пам’ять, нове знання, оновлення моделі та спосіб вибору дії й показує, чому власний журнал системи може бути зміщеним. Стаття 22 розміщує експертне міркування між датчиками, локальним керуванням, центральним рівнем і людськими повноваженнями на прикладах управління військами, робототехніки та виробництва.

Усі три статті розраховані на читача середнього технічного рівня. Вони не обіцяють автономного встановлення першопричини, безпечної самозміни чи перенесення універсальної схеми до критичного керування: модель діагностики може бути неповною, гарантії навчання залежать від покриття даних, а межі безпеки й повноважень визначає предметна область.

## Спільна рамка п'яти предметних областей

Під час літературного й технічного огляду кожна стаття оцінюється як загальна теорія та через п'ять класів застосувань: **автомобільна галузь**, **авіація**, **медицина**, **військова справа** та **законодавство**. Один дизайн не можна без змін переносити між ними. Спільні запитання допомагають побачити відмінності в даних, допустимій автоматизації, ціні помилки та повноваженнях людини.

Для кожного домену перевіряємо п'ять питань:

1. Яку конкретну проблему має розв'язати експертна система?
2. Які знання та докази придатні для машинного опрацювання?
3. Де проходить межа між рекомендацією, автоматизованою дією та забороненою автономією?
4. Хто має право затвердити остаточне рішення?
5. Якими стандартами, процедурами assurance і метриками перевіряється результат?

Законодавство особливо корисне як контрольний домен: тут недостатньо знайти схожий текст. Потрібно врахувати юрисдикцію, чинність норми в часі, ієрархію джерел, редакцію документа, винятки та межі юридичних повноважень системи.

## Формат для GitHub і GitLab

Статті використовують спільне підмноження GitHub Flavored Markdown і GitLab Flavored Markdown. Схеми зберігаються як редаговані блоки Mermaid, а формули — у LaTeX-синтаксисі `$...$` і `$$...$$`: GitHub рендерить їх через MathJax, GitLab — через KaTeX. Це дає змогу обходитися без растрових PNG. Докладніше: документація GitHub про [діаграми](https://docs.github.com/en/enterprise-cloud@latest/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams) і [математичні вирази](https://docs.github.com/en/enterprise-cloud@latest/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions), а також [GitLab Flavored Markdown](https://docs.gitlab.com/user/markdown/).

Кожна стаття містить навігацію до попередньої та наступної частин і посилання назад на цей зміст.

## Перевірка перед публікацією

У каталозі серії є локальний набір перевірок для спільного формату GitHub і GitLab. Після першого клонування встановіть зафіксовані залежності й запустіть валідацію:

```bash
npm ci
npm run validate
```

Команда послідовно перевіряє:

- структуру Markdown через `markdownlint-cli2` без нав'язування довжини рядка чи авторського стилю;
- синтаксис усіх Mermaid-блоків офіційним parser-ом Mermaid у DOM-сумісному середовищі;
- усі блокові й inline-формули через MathJax, який використовує GitHub;
- ті самі формули через KaTeX, який використовує GitLab;
- структуру заголовків, GitLab-сумісні якорі й пари `accTitle` / `accDescr` для доступності Mermaid-схем;
- існування локальних файлів і заголовків, на які ведуть відносні посилання.

Окремі команди `npm run validate:markdown`, `npm run validate:github` і `npm run validate:gitlab` зручні для діагностики. Успішний локальний прогін перевіряє синтаксис, але не гарантує піксельної тотожності платформ: GitHub або GitLab можуть оновити вбудовану версію Mermaid раніше чи пізніше за локальну залежність.
