# Підзавдання відкритих завдань

Каталог містить дрібні, самодостатні підзавдання, на які розбито вісім основних завдань із [open/](../). Кожне підзавдання має посилання на основне завдання, власні вхідні дані, межі змін і критерії приймання, тому його можна безпечно передавати окремому виконавцю (людині чи субагенту).

## 0. Місія: наукова перевірка тверджень книги

Завдання в `open/` створює окремий агент-аналітик книги. Він шукає в тексті формули, теореми, числа та результати експериментів, які читач не може перевірити сам, бо вони походять із розробок досліджуваного рушія. Мета кожного підзавдання — **підтвердити або спростувати** таке твердження, щоб книга була науково коректною й не вводила читача в оману. Реалізація функціоналу вторинна: вона потрібна лише як засіб перевірки або усунення розбіжності між книгою та кодом.

Кожне підзавдання завершується **вердиктом** по кожному твердженню, якого воно стосується:

| Вердикт | Значення | Дія над книгою |
|---|---|---|
| Підтверджено | є протокол, відтворюваний результат або перевірене джерело | посилання на протокол |
| Підтверджено з обмеженнями | підтверджено лише для описаних умов (набір, платформа, `N`) | додати умови та межі в текст |
| Спростовано | виміряно або доведено інше значення, або формула хибна | виправити або вилучити |
| Не підтверджено | протоколу немає й отримати його неможливо | вилучити або позначити як інженерну оцінку з підставами |
| Потрібне рішення автора | вибір належить автору | запитати, не вирішувати |

Принципи:
1. **Скептицизм за замовчуванням.** Початкове твердження вважається гіпотезою. «За даними автора», запис у MEMO чи ADR або наявність коду — не свідчення. Свідчення — відтворюваний запуск, доведення або первинне джерело.
2. **Незалежність.** Перевіряючий не повинен підганяти набір, метрику чи поріг під очікуваний результат. Негативний результат публікується так само, як позитивний.
3. **Книга за нашим вердиктом, а не навпаки.** Якщо код і книга розходяться, спочатку з'ясувати, що правильне наукою; потім виправляти те, що хибне, — код, текст або обидва.
4. **Звіт про спростування — повноцінний результат.** Підзавдання не вважається невдалим, якщо твердження спростовано.

## 0.1. Кодова база та попередні матеріали

Кодова база міститься в окремому репозиторії рушія; його адресу й актуальний зріз надає власник реалізації. Для кожного основного завдання виконавець знаходить дзеркальне завдання за ID та перевіряє контекст походження чисел. Внутрішні локальні шляхи не є частиною публічного протоколу відтворення.

| Завдання книги | ID дзеркального завдання рушія | Напрям перевірки |
|---|---|---|
| ZNA-167 | `TASK-ZNA-167` | Детектор зашитих доменних даних і CI-перевірка |
| ZNA-168 | `TASK-ZNA-168` | Виділення діалектичних елементів |
| ZNA-169 | `TASK-ZNA-169` | Асоціативне зіставлення графів та архітектурне рішення |
| ZNA-170 | `TASK-ZNA-170` | Бюджети обходу графа |
| TST-008 | `TASK-TST-008` | Регресійне оцінювання відповідей |
| TST-009 | `TASK-TST-009` | Калібрування міждоменної аналогії та дослідницькі матеріали |
| TST-010 | `TASK-TST-010` | Вимірювання продуктивності та регресійні тести затримки |

Правила роботи з репозиторієм рушія:
- Розробка ведеться за його власними інструкціями. Зміни коду й тестів — лише в межах підзавдання та за його правилами; результати перевірки зберігають у погодженому каталозі звітів і повертають у книгу через вердикт.
- Не змінювати чуже: дзеркальні завдання рушія не редагувати, лише посилатися на них.
- Те, що не залежить від коду (інвентаризація, джерела, протоколи, статистика), виконувати незалежно від стану реалізації.

## 1. Правила для будь-якого виконавця підзавдання

1. Виконувати лише своє підзавдання. Файли поза переліком «Дозволено змінювати» не змінювати; два підзавдання не повинні мати спільних файлів для запису, якщо вони позначені «паралельно».
2. Спочатку перевірити, що всі підзавдання зі списку «Залежить від» мають статус «Виконано». Якщо ні — не починати й повідомити про це.
3. Дотримуватися [AGENTS.md](../../../../AGENTS.md) книги: зміни лише в українському оригіналі, формат NOTE-блоків, збереження LaTeX; коміти й пуш лише за прямою вказівкою власника.
4. Не вигадувати числа, пороги, цільові показники та результати вимірювань. Якщо рішення належить автору (позначено «Рішення автора»), зупинитися й повернути запитання, а не обирати значення самостійно.
5. Не позначати як підтверджене те, що не перевірено; негативний результат фіксувати як негативний.
6. Не переносити внутрішні артефакти дослідницьких записок у книгу. Перед публікацією правок книги виконати `python3 scripts/inspect_project_leakage.py` (з кореня репозиторію `book/`).
7. Код рушія й CI містяться в окремому репозиторії реалізації (див. розділ 0.1), а не в репозиторії книги. «Кодова база» у файлах підзавдань означає саме його.
8. Після завершення: змінити рядок «Статус» у файлі підзавдання на «Виконано (дата)», дописати розділ «Звіт виконавця»: що зроблено, змінені файли, команди перевірки, **вердикт за таблицею з розділу 0 для кожного твердження**, відкриті питання. Статус основного завдання змінює лише його власник після виконання всіх підзавдань.

## 2. Формат файлу підзавдання

Назва файлу — `TASK-<код>.<номер>-<слаг>.md`. Заголовок містить: основне завдання, статус, тип роботи, залежності, блокування, перелік паралельних підзавдань, межі змін; далі — вхідні дані, кроки, результат, критерії приймання, заборони.
