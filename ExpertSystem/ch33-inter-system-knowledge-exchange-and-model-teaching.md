## Анотація

Уявіть автономний ударний або розвідувальний ройовий безпілотний комплекс чи роботизовану фабрику (DefTech, IEC 61508 [[14]](#src-14) / ISO 26262 [[15]](#src-15)). Нейромережевий класифікатор комп'ютерного зору (CV) виявляє силует об'єкта й передає векторні координати на привід наведення або маніпулятор. Якщо нейромережа не має детермінованого формального щита безпеки (*Safety Shield*), галюцинація через оптичну заваду або атаку змагальних збурень (*adversarial patch*) призведе до хибного наведення на дружній чи цивільний об'єкт. І навпаки: якщо польовий зв'язок передає телеметрію без криптографічної атестації (підписи Ed25519 та дерева Меркла), зловмисник через ін'єкцію контрприкладів скомпрометує базу знань, заблокувавши роботу всієї місії. Згідно з **авторською концепцією експертної системи як супервізора реального часу в автономних кіберфізичних комплексах (парадигма експертної супервізії реального часу за моделлю автора)**, експертна система більше не може бути ізольованим консультантом для людини-оператора: вона зобов'язана виконувати роль детермінованого супервізора в реальному часі.

Ця глава розглядає авторську архітектуру міжсистемного обміну знаннями: експертна система формує перевірені результати для заданих правил і профілів, навчає інші моделі та захищено приймає зовнішні докази. Ці runtime-результати не є повною оцінкою відповідності стандартам або сертифікацією виробу. Спочатку глава визначає ролі експертної системи в гетерогенному середовищі: оцінювач застосовних правил, щит безпеки для нейромережевих агентів і генератор перевіреного курікулуму. Далі розглянуто трансляцію предикатних обмежень у числові конверти валідності для цифрових сигнальних процесорів (DSP), методи символьної дистиляції знань у нейронні мережі за допомогою семантичних функцій втрат, а також протоколи низьколатентного обміну (NATS, gRPC, JSON-LD, SHACL). На завершення викладено механізми захисту від отруєння знань, розмежування прав за решіткою міток безпеки та робочий модуль атестації на Go.

## 1. Експертна система як постачальник знань і вчитель сторонніх систем

Традиційна інженерія знань розглядала експертну систему як кінцевого радника для людини-оператора: оператор уводить факти через діалоговий інтерфейс, рушій логічного виведення застосовує правила, а пояснювальний модуль повертає текстове обґрунтування. У кіберфізичних комплексах, роботизованих платформах і розподілених центрах керування споживачем висновку частіше стає інша інформаційна система: алгоритм планування траєкторії, мікроконтролер виконавчого механізму або конвеєр підготовки даних для навчання глибоких нейромереж.

За **авторським принципом усунення семантичного розриву між сигнальним, символьним та виконавчим трактами**, пряма передача неструктурованих даних між такими підсистемами без формалізованого контексту є неприпустимою в місійно-критичних комплексах, оскільки спричиняє розрив семантичного контексту. Якщо сигнальний обробник передає нейромережі числовий масив без знання фізичних інваріантів об'єкта, модель може вивчити хибні статистичні кореляції. Якщо ж стороння модель генерує керівні команди без перевірки нормативним оракулом, виникає ризик виходу за межі експлуатаційної безпеки. Експертна система усуває цей розрив, реалізуючи **авторську концепцію тріади міжсистемних ролей експертної системи**:

1. **Оцінювач застосовних правил (Policy/Rule Evaluator):** експертна система зіставляє поточний стан із конкретними правилами й умовами обраного профілю та повертає відтворюваний вердикт із доказами ([Глава 21](ch21-from-recommendation-to-action.md)). Така перевірка не замінює повної оцінки відповідності стандарту чи рішення уповноваженого органу.
2. **Формальний супервізор або щит безпеки (Safety Shield):** перед подачею команд на виконавчі приводи експертна система перехоплює дії сторонніх контролерів або нейромережевих агентів, блокуючи небезпечні переходи за правилами Fail-Closed ([Глава 28](ch28-dual-mode-expert-systems.md)).
3. **Генератор верифікованого курікулуму (Curriculum Generator):** експертна система синтезує навчальні вибірки для сторонніх моделей машинного навчання, маркуючи дані формальними доказами та гарантуючи відсутність суперечностей у навчальному матеріалі.

## 2. Постачання знань обробникам фізичних сигналів та сенсорної інформації

Фізичні сенсори (радари, лідари, віброперетворювачі, спектроаналізатори, тепловізійні матриці) формують потоки неперервних числових сигналів. Цифрові сигнальні процесори (DSP) і модулі комп'ютерного зору (CV) перетворюють ці сигнали на часові ряди, карти глибини та вектори ознак. Згідно з **авторським принципом семантичної сліпоти статистичних сигнальних обчислювачів (DSP / CV)**, обробники сигналів оперують суто статистичними й спектральними характеристиками (швидке перетворення Фур'є, вейвлет-фільтри, матриці коваріації), залишаючись семантично сліпими до предметного контексту та онтологічних інваріантів об'єкта. Вони не знають, що температура редуктора не може фізично зрости на сорок градусів за дві мілісекунди, або що падіння амплітуди відбитого імпульсу на певній частоті зумовлене зміною атмосферного тиску, а не відмовою випромінювача.

### 2.1. Переклад логічних норм у числові конверти валідності

За **авторською формальною математичною моделлю сенсорного конверта валідності**, експертна система транслює декларативні онтологічні аксіоми у строгі числові параметри фільтрації, які називаються **конвертами валідності (validity envelopes)**. Конверт валідності визначає гіпероб'єм у просторі вимірювань, усередині якого сигнал вважається фізично вірогідним:

```math
\mathcal{E}_s = \left\{ y(t) \in \mathbb{R}^d \;\middle|\; y_{\min} \le y(t) \le y_{\max} \;\land\; \left\|\frac{dy}{dt}\right\| \le \Delta_{\max} \;\land\; \Phi(y(t), x_{\text{state}}) = 1 \right\}
```

де $`y_{\min}`$ та $`y_{\max}`$ задають стаціонарні межі діапазону сенсора, $`\Delta_{\max}`$ обмежує фізично допустиму швидкість зміни процесу, а $\Phi$ позначає булевий предикат контекстної відповідності поточному режиму роботи агрегата $`x_{\text{state}}`$, визначеному в [Главі 22](ch22-cybernetics-edge-to-backend.md).

Коли експертна система експортує конверт валідності у сигнальний процесор або фільтр Калмана, вона задає строби інновацій (innovation gating) на основі відстані Махаланобіса Бар-Шалома та співавторів [[1]](#src-1):

```math
d_M^2(t) = \tilde{y}^T(t) S^{-1}(t) \tilde{y}(t) \le \gamma_{\text{threshold}}
```

**Параметри та вимірні величини:**
- $`\tilde{y}(t) = y(t) - \hat{y}(t|t-1) \in \mathbb{R}^d`$ — вектор інновації (нев'язки передбачення вимірювання) розмірності $d$;
- $`S(t) \in \mathbb{S}_{++}^d`$ — симетрична додатно визначена коваріаційна матриця інновації розмірності $d \times d$;
- $`\gamma_{\text{threshold}} = \chi_d^2(1 - \alpha)`$ — квантиль розподілу хі-квадрат із $d$ ступенями вільності для проектного рівня значущості $\alpha$ (наприклад, $`\alpha = 0{,}01`$);
- $`d_M^2(t) \ge 0`$ — безрозмірнісний квадрат відстані Махаланобіса.

**Операційні переходи (авторське алгоритмічне правило бінарного арбітражу інновацій сигнального фільтра) та числовий приклад:**
- Якщо $`d_M^2(t) \le \gamma_{\text{threshold}}`$, спостереження визнається фізично достовірним, і фільтр Калмана оновлює вектор стану об'єкта (`INNOVATION_ACCEPTED`);
- Якщо $`d_M^2(t) > \gamma_{\text{threshold}}`$, вимірювання кваліфікується як позаконвертна аномалія (`INNOVATION_REJECTED`); спостереження не вноситься в оцінку стану, фільтр зберігає апостеріорний прогноз, а система генерує звіт про інцидент сенсорного тракту;
- Практичний приклад розрахунку: розглядається скалярний канал тиску олії ($d = 1$). За рівня значущості $`\alpha = 0{,}01`$ критичний поріг становить $`\gamma_{\text{threshold}} = \chi_1^2(0{,}99) = 6{,}635`$. Нехай передбачене значення становить $`\hat{y} = 10{,}0\,\text{бар}`$, дисперсія інновації $`S = 0{,}25\,\text{бар}^2`$ (середньоквадратичне відхилення $`\sigma = 0{,}5\,\text{бар}`$), а поточний відлік датчика стрибнув до $`y = 11{,}6\,\text{бар}`$. Нев'язка: $`\tilde{y} = 11{,}6 - 10{,}0 = 1{,}6\,\text{бар}`$.

```math
d_M^2 = \frac{(1{,}6\,\text{бар})^2}{0{,}25\,\text{бар}^2} = \frac{2{,}56}{0{,}25} = 10{,}24.
```

Оскільки $`10{,}24 > 6{,}635`$, строб інновації відкидає вимірювання (`INNOVATION_REJECTED`), запобігаючи спотворенню фільтра Калмана раптовим стрибком тиску.

> [!NOTE]
> **Три інваріанти сенсорного конверта валідності за моделлю автора**
> 1. Багатовимірне геометричне обмеження: визначення простору допустимих сигналів $`\mathcal{E}_s`$ через комбінацію статичних меж, швидкості наростання та предикатів контекстного режиму.
> 2. Стохастичний строб інновацій: відсікання аномальних вимірювань за відстанню Махаланобіса $`d_M^2(t) \le \chi_d^2(1 - \alpha)`$ для запобігання дестабілізації фільтрів Калмана.
> 3. Детермінована деградація ваг: динамічне обнулення коефіцієнтів довіри до скомпрометованих сенсорних каналів при виявленні крос-модального спуфінгу.
> *Керування рантаймом / Інженерний інваріант:* Запобігає поширенню спотворених фізичних сигналів у символьний тракт експертного виведення.

### 2.2. Предикатні правила детекції завад та сенсорного спуфінгу

Завдяки зв'язку з інженерною онтологією експертна система виявляє узгоджені аномалії, які окремий сенсорний канал вважає валідними. Наприклад, якщо геопозиція за супутниковим приймачем показує швидкість 120 км/год, але інерціальна система фіксує нульове поздовжнє прискорення, а колісні одометри реєструють нерухомий вал, окремі обчислювачі можуть піддатися супутниковому спуфінгу. Експертна система застосовує **авторську модель крос-сенсорної детекції завад та інваріант виявлення супутникового спуфінгу**:

```math
\forall t \quad \lvert v_{\text{GNSS}}(t) - v_{\text{odo}}(t) \rvert > \epsilon_v \implies \text{SpoofingSuspected}(\text{GNSS}, t) \land \text{DegradeWeight}(\text{GNSS}, 0)
```

**Параметри та інженерні обмеження:**
- $`v_{\text{GNSS}}(t), v_{\text{odo}}(t) \ge 0`$ — миттєві оцінки поздовжньої швидкості за супутниковим навігаційним приймачем та колісними одометрами ($`\text{км/год}`$);
- $`\epsilon_v`$ — гранично допустимий поріг неузгодженості швидкості (наприклад, $`\epsilon_v = 15{,}0\,\text{км/год}`$).

**Операційні дії та приклад:**
- Якщо супутниковий приймач фіксує $`v_{\text{GNSS}} = 120\,\text{км/год}`$, а одометр передає $`v_{\text{odo}} = 5\,\text{км/год}`$, модуль обчислює різницю: $`\lvert 120 - 5 \rvert = 115\,\text{км/год} > 15\,\text{км/год}`$.
- Згідно з **авторським алгоритмічним правилом динамічної деградації ваг та переходу в автономне числення**, експертна система негайно надсилає сигнальному процесору директиву на динамічне обнулення ваги недовіреного каналу GNSS у комплексному фільтрі злиття навігаційної інформації (`DegradeWeight(GNSS, 0)`), переводячи навігацію в режим автономного числення за інерціальними даними (Dead Reckoning).

## 3. Навчання сторонніх систем: символьна дистиляція та верифікований курікулум

Коли сторонньою системою є нейромережевий класифікатор або контролер, експертна система виступає формальним учителем. Пряме навчання нейромереж на сирих емпіричних вибірках часто веде до порушення базових фізичних чи логічних законів: комп'ютерний зір може виявити дорожній знак у місці, забороненому геометрією сцени, або класифікатор електромережі прогнозує від'ємний опір ізоляції. Відповідно до **авторського принципу формалізації індуктивних упереджень нейромережевих моделей через онтологічні норми**, емпіричне навчання моделей повинно примусово спрямовуватися експертною системою через математично верифіковані обмеження, що унеможливлюють порушення фізичних інваріантів і правил безпеки.

### 3.1. Символьна дистиляція знань через семантичні функції втрат

На відміну від класичної дистиляції знань Гінтона та співавторів [[16]](#src-16), яка переносить статистичні кореляції («темне знання») через пом'якшені ймовірнісні розподіли виходів мережі-вчителя за високої температури $T$, **авторське наукове розмежування м'якої статистичної та символьної дистиляції знань** базується на прямій трансляції детермінованих правил логічного виведення у вагові коефіцієнти штучної нейромережі. Підхід спирається на механізм апостеріорної регуляризації Ху та співавторів [[2]](#src-2), де експертна система генерує розподіл цільових ймовірностей $`q(y|x)`$, що задовольняє набір логічних правил $`\mathcal{R} = \{(r_k, \lambda_k)\}`$, мінімізуючи дивергенцію Кульбака-Лейблера відносно базової нейромережі $`p_\theta(y|x)`$:

```math
\min_{q} \text{KL}(q(y|x) \parallel p_\theta(y|x)) - \sum_{k} \lambda_k \mathbb{E}_{q}[\mathbf{1}_{r_k}(x, y)]
```

де $`\mathbf{1}_{r_k}(x, y)`$ дорівнює одиниці, якщо пара $(x, y)$ задовольняє правило $`r_k`$, а $`\lambda_k \ge 0`$ визначає вагову жорсткість правила. Розв'язок оптимізаційної задачі має вигляд розподілу Гіббса:

```math
q^*(y|x) \propto p_\theta(y|x) \exp\left( \sum_k \lambda_k \mathbf{1}_{r_k}(x, y) \right)
```

Отриманий розподіл $`q^*(y|x)`$ слугує псевдоеталоном (soft labels) для навчання мережі-студента через функцію втрат крос-ентропії.

Для прямого наскрізного диференціювання логічних обмежень застосовують семантичні функції втрат Сюя та співавторів [[3]](#src-3). Якщо формальне правило представлене пропозиційною формулою $\alpha$ над виходами класифікатора, семантична втрата визначається як від'ємний логарифм імовірності істинності формули:

```math
\mathcal{L}_{\text{semantic}}(\theta, \alpha) = -\log \sum_{y \models \alpha} \prod_{j: y_j = 1} p_\theta(\hat{y}_j = 1 \mid x) \prod_{j: y_j = 0} (1 - p_\theta(\hat{y}_j = 1 \mid x))
```

Згідно з **авторським градієнтним принципом регуляризації вагових коефіцієнтів нейромережі**, під час зворотного поширення помилки градієнт семантичної втрати примусово штрафує вагові коефіцієнти мережі за будь-яке наближення виходів до конфігурацій, що порушують логічні інваріанти експертної системи ([Глава 29](ch29-neuro-symbolic-architecture.md)).

Діаграма ілюструє архітектуру взаємодії логічного вчителя та нейромережевого студента через семантичний градієнтний цикл навчання:

### 3.2. Формальні щити безпеки (Shielding) у навчанні агентів

Під час підкріплюваного навчання (Reinforcement Learning, RL) агент досліджує простір станів методом спроб і помилок. У критичних застосуваннях випадкове дослідження може спричинити фізичне руйнування механізму або перехід у заборонений аварійний стан.

Експертна система реалізує архітектуру формального екранування або щита за Альшіхом та співавторами [[4]](#src-4). Щит синтезується з безпекових специфікацій, виражених формулами лінійної темпоральної логіки (Linear Temporal Logic, LTL). Експертна система обчислює множину безпечних дій у поточному стані $`\mathcal{A}_{\text{safe}}(s_t) \subseteq \mathcal{A}`$. Якщо дія агента $`a_t \notin \mathcal{A}_{\text{safe}}(s_t)`$, щит перехоплює команду, підставляючи найближчу допустиму безпечну дію $`a_t' = \arg\min_{a \in \mathcal{A}_{\text{safe}}} \|a - a_t\|`$, і повертає агенту штраф у функції винагороди. Таким чином, стороння система вчиться оптимізувати цільову функцію виключно в межах допустимого безпекового конверта.

> [!NOTE]
> **Три засади символьного навчання та екранування агентів за моделлю автора**
> 1. Апостеріорна логічна регуляризація: формування псевдоеталонного розподілу Гіббса $`q^*(y|x)`$ для передачі предикатних правил у ваги нейромережі-студента.
> 2. Семантична диференційовна функція втрат: штрафування недопустимих логічних конфігурацій через від'ємний логарифм імовірності істинності формули $`\mathcal{L}_{\text{semantic}}`$.
> 3. Формальне LTL-екранування дій: безперервне перехоплення команд RL-агента з проекцією на множину безпечних дій $`\mathcal{A}_{\text{safe}}`$ для захисту від аварійних станів.
> *Керування рантаймом / Інженерний інваріант:* Гарантує строге дотримання безпекових інваріантів навченими моделями без ризику деструктивних фізичних дій під час дослідження середовища.

### 4.2. Суб'єктна маршрутизація в NATS JetStream

Брокер NATS використовує ієрархічні текстові суб'єкти (subjects), що дозволяє спрямовувати знання за категоріями, доменами безпеки та типами споживачів:

- `knowledge.export.dsp.envelopes.<subsystem>`: публікація конвертів валідності для сигнальних процесорів конкретної підсистеми;
- `knowledge.export.models.distillation.<domain>`: поширення навчальних корпусів і псевдоеталонів для сторонніх моделей;
- `knowledge.feedback.telemetry.anomalies.<sensor_id>`: приймання звітів про вихід спостережень за межі встановленого конверта;
- `knowledge.control.quarantine.admission`: канал координації шлюзу допуску нових фактів.

Завдяки механізму збереження черги повідомлень JetStream виконується **авторський архітектурний інваріант гарантованої доставки оновлень знань (At-least-once Persistence)**: будь-який периферійний вузол, тимчасово відключений від мережі ([Глава 22](ch22-cybernetics-edge-to-backend.md)), після відновлення зв'язку гарантовано вичитує всі актуальні оновлення в детермінованому хронологічному порядку без втрати послідовності.

### 4.3. Відкритий стандарт епістемічного обміну (OEIR) за парадигмою міжнародного стандарту ONNX: версіонування наборів операторів, згортання інтервалів і статична верифікація сигнатур

Якщо текстові протоколи на базі JSON-LD та шина повідомлень вирішують задачу транспортної доставки фактів, то для міжсистемного обміну скомпільованими графами правил між різнорідними обчислювачами (від серверів x86-64 і вбудованих вузлів ARM64 до співпроцесорів ПЛІС/FPGA) потрібен уніфікований бінарний стандарт представлення знань. В індустрії машинного навчання аналогічну кризу несумісності між фреймворками подолав відкритий міжнародний стандарт **ONNX (Open Neural Network Exchange)**, який запровадив єдину проміжну репрезентацію обчислювального графа, версіоновані реєстри операторів (`OpSet`), компіляторне злиття вузлів (*operator fusion*) і статичний верифікатор цілісності моделі (`onnx.checker`).

Спираючись на цей перевірений міжнародний базис і враховуючи специфіку детермінованого логічного виведення, автором розроблено концепцію **Відкритої епістемічної проміжної репрезентації (Open Epistemic Intermediate Representation — OEIR) М. М. Федчика**, яка стандартизує обмін виконуваними правилами через три формальні механізми:

1. **Замкнене версіонування наборів операторів виведення (`Epistemic OpSet`):**
   Кожен скомпільований сегмент правил у пакеті знань явно декларує ідентифікатор домену та цілочисельну версію набору елементарних операторів (наприклад, `epistemic.core:v1`). Семантика кожного оператора (порівняння інтервалів у фіксованій точці $Q16.16$, перевірка криптографічного дайджесту цитати, немонотонне спростування правила винятком) фіксується незмінною для заданого номера версії набору. Це гарантує багаторічну пряму та зворотну сумісність: нові покоління середовища виконання без помилок інтерпретують архівні сертифікаційні пакети знань без потреби їх повторної компіляції.
2. **Компіляторне згортання правил та топологічний перетин інтервалів (*Taxonomy & Interval Fusion*):**
   За аналогією до злиття послідовних шарів у компіляторах нейромереж, під час пакування графа OEIR оптимізатор виконує статичне згортання транзитивних ланцюжків родо-видового підпорядкування (`IsA(A, B) ∧ IsA(B, C) ∧ Rule(C) -> Rule_Fused(A)`) та обчислює перетин усіх кон'юнктивних нормативних обмежень фізичного параметра $x$, що діють у предметній області за вирахуванням спростованих винятками $`\mathcal{D}`$:

```math
\mathcal{I}_{\mathrm{fused}}(x) = \bigcap_{k \in \mathrm{Active}(\mathcal{R} \setminus \mathcal{D})} [a_k, b_k]_{Q16.16}
```

   Якщо для будь-якого робочого режиму виявляється порожній перетин $`\mathcal{I}_{\mathrm{fused}}(x) = \emptyset`$, компілятор детерміновано зупиняє збирання пакета, виявляючи взаємовиключні норми різних стандартів ще на етапі підготовки знань до передачі в експлуатацію.
3. **Статичний верифікатор сигнатур та арності предикатів (*Epistemic Model Checker*):**
   Перед монтуванням отриманого ззовні пакета знань у спільну пам'ять завантажувач запускає лінійний прохід статичного верифікатора графа. Верифікатор перевіряє, що кожен предикат $p$ у правилах та у вихідній схемі парсера запитів має ідентичну кількість аргументів (арність $`\mathrm{arity}(p)`$), сумісну фізичну розмірність одиниць вимірювання UCUM і дійсний індекс першоджерела $s$:

```math
\mathrm{ValidOEIR}(\mathcal{G}) = \mathbb{I}\!\left(\forall r \in \mathcal{G}:\; \mathrm{op}(r) \in \mathrm{OpSet}_{v} \;\land\; \mathrm{arity}(p_r) = \mathrm{arity}_{\mathrm{lex}}(p_r) \;\land\; \mathcal{I}_{\mathrm{fused}}(r) \neq \emptyset\right)
```

> [!NOTE]
> **Чотири засади відкритого стандарту епістемічного обміну (OEIR) за парадигмою ONNX (авторська концепція М. М. Федчика)**
> 1. **Уніфікована графова репрезентація з немонотонними ребрами:** розширення класичної моделі обчислювального графа ONNX підтримкою деонтичних модальностей, строгих посилань на байти першоджерел та ребер немонотонного спростування (дефітерів ASPIC+).
> 2. **Версіоновані набори операторів виведення (`Epistemic OpSet`):** сувора прив'язка кожного пакета знань до незмінної специфікації версії операторів, що унеможливлює зміну семантики правил при оновленні виконавчого ядра.
> 3. **Компіляторне згортання інтервалів і рання детекція суперечностей:** злиття численних нормативних обмежень одного параметра в єдиний інтегральний інтервал $Q16.16$ на етапі збирання скорочує глибину обчислень у рантаймі та виявляє колізії стандартів до розгортання ($`\mathcal{I}_{\mathrm{fused}} = \emptyset`$).
> 4. **Статичний верифікатор узгодженості сигнатур і арності:** автоматична перевірка сумісності імен предикатів, кількості аргументів та фізичних розмірностей між лінгвістичним нормалізатором запитів і скомпільованим доменом у момент монтування пакета в пам'ять.
> *Керування рантаймом / Інженерний інваріант:* Пакет знань, який не пройшов статичну перевірку `ValidOEIR(G) = 1` (розбіжність арності предикатів, непідтримувана версія `OpSet` або порушена цілісність посилання на першоджерело), детерміновано відхиляється завантажувачем без монтування у віртуальний адресний простір.

Послідовність повідомлень та верифікації OEIR-пакетів при міжсистемній синхронізації через брокер подій відображена на діаграмі послідовності:

## 5. Умови, правила збереження семантики та онтологічне узгодження

Класична концепція онтологій Грубера [[19]](#src-19) визначає онтологію як явну специфікацію концептуалізації, проте прагматичне зіставлення термінів не захищає від логічних колізій під час об'єднання баз знань. За **авторським принципом запобігання семантичному спотворенню при міжсистемній реплікації правил**, коли знання передаються між незалежно розробленими інформаційними системами, категорично забороняється довільне розширення або звуження смислового обсягу предикатів без доведення консервативності.

### 5.1. Консервативні розширення та локальність модулів

Сформульоване **авторське наукове розмежування між прагматичним узгодженням онтологій Грубера та формальним консервативним розширенням** спирається на теорію модульності онтологій Куенки Грау та співавторів [[8]](#src-8): експорт фрагмента знань $`\mathcal{M}`$ з вихідної онтології $`\mathcal{O}_1`$ до цільової системи $`\mathcal{O}_2`$ є коректним тоді і тільки тоді, коли $`\mathcal{M}`$ є **консервативним розширенням (conservative extension)** відносно виділеної сигнатури $\Sigma$:

```math
\mathcal{O}_1 \models \psi \iff \mathcal{M} \models \psi \quad \text{для всіх формул } \psi \text{ над сигнатурою } \Sigma
```

Це гарантує дві фундаментальні властивості:
1. **Принцип безпеки імпорту знань над виділеною сигнатурою (за формулюванням автора):** імпорт модуля не змінює зв'язків між внутрішніми поняттями цільової онтології, які не стосуються спільної сигнатури $\Sigma$.
2. **Принцип локальної дедуктивної повноти модульного виведення (за формулюванням автора):** всі наслідки над сигнатурою $\Sigma$, які могли бути виведені у повній вихідній онтології $`\mathcal{O}_1`$, можуть бути виведені виключно з виділеного модуля $`\mathcal{M}`$ без завантаження всієї бази знань.

### 5.2. Правила збереження семантичних типів

Під час трансляції знань забороняються операції неявного звуження або розширення типів даних:
- **Заборона втрати точності модальностей:** якщо вихідне твердження є деонтичною рекомендацією `SHOULD`, воно не має транслюватися у безумовну заборону `MUST NOT` стороннього протоколу без явної згоди інженера знань ([Глава 14](ch14-requirements-detection-and-formalization.md)).
- **Ізоляція частково замкненого світу (PCWA):** твердження, отримані в умовах припущення про замкненість окремої предметної області ([Глава 07](ch07-knowledge-base-typology.md)), маркуються спеціальним прапорцем повноти `scope: closed`. Стороння система не має права застосовувати правило заперечення як відмови (Negation-as-Failure) до фактів, що надходять з відкритих доменів (`scope: open`).

Скінченний автомат процедури онтологічного узгодження та захисту семантичної цілісності при імпорті зовнішнього модуля знань наведено на діаграмі переходів станів:

```mermaid
stateDiagram-v2
    accTitle: Автомат узгодження онтологічних розбіжностей та консервативного розширення
    accDescr: Машина станів верифікації зовнішнього модуля знань на збереження семантичних типів, локальності та відсутності логічних колізій.

    [*] --> IngressModule : Отримання зовнішнього модуля знань M
    
    state IngressModule {
        [*] --> SyntaxParse
        SyntaxParse --> ExtractSignature : Складання списку понять Sigma
    }
    
    IngressModule --> ConservativeCheck : Синтаксично валідовано
    IngressModule --> SyntaxError : Помилка формату схеми

    state ConservativeCheck {
        [*] --> TheoremProver
        TheoremProver --> EntailmentTest : Перевірка O1 |= psi <=> M |= psi
    }
    note right of ConservativeCheck : Контроль безпеки імпорту над сигнатурою Sigma

    ConservativeCheck --> TypeIntegrityCheck : Консервативне розширення доведено
    ConservativeCheck --> QuarantineConflict : Виявлено зміну зв'язків цільової онтології

    state TypeIntegrityCheck {
        [*] --> DeonticModalityGate : Перевірка деонтики (SHOULD -> MUST заборонено)
        DeonticModalityGate --> ScopeAudit : Аудит меж відкритого/замкненого світу (PCWA)
    }

    TypeIntegrityCheck --> AdmittedExtension : Семантичну цілісність підтверджено
    TypeIntegrityCheck --> QuarantineConflict : Виявлено неявне звуження типу

    AdmittedExtension --> [*] : Інтеграція в робочу базу знань
    QuarantineConflict --> [*] : Ескалація інженеру знань (HITL)
    SyntaxError --> [*] : Відхилено завантажувачем
```

## 6. Розмежування доступу та безпека знань: решітка міток і селективне розкриття

У складних інженерних і оборонних проєктах база знань містить твердження з різними грифами конфіденційності, правами інтелектуальної власності та обмеженнями експортного контролю. Згідно з **авторським принципом багаторівневого захисту інтелектуальної власності та грифів конфіденційності знань**, експертна система у розподіленій федерації зобов'язана запобігати витоку закритих правил і деталей апаратної топології до сторонніх систем з нижчим рівнем допуску через обов'язкову решіткову фільтрацію кожного вихідного твердження.

### 6.1. Багаторівнева безпека на базі решітки міток Деннінг

Розмежування доступу базується на класичній моделі решітки безпечних інформаційних потоків Деннінг [[9]](#src-9) та моделі Белла-ЛаПадули [[10]](#src-10). Множина міток безпеки формує частково впорядковану решітку $`(\mathcal{L}, \le, \sqcap, \sqcup)`$:

```math
\mathcal{L} = \mathcal{C} \times 2^{\mathcal{K}}
```

де $`\mathcal{C} = \{\text{Public} < \text{Internal} < \text{Restricted} < \text{Critical}\}`$ визначає лінійну ієрархію рівнів конфіденційності, а $`\mathcal{K}`$ є множиною категоріальних обмежень (наприклад, конкретні назви проєктів або консорціумів).

Мітка суб'єкта $`L_s = (c_s, K_s)`$ домінує над міткою об'єкта знання $`L_o = (c_o, K_o)`$ тоді і тільки тоді, коли:

```math
L_s \ge L_o \iff (c_s \ge c_o) \land (K_o \subseteq K_s)
```

**Параметри та умови решітки:**
- $`c_s, c_o \in \mathcal{C}`$ — рівні класифікації суб'єкта та об'єкта у впорядкованій множині $`\text{Public} < \text{Internal} < \text{Restricted} < \text{Critical}`$;
- $`K_s, K_o \subseteq \mathcal{K}`$ — множини цільових категорій допуску (компартментів);
- $`L_s = (c_s, K_s), L_o = (c_o, K_o)`$ — комбіновані мітки безпеки.

**Авторське алгоритмічне правило шлюзу експорту знань за допуском отримувача та числовий приклад:**
- Твердження $f$, помічене міткою $`L_o = L(f)`$, передається сторонній системі з допуском $`L_s = L_{\text{recipient}}`$ тоді й тільки тоді, коли допуск отримувача домінує над міткою факту: $`L_s \ge L_o`$.
- Якщо $`L_s \not\ge L_o`$, шлюз експорту відкидає факт зі статусом `REJECT_CLEARANCE_VIOLATION`.
- Практичний приклад: стороння діагностична система має допуск $`L_s = (\text{Internal}, \{\text{Avionics}, \text{Telemetry}\})`$. База знань містить факт $`f_1`$ із міткою $`L(f_1) = (\text{Internal}, \{\text{Telemetry}\})`$ та критичне калібрувальне правило $`f_2`$ із міткою $`L(f_2) = (\text{Restricted}, \{\text{Avionics}\})`$.
  - Для $`f_1`$: $`c_s = \text{Internal} \ge c_o = \text{Internal}`$ і $`K_o = \{\text{Telemetry}\} \subseteq K_s`$, отже $`L_s \ge L(f_1)`$ → експорт схвалено (`EXPORT_PERMITTED`);
  - Для $`f_2`$: $`c_s = \text{Internal} < c_o = \text{Restricted}`$, отже $`L_s \not\ge L(f_2)`$ → факт детерміновано відсікається шлюзом (`EXPORT_DENIED`).

### 6.2. Селективне розкриття доказів через дерева Меркла

Коли стороння аудиторська система вимагає підтвердження того, що певна вимога чи тест дійсно входять до затвердженого випуску бази знань, повне розкриття бази знань може розкрити конфіденційні деталі прошивки чи топології.

Для розв'язання цієї проблеми експертна система використовує криптографічні дерева Меркла [[11]](#src-11). Корінь дерева $`R_{\text{Merkle}}`$ публікується у відкритому сертифікаті випуску ([Глава 32](ch32-high-performance-knowledge-packs-mmap-and-harvesting.md)). Щоб довести присутність конкретного факту $`f_i`$ з хешем $`H(f_i)`$, експертна система генерує компактний шлях аутентифікації довжиною $O(\log N)$, який називається **доказом включення Меркла (Merkle inclusion proof)**:

```math
\pi(f_i) = \langle h_1, h_2, \dots, h_{\lceil \log_2 N \rceil} \rangle
```

Стороння система самостійно перераховує згортку:

```math
H(\dots H(H(f_i), h_1) \dots) = R_{\text{Merkle}}
```

**Параметри та числовий приклад верифікації:**
- $N$ — загальна кількість зафіксованих фактів у бінарному контейнері бази знань;
- $`H(f_i)`$ — криптографічний хеш SHA-256 цільового факту $`f_i`$;
- $`\lceil \log_2 N \rceil`$ — довжина шляху доказу включення Меркла;
- $`R_{\text{Merkle}}`$ — кореневий хеш дерева, засвідчений у публічному сертифікаті випуску.
- Якщо обчислений хеш строго збігається з $`R_{\text{Merkle}}`$, факт приймається як автентичний (`PROOF_VALID`); якщо результат відрізняється хоча б на 1 біт, транзакція відхиляється (`PROOF_INVALID`).
- Числовий розрахунок: для бази знань обсягом $N = 1024$ фактів довжина шляху становить $`\lceil \log_2 1024 \rceil = 10`$ проміжних хешів по 32 байти (сумарний розмір доказу лише $`320\,\text{байт}`$ замість передачі всього масиву в $`32\,\text{КБ}`$). Перевірка згортки на процесорі ARM Cortex-A72 займає менше ніж $`12\,\mu\text{s}`$, забезпечуючи підтвердження факту в режимі реального часу.

> [!NOTE]
> **Чотири механізми захищеного розкриття знань за моделлю автора**
> 1. Двовимірна решітка допусків: строго формалізоване відсікання знань за комбінацією рівнів конфіденційності $`\mathcal{C}`$ та цільових категорій допуску $`2^{\mathcal{K}}`$.
> 2. Принцип домінування суб'єкта: передача факту сторонній системі виключно за умови виконання відношення домінування $`L_s \ge L_o`$.
> 3. Селективне розкриття Меркла: криптографічне підтвердження належності факту базі знань через компактний логарифмічний аутентифікаційний шлях $`\pi(f_i)`$.
> 4. Нульове розголошення суміжних фактів: валідація окремих вимог сторонніми аудиторами без деанонімізації повної онтології та топології системи.
> *Керування рантаймом / Інженерний інваріант:* Забезпечує доказову перевірку нормативних тверджень зовнішніми агентами зі збереженням конфіденційності закритої інтелектуальної власності.

### 6.3. Протокол криптографічної федерації доказів (Evidence-Only Federation) та асиметричний діод знань

У багатоланцюгових інженерних консорціумах та інтегрованих промислових холдингах суміжні підприємства часто діють як автономні суверенні анклави. Прямий обмін повними онтологіями, сирцевим програмним кодом чи закритими схемотехнічними топологіями може обмежуватися регуляторними, договірними або інтелектуально-правовими умовами. Якщо для виробу застосовні вимоги ISO 26262, DO-178C чи іншого стандарту, інтегратор організує їх оцінювання в межах погодженого assurance-процесу; окрема квитанція або формальний свідок може підтвердити лише конкретне твердження й перевірку, а не повну відповідність виробу чи сертифікацію.

Автором запропоновано **протокол криптографічної федерації доказів (Evidence-Only Federation) М. Федчика**, згідно з яким суверенні інженерні домени обмінюються криптографічно підписаними квитанціями верифікації (`Verification Receipts`) та формальними свідками доведення теорем (формальні траси Lean 4 / Z3) без трансляції самих закритих фактів та правил. Підпис підтверджує походження квитанції, а свідок — конкретне формальне твердження за заданими припущеннями; жоден із цих артефактів самостійно не замінює незалежного аудиту, аналізу небезпек чи сертифікації.

Квитанція федеративного доказу формується у вигляді типізованого кортежу:

```math
\mathcal{R} = \langle \mathrm{ClaimID}, H(\mathcal{P}_{\mathrm{private}}), \pi_{\mathrm{proof}}, \tau_{\mathrm{timestamp}}, \sigma_{\mathrm{Ed25519}} \rangle
```

де $`\mathrm{ClaimID}`$ — уніфікований ідентифікатор нормативної вимоги; $`H(\mathcal{P}_{\mathrm{private}})`$ — криптографічна згортка закритого предикату постачальника; $`\pi_{\mathrm{proof}}`$ — компактний формальний свідок верифікації в системі SMT/Lean; $`\tau_{\mathrm{timestamp}}`$ — позначка часу RFC 3161; $`\sigma_{\mathrm{Ed25519}}`$ — цифровий підпис акредитованого вузла.

Для захисту внутрішнього середовища від витоку даних обмін реалізується через **асиметричний діод знань**, де інформаційний потік строго односпрямований: діод пропускає квитанції $`\mathcal{R}`$ із зовнішньої зони у внутрішній аудит, фізично унеможливлюючи зворотні канали витоку даних. Предикат допуску квитанції визначається як:

$$
P_{\mathrm{permit}}(\mathcal{R}) = \mathbb{I}\left(\mathrm{Verify}(\sigma_{\mathrm{Ed25519}}) = 1 \land \mathrm{CheckWitness}(\pi_{\mathrm{proof}}) = 1 \land (t_{\mathrm{now}} - \tau_{\mathrm{timestamp}} \le \Delta t_{\mathrm{fresh}})\right)
$$

**Параметри та умови верифікації діода:**
- $`P_{\mathrm{permit}}(\mathcal{R}) \in \{0, 1\}`$ — булеве рішення про допуск квитанції до внутрішнього реєстру доказів, не рішення про сертифікацію компонента;
- $`\mathbb{I}(\cdot)`$ — індикаторна функція істинності кон'юнкції умов;
- $`\mathrm{Verify}(\sigma_{\mathrm{Ed25519}})`$ — функція перевірки підпису за публічним ключем довіреного анклаву;
- $`\mathrm{CheckWitness}(\pi_{\mathrm{proof}})`$ — детермінована перевірка синтаксичного дерева математичного доказу;
- $`t_{\mathrm{now}} - \tau_{\mathrm{timestamp}}`$ — тривалість транспортування квитанції;
- $`\Delta t_{\mathrm{fresh}}`$ — гранично допустимий інтервал свіжості (запобігання Replay-атакам, зазвичай $`\Delta t_{\mathrm{fresh}} \le 5000\,\text{мс}`$).

**Імператив замкненого циклу розрахунку (Actionable Closed Loop):**
1. **Керування рантаймом і потоком обчислень (Control Flow & Runtime Decisions):**
	При отриманні пакета шлюз асиметричного діода обчислює предикат $`P_{\mathrm{permit}}(\mathcal{R})`$. Якщо $`P_{\mathrm{permit}} = 1`$, квитанція приймається до реєстру доказів зі статусом `FEDERATED_EVIDENCE_ACCEPTED`; це підтверджує лише підпис, свідок і свіжість конкретного твердження за заданими припущеннями, не безпеку постачальника чи відповідність виробу. Якщо $`P_{\mathrm{permit}} = 0`$ (підпис недійсний, свідок не збігається або $`t_{\mathrm{now}} - \tau > \Delta t_{\mathrm{fresh}}`$), пакет детерміновано скидається, транзакція блокується зі статусом `FEDERATION_SECURITY_REJECT`, а сторожовий таймер фіксує спробу ін'єкції недостовірних знань.
2. **Апаратний сайзинг та інфраструктурні обмеження (Hardware Dimensioning):**
   Односпрямований тракт діода знань базується на оптичному розв'язувачі (TX $\to$ RX) або виділеному ізольованому буфері DMA з підтримкою апаратного кільцевого буфера місткістю $`V_{\mathrm{diode}} = 128\,\text{КБ}`$. Це гарантує безперервне приймання квитанцій при навантаженні до $2\,500$ транзакцій/с без виникнення зворотних колізій шини.
3. **Практичний числовий приклад (Worked Numerical Example):**
   Постачальник модуля керування гальмами передає квитанцію $`\mathcal{R}`$ розміром $`512\,\text{байт}`$ із міткою $`\tau = 100\,\text{мс}`$. Сервер-верифікатор витрачає $`t_{\mathrm{sig}} = 52\,\mu\text{с}`$ на перевірку Ed25519 та $`t_{\mathrm{smt}} = 1.8\,\text{мс}`$ на перевірку коректності кроків математичного свідка Z3. Повний час аудиту становить $`t_{\mathrm{total}} = 1.852\,\text{мс}`$, що значно менше допустимого ліміту $`\Delta t_{\mathrm{fresh}} = 5000\,\text{мс}`$. Значення $`P_{\mathrm{permit}} = 1`$ задовольняє вимогу, і статус безпеки стороннього модуля затверджується без передачі вихідного коду постачальника.

> [!NOTE]
> **Авторський протокол криптографічної федерації доказів та асиметричний діод знань М. М. Федчика (Чотири засади суверенної взаємодії)**
> 1. *Принцип нульового розкриття онтології*: передача виключно криптографічних свідків верифікації та хешів артефактів без розкриття вихідного коду чи тексту регламентів.
> 2. *Асиметричний односпрямований діод знань*: фізична та протокольна неможливість зворотного витоку внутрішнього контексту через інтерфейс прийому доказів.
> 3. *Темпоральна свіжість квитанцій*: обов'язкова відсічка застарілих транзакцій ($`t_{\mathrm{now}} - \tau > \Delta t_{\mathrm{fresh}}`$) для запобігання атакам повторного відтворення (Replay Attacks).
> 4. *Апаратне ізолювання верифікації*: перевірка свідків доведення у захищеному ізольованому анклаві без доступу до зовнішньої мережі.
> *Керування рантаймом / Інженерний інваріант:* Забезпечує інтеграцію гетерогенних корпоративних баз знань зі збереженням суверенітету інтелектуальної власності кожного учасника.

## 7. Підтвердження фактів (Fact Attestation) та захист від отруєння знань

Згідно з **авторською концепцією ризику отруєння знань у розподілених федераціях**, при отриманні спостережень, результатів тестування чи правил від сторонніх систем експертна система наражається на загрозу **отруєння знань (knowledge poisoning)**. Зловмисник або скомпрометований сенсорний вузол може надсилати спотворені факти (наприклад, стверджуючи, що критична температура становить 500 °C замість 100 °C або що аварійний клапан повинен залишатися закритим під час перевищення тиску), що паралізує або спотворить подальше логічне виведення.

### 7.1. Криптографічна атестація фактів за схемою Ed25519

Кожен експортований факт підписується цифровим підписом системи-джерела за схемою Ed25519 Бернштейна та співавторів [[12]](#src-12). Структура атестованого факту містить канонічні байти твердження, ідентифікатор джерела та криптографічний підпис:

```math
\sigma = \mathrm{Ed25519}_{\mathrm{Sign}}\!\left(
SK_{\mathrm{source}},
\mathrm{SHA256}\!\left(\mathrm{Canon}(\texttt{attested-fact-v1},s,p,o,l,i)\right)\right).
```

Тут $\sigma$ — 64-байтний підпис Ed25519, $`SK_{\mathrm{source}}`$ — закритий ключ джерела (64 байти в поданні Go), а $s,p,o$ — точні байти предмета, предиката й об'єкта. $l$ позначає мітку рівня доступу в найкоротшому десятковому ASCII-поданні, $i$ — ідентифікатор джерела. `Canon` кодує домен формату та кожне з п'яти полів окремо: спочатку 8-байтну беззнакову довжину big-endian, потім незмінні байти поля. SHA-256 дає 32 байти; Ed25519 підписує саме їх, не шістнадцятковий текст. Методи `Fact.Digest` і `Fact.ID` нижче використовують цей навчальний формат.

Довжинні префікси потрібні до криптографії: кортежі `("a|b","c","d",0,"s")` та `("a","b|c","d",0,"s")` дають однакове наївне склеювання, але різні канонічні пакети по 71 байту. Це не колізія SHA-256, а неоднозначність старого кодування. Зміна будь-якого з п'яти полів створює іншу ідентичність факту; попередній підпис і дозвіл baseline не переносяться на неї. Обсяг 71 байт стосується цих двох пакетів, не загального розміру Go-об'єкта або буфера; підпис додає ще 64 байти без накладних витрат.

Підпис підтверджує походження й цілісність відносно довіреного ключа за прийнятих криптографічних припущень, не істинність твердження або дозвіл імпорту. Роль такої атестації в ланцюжках постачання артефактів розглянуто в in-toto Торрес-Аріаса та співавторів [[13]](#src-13). Для промоції в §9 застосовано інший домен підписаних байтів, `promotion-certificate-v1`, щоб підпис джерела не підміняв затвердження зміни знань.

П'ять полів утворюють лише навчальний профіль факту. Якщо тип твердження потребує одиниці, модальності, умови або області чинності, вони мають увійти до погодженої схеми й підписаних байтів, а не залишатися ігнорованими полями зовнішнього JSON. Декодер і повний контракт матеріальних атомів у цьому Go-прикладі не реалізовано; точна байтова ідентичність не є доказом семантичної повноти.

### 7.2. Таксономія загроз: форми атак отруєння знань (Knowledge Poisoning)

Отруєння бази знань у доказових системах класифікується за чотирма основними векторами впливу:

#### 7.2.1. Пряма інверсія аксіоми (Axiom Inversion / Overwrite)
Атакуючий вузол (навіть володіючи валідним сертифікатом доступу) надсилає твердження, що прямо суперечить засадничим законам фізики чи нормам безпеки:

```math
\mathrm{Attestation}: \langle \texttt{emergency\_brake}, \texttt{status\_on\_failure}, \texttt{DISABLED} \rangle
```

Мета: зняття захисних блокувань у критичний момент.

#### 7.2.2. Прихований семантичний дрейф (Stealth Semantic Drift)
Атака розтягується в часі: щосекунди надсилаються ледь помітні дельти числових меж або допусків (наприклад, граничний струм зсувається на $`+0{,}1\%`$ за кожне спостереження). Окремо кожен факт проходить локальний фільтр аномалій, але накопичувальний ефект виводить систему за безпечний експлуатаційний конверт.

#### 7.2.3. Індукція зациклення розв'язувача (Cyclic Denial-of-Reasoning)
Впровадження циклічних взаємозалежностей між новими предикатами:

```math
P_1(x) \leftarrow P_2(x), \quad P_2(x) \leftarrow P_3(x), \quad P_3(x) \leftarrow P_1(x)
```

Це провокує експоненційне зростання обчислювальної складності або зависання під час резолюційного виведення чи пошуку найменшої нерухомої точки.

#### 7.2.4. Атака Сивіли у зворотному зв'язку (Sybil Consensus Poisoning)
Компрометація пулу сенсорів для одночасної відправки фіктивних контрприкладів, що штучно перевищують поріг $`N_{\text{threshold}}`$ і змушують систему вважати фальшиву аномалію реальним зсувом фізичного середовища.

### 7.3. Шлюз вхідного контролю та життєвий цикл карантину знань

Шлюз вхідного контролю відділяє походження факту від права включити його в активні знання експертної системи. Якщо зразки з недійсним підписом і справжні кандидати мають спільний шлях просування, сам ключ сховища стає помилковим дозволом на імпорт. Якщо ж допуск прив'язано лише до назви предиката, один перевірений факт відкриває шлях неперевіреним твердженням з іншими предметом, значенням або походженням. Авторський **життєвий цикл карантину знань (Knowledge Quarantine Lifecycle)** розділяє ці стани й прив'язує рішення до точної ідентичності:

```mermaid
flowchart TD
    accTitle: Шлюз вхідного контролю та карантин фактів
    accDescr: Відхилені зразки ізолюються у форензичному сховищі без шляху промоції. Валідний новий факт стає кандидатом незалежно від відомості предиката; просування вимагає формальної й регресійної перевірки, затвердження конкретної зміни та чинної прив'язки до кандидата й baseline.

    IN["Вхідний атестований факт<br/>(Attested Fact)"] --> C1{"Криптографічний підпис<br/>(Ed25519 & Trusted Registry)"}
    C1 -->|"НЕДІЙСНИЙ"| REJ_SIG["<b>REFUSAL: DecisionRejectSignature</b><br/>Форензичне сховище й аудит"]
    C1 -->|ВАЛІДНИЙ| C2{"Сумісність з аксіомами<br/>(Authoritative Axioms)"}
    
    C2 -->|"СУПЕРЕЧНІСТЬ"| REJ_POI["<b>REFUSAL: DecisionRejectPoisoning</b><br/>Форензичне сховище й аудит"]
    C2 -->|ВІДПОВІДАЄ| C3{"Статус у базі знань"}
    
    C3 -->|"Точний факт має чинний допуск"| ADMIT["<b>DecisionAdmit</b><br/>Не весь предикат або пакет"]
    C3 -->|"Інший факт або допуску немає"| QUAR["<b>DecisionQuarantine</b><br/>Ізольований кандидат"]
    
    subgraph Quarantine["<b>Карантинне середовище верифікації (Offline/Batch Audit)</b>"]
        QUAR --> SMT{"Формальний іспит SMT/ASP успішний?<br/>Погоджений профіль та інваріанти"}
        SMT -->|"Так"| REG{"Регресійний іспит успішний?<br/>Погоджена екзаменаційна матриця"}
        SMT -->|"Ні або невідомо"| HOLD
        REG -->|"Ні або невідомо"| HOLD
        REG -->|"Так"| HITL{"Аудит інженера знань<br/>(Human-in-the-Loop)"}
        HITL -->|"ЗАТВЕРДЖЕНО конкретну зміну"| BIND{"<b>Чинний сертифікат промоції?</b><br/>Тип, точний факт, baseline, звіти,<br/>роль підписанта й повторна атестація"}
        BIND -->|"Так, версія не змінилась"| PROMOTE["Просування лише цього факту<br/>та фіксація нового покоління"]
        BIND -->|"Ні або невідомо"| HOLD["Кандидат неактивний<br/>Явна причина й аудит"]
        HITL -->|"ВІДХИЛЕНО"| HOLD
    end
```

1. **Криптографічна валідація та форензична ізоляція:** якщо відкритий ключ джерела відсутній у списку довірених або цифровий підпис не відповідає згортці байтів, факт або пакет знань негайно відхиляється від допуску в активне ядро виведення (`DecisionRejectSignature` / `REFUSAL`, ніколи не монтується в робочу пам'ять) і водночас примусово ізолюється в захищеному карантинному сховищі (`QUARANTINE`) із незмінним записом у журналі аудиту (Audit Log) для збереження криміналістичних (форензичних) доказів спроби підробки (узгоджено з регламентом [Глави 37, §8](ch37-input-information-assessment-and-algorithmic-skepticism.md#8-експертний-скепсис-як-алгоритм)).
2. **Перевірка суперечностей з аксіомами:** факт відхиляється негайно (`DecisionRejectPoisoning`), якщо його предикат прямо заперечує встановлені фундаментальні аксіоми безпеки.
3. **Кандидатний буфер та формальна офлайн-верифікація:** кожне нове твердження, навіть із відомим предикатом, потребує власного допуску. Валідний кандидат ізолюється від форензичних зразків і проходить перевірки за погодженим логічним профілем, зокрема SMT-розв'язувачем Z3 [[20]](#src-20) або ASP-розв'язувачем Clingo [[21]](#src-21), регресійний іспит та фахове затвердження конкретної зміни baseline. Формальна перевірка не зводиться до заборони будь-якого циклу ([Глава 23](ch23-knowledge-base-verification.md)).

Сертифікат промоції повинен зв'язувати тип переходу, повну ідентичність кандидата, вихідну версію baseline, звіти формальної й регресійної перевірок та уповноваженого підписанта затвердження. Сам ключ карантину, підпис постачальника або ознака «предикат відомий» не є такими свідченнями. За невідомого результату, недоступного звіту, зміни кандидата/версії або недійсного дозволу знання не активуються. Форензичний зразок не змінює статусу на кандидатний через виклик промоції: для нового розгляду потрібен окремий автентифікований вхід.

У навчальному §9 `forensics` і `candidates` є різними сховищами, а `admitted` індексується повним `Fact.ID`. Підпис джерела перевіряється знову перед просуванням; зміна довірчої конфігурації консервативно інвалідує кеш дозволів. Підписаний сертифікат прив'язаний до поточного покоління стану шлюзу, а перевірка й перехід серіалізовані одним м'ютексом. Дозвіл належить конкретному факту, не всьому предикату чи пакету; повторне використання незміненого допущеного факту не потребує нового людського підпису.

> [!NOTE]
> **Чотири стадії карантинної фільтрації знань за моделлю автора**
> 1. Криптографічна автентифікація та форензичний карантин: миттєве відхилення допуску (`REFUSAL` / `DecisionRejectSignature`) вхідних тверджень або пакетів із невалідним цифровим підписом Ed25519 без монтування в активне ядро виведення з одночасною ізоляцією артефакту в `QUARANTINE` та незмінною фіксацією інциденту в журналі аудиту.
> 2. Аксіоматична сумісність: жорстке блокування фактів, що прямо заперечують засадничі онтологічні норми та закони фізики системи.
> 3. Кандидатна ізоляція: нове твердження не успадковує допуску лише через відомий предикат; форензичні зразки не потрапляють на цей шлях.
> 4. Формальний і регресійний іспити та затвердження зміни baseline: дозвіл зв'язано з точним кандидатом, звітами й вихідною версією.
> *Керування рантаймом / Інженерний інваріант:* Без усіх необхідних чинних підстав факт не активується; відмова й форензичний запис не підміняють доказу достатності, але зберігають слід відхилення.

## 8. Зворотний зв'язок (Feedback Loop) та донавчання експертної системи

Взаємодія між системами є двостороннім процесом. Згідно з **авторською концепцією зворотного зв'язку від експлуатаційного середовища через крайові випадки**, коли підлеглі системи (DSP, комп'ютерний зір, автономні агенти) працюють у фізичному середовищі, вони неминуче стикаються з **крайовими випадками (corner cases)**: несподіваними поєднаннями погодних умов, аномальними спектрами вібрації на нових режимах чи нестандартними протокольними відповідями мережевого обладнання, які слугують єдиним легітимним емпіричним джерелом для контрольованого донавчання бази знань.

### 8.1. Черга контрприкладів та агрегація інцидентів

Якщо сторонній обробник фіксує вихід сигналу за межі встановленого конверта або нейромережа фіксує високу ентропію класифікації, формується структурований звіт про аномалію. Звіти потрапляють у чергу зворотного зв'язку (Feedback Queue).

Колектор зворотного зв'язку агрегує інциденти. Окремий одиночний викид може бути випадковою фізичною завадою сенсора і не вимагає перегляду правил. Але якщо кількість однотипних контрприкладів для певного сигналу перевищує статистичний поріг $`N_{\text{threshold}}`$, колектор позначає це явище як стійку аномалію, що свідчить про зміну фізичних характеристик середовища.

### 8.2. Живлення циклу неперервного навчання

Накопичені верифіковані контрприклади стають вхідним матеріалом для:
- Поповнення екзаменаційної матриці з [Глави 25](ch25-how-expert-systems-learn.md): новий контрприклад додається до обов'язкових негативних або граничних тестів, формуючи новий зріз складності.
- **Авторської методики детекції параметричного дрейфу сенсорів тестом CUSUM** ([Глава 26](ch26-continual-learning.md)): потік звітів аналізується статистичним тестом кумулятивних сум (CUSUM) Пейджа [[22]](#src-22) для раннього попередження про деградацію сенсорів або зсув робочої точки.
- **Авторського алгоритму адаптивного перегляду меж конверта валідності:** інженер знань або автоматичний оптимізатор пропонує оновлені межі $`\mathcal{E}_s'`$, які проходять повний цикл екзаменаційного тестування перед випуском нового покоління бінарного контейнера бази знань.

> [!NOTE]
> **Три канали захищеного зворотного зв'язку за моделлю автора**
> 1. Агрегація та фільтрація викидів: статистичне відсікання поодиноких випадкових флуктуацій сенсорів із фіксацією системних аномалій за порогом $`N_{\text{threshold}}`$.
> 2. Збагачення екзаменаційної матриці: автоматична конвертація підтверджених польових контрприкладів у нові регресійні тестові зрізи.
> 3. Адаптивне коригування конвертів: запуск статистичних процедур CUSUM для виявлення параметричного дрейфу та керованого перегляду меж валідності.
> *Керування рантаймом / Інженерний інваріант:* Перетворює експлуатаційні крайові випадки у джерело керованого та безпечного донавчання бази знань без деградації засадничих правил.

## 9. Програмна реалізація мовою Go: модуль xchange

Навчальний пакет `xchange` показує межу між підписаним зовнішнім фактом, кандидатом і конкретним дозволом його введення. Він перевіряє реальні Ed25519-підписи факту та сертифіката промоції, розділяє сховища й зв'язує перехід із поколінням стану. Це не виробничий завантажувач знань або повна реалізація всіх механізмів глави. У лістингу також залишено окремі демонстрації:
1. Експорт знань із фільтрацією за решіткою рівнів доступу та цифровим підписом Ed25519.
2. Шлюз вхідного контролю фактів із захистом від отруєння знань (перевірка підпису та аксіоматичних суперечностей).
3. Валідацію числових сигналів сенсорним конвертом.
4. Зворотний зв'язок: колектор аномалій із фіксацією порогу для запуску циклу донавчання.

Код не використовує сторонніх бібліотек, спираючись виключно на стандартний пакет Go (`crypto/ed25519`, `crypto/sha256`, `sync`, `math`).

`FormalPassed` і `RegressionPassed` у сертифікаті є **підписаними твердженнями уповноваженого власника baseline** з хешами звітів. Контролер перевіряє тип, зв'язування та підпис цих свідчень, але не запускає Z3/Clingo, не виконує регресійного іспиту й не перевіряє зміст звітів. У тестах використано синтетичні звіти та тимчасові ключі. Довірені ключі джерел і підписантів baseline задаються різними конфігураційними реєстрами; вхідний пакет не може сам додати собі таке повноваження.

У канонічному `PromotionCertificate.Digest` немає поля `Signature`; підпис обчислюється після дайджесту, без самопосилання. Зв'язаний `Baseline` — лише хеш ланцюжка змін стану цього екземпляра: довірені ключі, аксіоми й допущені факти. Це не повний маніфест усіх правил, джерел і платформ. Перевірка та зміна під м'ютексом стосуються одного процесу; немає стійкого commit, глобального replay-захисту після перезапуску, строків чинності або незмінного зовнішнього журналу. `AuditLog` повертає копію накопиченого в пам'яті журналу, не доказ його довговічності. Потрібні окремі ресурсні межі буферів; обрізання кандидатів або пропуск перевірок не є допустимою деградацією.

Одновимірний `SecurityLevel` не моделює категорій доступу; сенсорний `ValidateSample` не є повною перевіркою швидкості та особливих числових значень. Ці незалежні залишки прикладу не виправляються сертифікатом промоції.

package xchange

import (
	"crypto/ed25519"
	"crypto/sha256"
	"encoding/binary"
	"encoding/hex"
	"errors"
	"fmt"
	"math"
	"strconv"
	"sync"
	"time"
)

// SecurityLevel позначає рівень конфіденційності в решітці доступу.
type SecurityLevel int

const (
	LevelPublic SecurityLevel = iota
	LevelInternal
	LevelRestricted
	LevelCritical
)

// Dominates перевіряє умову потоку інформації в решітці безпеки (L_sub >= L_obj).
func (l SecurityLevel) Dominates(other SecurityLevel) bool {
	return l >= other
}

// Fact описує атомарне інженерне твердження.
type Fact struct {
	Subject   string        `json:"subject"`
	Predicate string        `json:"predicate"`
	Object    string        `json:"object"`
	Level     SecurityLevel `json:"level"`
	SourceID  string        `json:"source_id"`
}

func hashFields(domain string, fields ...string) [32]byte {
	h := sha256.New()
	var length [8]byte
	for _, field := range append([]string{domain}, fields...) {
		binary.BigEndian.PutUint64(length[:], uint64(len(field)))
		h.Write(length[:])
		h.Write([]byte(field))
	}
	var d [32]byte
	copy(d[:], h.Sum(nil))
	return d
}

func hexDigest(d [32]byte) string {
	return hex.EncodeToString(d[:])
}

// Digest зв'язує точні байти всіх полів; довжинні префікси усувають неоднозначність роздільників.
func (f Fact) Digest() [32]byte {
	return hashFields("attested-fact-v1", f.Subject, f.Predicate, f.Object,
		strconv.Itoa(int(f.Level)), f.SourceID)
}

func (f Fact) ID() string {
	return hexDigest(f.Digest())
}

// AttestedFact об'єднує факт із криптографічним цифровим підписом системи-постачальника.
type AttestedFact struct {
	Fact      Fact   `json:"fact"`
	Signature string `json:"signature"`
}

// SignalEnvelope перекладає символьну норму експертної системи у валідаційні межі для DSP та сенсорів.
type SignalEnvelope struct {
	SignalName string  `json:"signal_name"`
	MinValue   float64 `json:"min_value"`
	MaxValue   float64 `json:"max_value"`
	MaxDelta   float64 `json:"max_delta"`
}

// ValidateSample перевіряє фізичну допустимість нового вимірювання за межами діапазону та швидкості зміни.
func (e SignalEnvelope) ValidateSample(prevVal, curVal float64) error {
	if curVal < e.MinValue || curVal > e.MaxValue {
		return fmt.Errorf("signal %s value %.3f out of range [%.3f, %.3f]", e.SignalName, curVal, e.MinValue, e.MaxValue)
	}
	if e.MaxDelta > 0 && prevVal != 0 {
		diff := math.Abs(curVal - prevVal)
		if diff > e.MaxDelta {
			return fmt.Errorf("signal %s jump %.3f exceeds max delta %.3f", e.SignalName, diff, e.MaxDelta)
		}
	}
	return nil
}

// KnowledgeExporter експортує знання стороннім системам з фільтрацією за решіткою доступу та підписом.
type KnowledgeExporter struct {
	SystemID   string
	PrivateKey ed25519.PrivateKey
	PublicKey  ed25519.PublicKey
}

// NewKnowledgeExporter створює експортер знань із новою парою ключів Ed25519.
func NewKnowledgeExporter(systemID string) (*KnowledgeExporter, error) {
	pub, priv, err := ed25519.GenerateKey(nil)
	if err != nil {
		return nil, err
	}
	return &KnowledgeExporter{
		SystemID:   systemID,
		PrivateKey: priv,
		PublicKey:  pub,
	}, nil
}

// Export фільтрує факти за рівнем допуску отримувача й підписує дозволені твердження.
func (e *KnowledgeExporter) Export(facts []Fact, recipientClearance SecurityLevel) []AttestedFact {
	var out []AttestedFact
	for _, f := range facts {
		if !recipientClearance.Dominates(f.Level) {
			continue
		}
		f.SourceID = e.SystemID
		digest := f.Digest()
		sig := ed25519.Sign(e.PrivateKey, digest[:])
		out = append(out, AttestedFact{
			Fact:      f,
			Signature: hex.EncodeToString(sig),
		})
	}
	return out
}

// AdmissionDecision визначає вердикт вхідного контролю факту.
type AdmissionDecision int

const (
	DecisionAdmit AdmissionDecision = iota
	DecisionRejectSignature
	DecisionRejectPoisoning
	DecisionQuarantine
)

const PromotionCertificateKind = "baseline-promotion-v1"

// PromotionCertificate засвідчує результати зовнішніх перевірок і схвалення конкретної зміни.
type PromotionCertificate struct {
	Kind             string
	FactID           string
	Baseline         string
	FormalReport     string
	RegressionReport string
	FormalPassed     bool
	RegressionPassed bool
	ApproverID       string
	Signature        string
}

func (c PromotionCertificate) Digest() [32]byte {
	return hashFields("promotion-certificate-v1", c.Kind, c.FactID, c.Baseline,
		c.FormalReport, c.RegressionReport, strconv.FormatBool(c.FormalPassed),
		strconv.FormatBool(c.RegressionPassed), c.ApproverID)
}

type axiomKey struct {
	subject, predicate string
}

type AdmissionController struct {
	mu          sync.RWMutex
	trustedKeys map[string]ed25519.PublicKey
	approvers   map[string]ed25519.PublicKey
	axioms      map[axiomKey]string
	candidates  map[string]AttestedFact
	forensics   map[string]AttestedFact
	admitted    map[string]bool
	baseline    string
	auditLog    []string
}

// NewAdmissionController ініціалізує шлюз вхідного контролю.
func NewAdmissionController() *AdmissionController {
	return &AdmissionController{
		trustedKeys: make(map[string]ed25519.PublicKey),
		approvers:   make(map[string]ed25519.PublicKey),
		axioms:      make(map[axiomKey]string),
		candidates:  make(map[string]AttestedFact),
		forensics:   make(map[string]AttestedFact),
		admitted:    make(map[string]bool),
		baseline:    hexDigest(hashFields("baseline-revision-v1", "empty")),
	}
}

func (ac *AdmissionController) advanceBaseline(event string, fields ...string) {
	ac.baseline = hexDigest(hashFields("baseline-revision-v1",
		append([]string{ac.baseline, event}, fields...)...))
}

func (ac *AdmissionController) CurrentBaseline() string {
	ac.mu.RLock()
	defer ac.mu.RUnlock()
	return ac.baseline
}

// RegisterTrustedSource додає відкритий ключ довіреного постачальника знань.
func (ac *AdmissionController) RegisterTrustedSource(sourceID string, pub ed25519.PublicKey) {
	ac.mu.Lock()
	defer ac.mu.Unlock()
	ac.trustedKeys[sourceID] = append(ed25519.PublicKey(nil), pub...)
	ac.advanceBaseline("source-key", sourceID, hex.EncodeToString(pub))
	ac.admitted = make(map[string]bool)
}

// RegisterBaselineApprover є довіреним конфігураційним API, не обробником вхідного пакета.
func (ac *AdmissionController) RegisterBaselineApprover(id string, pub ed25519.PublicKey) {
	ac.mu.Lock()
	defer ac.mu.Unlock()
	ac.approvers[id] = append(ed25519.PublicKey(nil), pub...)
	ac.advanceBaseline("approver-key", id, hex.EncodeToString(pub))
	ac.admitted = make(map[string]bool)
}

// SetAuthoritativeAxiom фіксує непорушну норму, спростування якої кваліфікується як отруєння знань.
func (ac *AdmissionController) SetAuthoritativeAxiom(subject, predicate, object string) {
	ac.mu.Lock()
	defer ac.mu.Unlock()
	ac.axioms[axiomKey{subject, predicate}] = object
	ac.advanceBaseline("axiom", subject, predicate, object)
	ac.admitted = make(map[string]bool)
}

func (ac *AdmissionController) validAttestation(af AttestedFact) bool {
	pub, ok := ac.trustedKeys[af.Fact.SourceID]
	sig, err := hex.DecodeString(af.Signature)
	digest := af.Fact.Digest()
	return ok && len(pub) == ed25519.PublicKeySize && err == nil &&
		len(sig) == ed25519.SignatureSize && ed25519.Verify(pub, digest[:], sig)
}

func (ac *AdmissionController) isolate(af AttestedFact, reason string) {
	key := hexDigest(hashFields("forensic-envelope-v1", af.Fact.ID(), af.Signature))
	ac.forensics[key] = af
	ac.auditLog = append(ac.auditLog, "REFUSAL+FORENSIC: "+reason+" sample="+key)
}

// Ingest здійснює атестацію факту: перевірку підпису, сумісності з аксіомами та маршрутизацію в карантин.
func (ac *AdmissionController) Ingest(af AttestedFact) AdmissionDecision {
	ac.mu.Lock()
	defer ac.mu.Unlock()

	if !ac.validAttestation(af) {
		ac.isolate(af, "untrusted source or invalid signature")
		return DecisionRejectSignature
	}
	if existing, hasAxiom := ac.axioms[axiomKey{af.Fact.Subject, af.Fact.Predicate}]; hasAxiom {
		if existing != af.Fact.Object {
			ac.isolate(af, "authoritative axiom conflict")
			return DecisionRejectPoisoning
		}
	}

	key := af.Fact.ID()
	if ac.admitted[key] {
		return DecisionAdmit
	}
	ac.candidates[key] = af
	ac.auditLog = append(ac.auditLog, "CANDIDATE: "+key)
	return DecisionQuarantine
}

var ErrPromotionDenied = errors.New("promotion denied")

func reportDigestValid(value string) bool {
	raw, err := hex.DecodeString(value)
	return err == nil && len(raw) == sha256.Size &&
		value == hex.EncodeToString(raw) && value != hexDigest([32]byte{})
}

// PromoteFromQuarantine перевіряє підписане свідчення, але не запускає SMT або регресійні тести.
func (ac *AdmissionController) PromoteFromQuarantine(key string, cert PromotionCertificate) (AttestedFact, error) {
	ac.mu.Lock()
	defer ac.mu.Unlock()
	deny := func(reason string) (AttestedFact, error) {
		ac.auditLog = append(ac.auditLog, "PROMOTION_BLOCKED: "+reason+" fact="+strconv.Quote(key))
		return AttestedFact{}, fmt.Errorf("%w: %s", ErrPromotionDenied, reason)
	}
	af, ok := ac.candidates[key]
	if !ok {
		return deny("not an eligible candidate")
	}
	if cert.Kind != PromotionCertificateKind || cert.FactID != key || cert.Baseline != ac.baseline {
		return deny("certificate type or candidate/baseline binding mismatch")
	}
	if !cert.FormalPassed || !cert.RegressionPassed ||
		!reportDigestValid(cert.FormalReport) || !reportDigestValid(cert.RegressionReport) {
		return deny("missing successful verification attestations")
	}
	pub, trusted := ac.approvers[cert.ApproverID]
	sig, err := hex.DecodeString(cert.Signature)
	digest := cert.Digest()
	if !trusted || len(pub) != ed25519.PublicKeySize || err != nil ||
		len(sig) != ed25519.SignatureSize || !ed25519.Verify(pub, digest[:], sig) {
		return deny("invalid baseline approval signature")
	}
	if af.Fact.ID() != key || !ac.validAttestation(af) {
		return deny("candidate identity or source attestation changed")
	}
	if existing, found := ac.axioms[axiomKey{af.Fact.Subject, af.Fact.Predicate}]; found &&
		existing != af.Fact.Object {
		return deny("candidate conflicts with current axiom")
	}
	delete(ac.candidates, key)
	ac.admitted[key] = true
	ac.advanceBaseline("promote", key, hexDigest(cert.Digest()))
	ac.auditLog = append(ac.auditLog, "PROMOTED: "+key+" baseline="+ac.baseline)
	return af, nil
}

func (ac *AdmissionController) AuditLog() []string {
	ac.mu.RLock()
	defer ac.mu.RUnlock()
	return append([]string(nil), ac.auditLog...)
}

// AnomalyReport фіксує крайовий випадок чи порушення меж сенсорної інформації стороннім процесором.

// FeedbackCollector збирає зворотний зв'язок від підлеглих систем і формує кандидатів на донавчання.
type FeedbackCollector struct {

	threshold int

// NewFeedbackCollector створює колектор зворотного зв'язку з порогом спрацьовування.
func NewFeedbackCollector(threshold int) *FeedbackCollector {
	return &FeedbackCollector{
		threshold: threshold,
		incidents: make(map[string][]AnomalyReport),
	}
}

// Record реєструє новий звіт і повертає true, якщо накопичено достатньо свідчень для запуску іспиту донавчання.
func (fc *FeedbackCollector) Record(rep AnomalyReport) (bool, error) {
	if rep.SignalName == "" {
		return false, errors.New("empty signal name in report")
	}
	fc.mu.Lock()
	defer fc.mu.Unlock()

	fc.incidents[rep.SignalName] = append(fc.incidents[rep.SignalName], rep)
	if len(fc.incidents[rep.SignalName]) >= fc.threshold {
		return true, nil
	}
	return false, nil
}

// IncidentCount повертає кількість накопичених повідомлень про аномалії для сигналу.
func (fc *FeedbackCollector) IncidentCount(signalName string) int {
	fc.mu.Lock()
	defer fc.mu.Unlock()
	return len(fc.incidents[signalName])
}

Тести перевіряють такі сценарії в заявлених навчальних межах:
- Відсікання конфіденційного факту отримувачу з недостатнім рівнем допуску (`Dominates`).
- Виявлення спроби підробки байтів факту за порушенням підпису Ed25519.
- Блокування отруєння знань при спробі замінити аксіому безпеки на протилежне значення навіть при валідному підписі джерела.
- Наведені випадки відсікання стрибка й виходу за діапазон; не повну часову модель або всі особливі числові значення сенсорного тракту.
- Акумуляція аномалій для передачі контрприкладів у конвеєр донавчання експертної системи.
- Непридатність форензичних зразків до просування, тип і підпис сертифіката, його зв'язок із точним фактом та поточним baseline, обов'язковість свідчень і відсутність допуску цілого предиката.
- Відмову за зміненого кандидата або конфігурації та рівно один успішний перехід при конкурентних спробах у межах процесу.

Після збереження двох опублікованих Go-блоків як `xchange.go` і `xchange_test.go` виконуються `go test -race -count=1 xchange.go xchange_test.go` та `go vet xchange.go xchange_test.go`. Це локальні тести лістингу, не атестація реалізації VIDA, математичної достатності SMT-свідчень або фізичної безпеки сенсорів.

## Висновки
1. **Міжсистемна роль експертної системи:** у розподілених гетерогенних комплексах експертна система оцінює поточний стан за конкретними застосовними правилами й профілями, діє як формальний щит безпеки для виконавчих приводів та генератор верифікованого курікулуму для сторонніх моделей; результат оцінки не є сертифікаційним рішенням.
2. **Конверти валідності для фізичних сигналів:** предикатні правила експертної системи транслюються у числові межі значень, допустимі швидкості наростання та строби інновацій фільтрів Калмана, забезпечуючи захист сенсорних обчислювачів (DSP, CV) від шумів і навмисного спуфінгу.
3. **Символьна дистиляція та безпечне підкріплюване навчання:** логічні інваріанти передаються нейромережам через семантичні функції втрат або апостеріорну регуляризацію розподілу цільових імовірностей, а формальні щити блокують небезпечні дії агентів у режимі реального часу.
4. **Стандартизовані протоколи обміну:** сумісність забезпечується серіалізацією JSON-LD, формами обмежень SHACL та підписаними бінарними пакетами знань, а мережева доставка реалізується через брокер NATS JetStream з гарантією доставки або низьколатентний gRPC.
5. **Збереження семантики через модульність:** правила безпечного експорту гарантують властивість консервативного розширення та локальності модулів, запобігаючи неконтрольованій зміні поведінки цільової системи та втраті модальностей вимог.
6. **Решітка рівнів безпеки та селективне розкриття:** передача фактів контролюється домінуванням міток конфіденційності в решітці Деннінг, а докази включення Меркла дозволяють сторонньому аудитору перевірити автентичність норми без витоку закритого вмісту всієї бази знань.
7. **Точна область допуску знань:** джерельний підпис не замінює затвердження зміни baseline. Відхилені форензичні зразки відділено від кандидатів, а просування зв'язане з конкретним фактом, чинною версією та свідченнями формальної й регресійної перевірок. Один допущений факт не відкриває весь предикат або пакет; навчальний контролер перевіряє підписані свідчення, не доводить їхню математичну достатність.
8. **Керований зворотний зв'язок:** сторонні системи повертають структуровані звіти про контрприклади й граничні аномалії, які після досягнення статистичного порогу поповнюють екзаменаційні матриці та живлять алгоритми виявлення дрейфу без небезпечного прямого самонавчання на сирих спостереженнях.

## Словник
| Український термін | Англійський відповідник | Коротке пояснення |
|---|---|---|
| Постачання знань | Knowledge Provisioning | Процес експорту верифікованих логічних тверджень, обмежень та правил стороннім системам |
| Символьна дистиляція | Symbolic Knowledge Distillation | Перенесення формальних логічних правил експертної системи у ваги нейромережі через семантичні втрати |
| Конверт валідності | Validity Envelope | Числові межі значень та швидкостей зміни, у межах яких фізичний сигнал вважається достовірним |
| Формальний щит безпеки | Safety Shield | Механізм перехоплення й заміни неприпустимих дій зовнішніх контролерів для дотримання інваріантів |
| Консервативне розширення | Conservative Extension | Властивість модульного розширення онтології, що гарантує незмінність висновків над вихідною сигнатурою |
| Решітка рівнів безпеки | Security Lattice | Частково впорядкована структура міток конфіденційності для формального контролю інформаційних потоків |
| Селективне розкриття | Selective Disclosure | Метод доведення автентичності окремого твердження без розкриття решти закритого контексту |
| Доказ включення Меркла | Merkle Inclusion Proof | Криптографічний шлях хешів дерева Меркла, що підтверджує присутність елемента у затвердженому маніфесті |
| Атестація факту | Fact Attestation | Криптографічне засвідчення походження та цілісності твердження цифровим підписом системи-джерела |
| Отруєння знань | Knowledge Poisoning | Зловмисне або помилкове впровадження суперечливих фактів для порушення коректності логічного виведення |
| Шлюз вхідного контролю | Admission Controller | Програмний компонент, що виконує перевірку підписів, аксіом та сумісності вхідних фактів до їх збереження |
| Карантинний буфер | Quarantine Buffer | Ізольоване сховище нових фактів і правил для проходження формальних перевірок та екзаменаційних тестів |
| Форензичне сховище | Forensic store | Зразки, відхилені через атестацію або конфлікт аксіом; їхній ключ не є дозволом промоції |
| Сертифікат промоції | Promotion certificate | Типізоване підписане свідчення про конкретного кандидата, вихідний baseline і результати перевірок; не підпис кожного runtime-застосування |
| Черга контрприкладів | Counterexample Queue | Буфер накопичення повідомлень про аномалії та граничні випадки від сторонніх систем для донавчання |
