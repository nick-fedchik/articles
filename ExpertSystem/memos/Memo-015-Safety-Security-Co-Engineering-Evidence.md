# Memo-015. Свідчення спільної інженерії функціональної безпеки й кібербезпеки

**Тип:** технічний меморандум (інженерний memorandum).

**Дата:** 2026-10-03.

**Статус:** протокол запропонованих дослідів; бібліотека `reqif`, генератори CycloneDX, інструменти OpenVEX і реалізації Uptane у цьому проході не запускалися.

**Пов'язана глава:** [30](../ch30-safety-cybersecurity-co-engineering.md).

## Питання й гіпотези

Чи може експертна система автоматизувати перевірку часових бюджетів, простежуваності, складу компонентів і статусу вразливостей так, щоб відрізняти підтверджений конфлікт від нестачі свідчень і не підміняти рішень відповідальних фахівців?

H-STPA: спільна структура керування за STPA-Sec [[1]](#src-1) знаходить сценарії, яких немає в окремих переліках HARA і TARA, за прийнятних витрат часу. H-REQIF: файли ReqIF [[2]](#src-2), які пройшли перевірку бібліотекою `reqif` [[3]](#src-3), завантажуються до графа без втрати об'єктів і зв'язків. H-FIND: правило оновлення з глави 30 не класифікує нестачу свідчень як відсутність конфлікту. H-SBOM: два різні генератори переліку CycloneDX [[4]](#src-4) для однієї збірки дають різні множини компонентів, і різниця пояснюється конкретними прогалинами генераторів. H-VEX: правила над історією тверджень OpenVEX [[5]](#src-5) виявляють прострочені розслідування й неповні твердження. H-UPD: стенд перевірки оновлень за вимогами Uptane [[6]](#src-6) відхиляє атаки відкату, заморожування й змішування версій. Спростування дає будь-який випадок нестачі свідчень, класифікований як «конфлікту немає», або атака на оновлення, яку стенд пропустив.

## Базова модель і варіанти

Базою є модуль `compliance` глави 30 із п'ятьма тестами й функцією `EvaluateUpdatePolicy`. Варіанти додають реальні формати й дані.

| Варіант | Що змінюється | Що перевірити |
|---|---|---|
| C0 | модуль глави без змін | проходження п'яти тестів і відсутність зауважень `gofmt` |
| C1 | реальні вимірювання часу на стенді замість навчальних чисел | виконання нерівності бюджету для найгірших виміряних значень |
| C2 | експорт вимог з інструменту керування вимогами у ReqIF і перевірка бібліотекою `reqif` | кількість об'єктів і зв'язків до й після завантаження до графа |
| C3 | перелік CycloneDX 1.7 від двох генераторів для однієї збірки | збіг множин компонентів і причини розбіжностей |
| C4 | історія тверджень OpenVEX для компонентів переліку | час перебування в кожному статусі й порушення правил повноти |
| C5 | стенд перевірки оновлень за Uptane 2.1.0 | відхилення атак відкату, заморожування й змішування версій |
| C6 | пілотний аналіз STPA-Sec для складського контролера | нові сценарії порівняно з HARA і TARA, дублікати, витрати часу |

## Власник і межі

Менеджер функціональної безпеки відповідає за HARA, FTTI і безпечні стани. Архітектор кібербезпеки відповідає за TARA, склад компонентів і статуси вразливостей. Власник процесу кваліфікації інструментів класифікує сценарії використання експертної системи за ISO 26262-8 [[7]](#src-7). Експертна система готує перевірки й показує прогалини, але не встановлює причинності між загрозою та небезпекою. Досліди атак на оновлення виконують лише на ізольованому стенді.

## Завдання для експертної системи

| ID | Дія | Артефакт і очікування |
|---|---|---|
| COE-01 | відтворити тести модуля глави 30 | п'ять тестів проходять, `gofmt -l` не повертає файлів |
| COE-02 | звірити визначення FTTI, FDTI, FRTI і FHTI з ліцензованою копією ISO 26262-1 [[8]](#src-8); у главі 30 вони звірені лише з дослівними цитатами в рецензованих статтях | запис кожного визначення з номером пункту й дослівною цитатою; розбіжність із главою 30 зафіксувати окремо |
| COE-03 | виміряти ATDI, ATRI і FRTI на стенді в найгірших умовах, які погодив власник | виконання нерівності бюджету для максимуму й для високого перцентиля; власник обирає, яке значення приймати |
| COE-04 | скласти 30 синтетичних сценаріїв оновлення з еталонними мітками експерта | матриця помилок `EvaluateUpdatePolicy`; кількість випадків нестачі свідчень, класифікованих як «конфлікту немає», має дорівнювати нулю |
| COE-05 | перевірити експортовані файли ReqIF командою `reqif validate --use-reqif-schema` і повторним проходом без змін | код повернення, збіг вихідного й повторно записаного файла, кількість об'єктів і зв'язків у графі |
| COE-06 | запустити запити пошуку прогалин простежуваності | вимоги без батька, критичні вимоги без тесту, тести, прив'язані до застарілої редакції; точність кожного запиту за ручною перевіркою |
| COE-07 | побудувати перелік CycloneDX для власної збірки експертної системи двома генераторами | коефіцієнт Жаккара між множинами компонентів і пояснення кожної розбіжності |
| COE-08 | зіставити компоненти переліку з публічною базою вразливостей за ідентифікаторами пакетів | частка хибних збігів і пропусків на розміченій вибірці |
| COE-09 | застосувати правила до історії тверджень OpenVEX | `affected` без запису про дію, `under_investigation` старше погодженого строку, `not_affected` без обґрунтування; час у кожному статусі |
| COE-10 | змоделювати атаки відкату, заморожування й змішування версій на стенді оновлень | кожну атаку відхилено з типом помилки; час перевірки метаданих |
| COE-11 | провести пілотний аналіз STPA-Sec для складського контролера | перелік небезпечних керувальних дій чотирьох видів, нові сценарії порівняно з HARA і TARA, витрати часу команди |
| COE-12 | класифікувати три сценарії використання експертної системи за TI, TD і TCL та прогнати валідаційний набір для двох поколінь пакета знань | рівень TCL для кожного сценарію й регресії між поколіннями пакета |

## Метрики й зупинка

Для часових бюджетів звітувати залишок бюджету для максимуму й обраного перцентиля та кількість прогонів. Для правила оновлення звітувати матрицю помилок за трьома класами. Для простежуваності звітувати точність кожного запиту пошуку прогалин і час ручної перевірки одного знайденого випадку. Для складу компонентів звітувати збіг генераторів, частку хибних збігів із базою вразливостей і пропусків. Для тверджень VEX звітувати медіанний і максимальний час у кожному статусі. Для стенда оновлень звітувати частку відхилених атак, яка має дорівнювати одиниці. Для STPA-Sec звітувати кількість нових сценаріїв, дублікатів і людино-годин.

Дослід зупиняють, якщо нестача свідчень класифікована як відсутність конфлікту, якщо атака на оновлення пройшла перевірку або якщо результат стенда переносять на робочий виріб без рішення власника.

## Аналіз даних

Пошук асоціативних правил в історії змін вимог показує, які типи вимог найчастіше втрачають зв'язки після зміни. Кластеризація розв'язаних конфліктів за парами «захисна реакція, захід кібербезпеки» підказує запитання для перегляду нового проєкту. Аналіз тривалості статусів VEX показує, на яких компонентах розслідування затримуються. Усі три результати визначають порядок ручної перевірки й не замінюють її.

## Очікуваний результат

Отримати протоколи вимірювання часу, матрицю помилок правила оновлення, звіти перевірки ReqIF, порівняння генераторів переліку компонентів, звіт зіставлення з базою вразливостей, правила й статистику тверджень VEX, протокол атак на стенді оновлень, пілотний аналіз STPA-Sec і звіт класифікації інструмента. Окремо записати межі: синтетичні сценарії оновлення, один стенд, визначення часових інтервалів, звірені лише за вторинними цитатами до виконання COE-02, і залежність зіставлення вразливостей від якості ідентифікаторів пакетів.

## Абревіатури

| Скорочення | Розшифрування |
|---|---|
| ATDI | Attack Detection Time Interval, час виявлення атаки |
| ATRI | Attack Reaction Time Interval, час активації захисних заходів |
| FDTI | Fault Detection Time Interval, час від виникнення несправності до її виявлення |
| FHTI | Fault Handling Time Interval, сума FDTI і FRTI |
| FRTI | Fault Reaction Time Interval, час від виявлення несправності до безпечного стану або аварійного режиму |
| FTTI | Fault Tolerant Time Interval, інтервал часу стійкості до відмов |
| HARA | Hazard Analysis and Risk Assessment, аналіз небезпек та оцінювання ризиків |
| ID | Identifier, ідентифікатор завдання |
| ReqIF | Requirements Interchange Format, формат обміну вимогами |
| STPA-Sec | System-Theoretic Process Analysis for Security, системно-теоретичний аналіз процесів для кібербезпеки |
| TARA | Threat Analysis and Risk Assessment, аналіз загроз та оцінювання ризиків |
| TCL | Tool Confidence Level, рівень довіри до інструмента |
| TD | Tool error Detection, виявлення помилки інструмента |
| TI | Tool Impact, вплив інструмента |
| VEX | Vulnerability Exploitability eXchange, обмін даними про експлуатованість вразливостей |
