# Memo-006. Виконання моделей: затримка, енергія, автономність та ізоляція відмов

**Тип:** технічний меморандум (інженерний memorandum).  
**Дата:** 2026-10-03.  
**Статус:** запропонований протокол; прискорювачі й розподілена мережа не випробувані.  
**Пов'язані глави:** [17](../ch17-implementation-stack.md), [18](../ch18-execution-infrastructure.md).

## Питання й гіпотези

Чи зменшує обраний прискорювач наскрізну затримку або енергію на прийнятий результат при незмінній якості й контрольованих відмовах?

H-RUN: конкретний маршрут GPU або NPU поліпшить обраний показник проти CPU на заданому профілі навантаження. H-ISO: окремий процес локалізує програмний збій сервісу моделей без пошкодження пакета знань. H-MESH: мережа простійних станцій дасть прийнятну вартість пакетного індексування. Жодна гіпотеза не випливає з паспортних TOPS, трильйонів операцій за секунду.

## Варіанти й конфігурація

CPU означає центральний процесор (*Central Processing Unit*), GPU графічний (*Graphics Processing Unit*), NPU нейронний (*Neural Processing Unit*). Базовий маршрут використовує CPU і зафіксовані ваги. Кандидат змінює один складник: пристрій, середовище або точність. Сумісність експорту моделі перевіряють до порівняння.

ONNX (*Open Neural Network Exchange*) Runtime розподіляє вузли графа між провайдерами виконання; порядок провайдерів може допускати повернення непідтримуваного вузла на CPU [[1]](#src-1). OpenVINO підтримує різні маршрути локального виконання й сервіси моделей [[2]](#src-2). Успішне завантаження на прискорювач не доводить виконання всіх операторів саме на ньому.

| Профіль | Що змінювати | Що залишити незмінним |
|---|---|---|
| Енкодер одного запиту | CPU проти підтримуваного GPU/NPU | ваги, токенізатор, довжина й спосіб усереднення |
| Пакетна векторизація | пакет і число виконавців | корпус, схема фрагмента й перевірка якості |
| Переранжування | пристрій і пакет кандидатів | ті самі пари запит–фрагмент |
| Генерація | локальний сервіс і підтримувана конфігурація | вхід, ліміт виходу, граматика, параметри генерації |
| Ізоляція | бібліотека в процесі проти окремого сервісу | модель і контракт виклику |

Квантування є окремою зміною: порівняння різної точності має також вимірювати якість. Випадковий початковий стан не гарантує побітової рівності між платформами; для кожного середовища перевірити його документовані обмеження відтворюваності.

## Завдання для експертної системи

| ID | Дія | Артефакт |
|---|---|---|
| RUN-01 | зафіксувати модель, конфігурацію й підтримку операторів | маніфест ваг, драйверів, пристрою й повернення на CPU |
| RUN-02 | розділити холодні й прогріті запуски | час завантаження, компіляції й першого виконання |
| RUN-03 | подати різні довжини й погоджену конкуренцію | розподіл наскрізного часу та відмов |
| RUN-04 | зіставити CPU й один прискорений маршрут | якість, час, пам'ять і енергія на результат |
| RUN-05 | перевірити межі черги й скасування | перевищення строку має явний статус |
| RUN-06 | перезапустити сервіс і ввести дозволені ресурсні відмови | базові знання лишаються цілими; невиконаний виклик не стає успішним |
| RUN-07 | від'єднати зовнішню мережу | автономна робота на зафіксованих локальних залежностях |
| RUN-08 | оновити один драйвер або середовище в копії | дрейф векторів, зміна ранжування й остаточних вердиктів |
| MESH-01 | перевірити одну станцію перед мережею | реальні пропускна здатність, доступність та енергія |
| MESH-02 | повторити й втратити підтвердження одиниці роботи | ідемпотентний запис і виявлення конфліктних результатів |
| MESH-03 | виконати пілот на дозволених вузлах | результати проти одного виконавця з урахуванням передавання |

MESH-01–03 виконувати лише після RUN-01–08 і рішення власника про доцільність мережі. Випробування відмов проводити в окремій копії, не на виробничому сервісі. Це не запит на автоматичну закупівлю чи зміну інфраструктури.

## Договір вимірювання

Вимірювати час від приймання запиту до перевіреного результату, включно з чергою, серіалізацією й авторизацією. Для генерації окремо обліковувати час до першого токена й до повної відповіді, довжину виходу та відмови. Повільні, скасовані й помилкові запити не вилучати зі звіту без явного обліку.

Перцентилі етапів не додавати як перцентиль повного маршруту. Корельовані затримки й приховану чергу видно за наскрізними трасами; OpenTelemetry надає модель таких трас [[3]](#src-3). Вибірка трас може спотворити оцінку хвоста, тому загальні лічильники й розподіли узгоджують із політикою вибірки. Траса швидкодії не замінює доказового сертифіката й не повинна містити секретні цитати.

Енергію вимірювати на тій самій межі: весь вузол або лише пристрій, із зазначенням датчика, фонового споживання й інтервалу. Паспортні 2,5 Вт одного прискорювача не порівнювати з повним споживанням іншого комп'ютера. Витрати мережі, CPU й підготовки входу включити до наскрізної оцінки.

Пам'ять включає ваги, тензори, кеш генерації, чергу й відображені файли. Для `mmap` окремо виміряти перший доступ і прогріте читання: відображення не усуває сторінкових відмов. Для окремого процесу перевірити спільні фізичні ресурси, а не лише перезапуск процесу.

## Договір розподіленої роботи

NATS JetStream підтримує збереження й повторну доставку непідтверджених повідомлень [[4]](#src-4). Ідентифікатор одиниці охоплює джерело, модель, токенізатор, конфігурацію й схему. Результат приймають до підтвердження; збій після запису й до підтвердження має породити безпечне повторення. Два різні результати з тим самим ідентифікатором розглядають як конфлікт.

Вузол отримує лише дозволені фрагменти. Перевірити строк зберігання брокера, журнали, кеші, тимчасові файли й можливий обмін пам'яті на диск. Твердження «агент не зберігає текст» потребує перевірки всього маршруту, не лише відсутності команди запису файла.

## Метрики й приймання

Звітувати медіану, p95 і p99, пропускну здатність, частоту перевищення строку, пік пам'яті, енергію на прийнятий результат і якість. Перцентиль не є найгіршим гарантованим часом. Вимоги жорсткого реального часу потребують окремого аналізу верхніх меж і підтримуваного середовища.

Числову перевірку доповнювати скінченністю, розмірністю, нормою за договором, релевантністю пошуку й вердиктами біля порогів. Висока косинусна близькість не гарантує однакового порядку кандидатів. Для мережі обліковувати прийняті результати, а не лише всі виконані векторизації.

Власник визначає межі якості, затримки, енергії й доступності до тесту. Приймання може бути частковим: прискорювач лише для пакетних задач, CPU для коротких запитів, окремий процес лише для нестабільного середовища. Невідомі гарантії не замінюють оптимістичними числами.

## Очікуваний результат

Комплект містить маніфести, профілі навантаження, точні входи, наскрізні вимірювання, журнал відмов, звіт дрейфу та рішення. Виробниче перемикання, поширення закритих фрагментів і розгортання агентів на станціях потребують окремого дозволу власника.

## Словник

| Термін | Значення |
|---|---|
| Холодний запуск | виконання з незавантаженою моделлю або непрогрітими залежностями |
| Повернення на CPU | виконання непідтримуваних операторів центральним процесором |
| Наскрізна затримка | час усього маршруту, а не одного обчислювального ядра |
| Автономність | виконання потрібного сценарію без недоступних зовнішніх залежностей |

## Абревіатури

| Скорочення | Розшифрування |
|---|---|
| CPU | Central Processing Unit, центральний процесор |
| GPU | Graphics Processing Unit, графічний процесор |
| NPU | Neural Processing Unit, нейронний процесор |
| ONNX | Open Neural Network Exchange, формат моделей |
| TOPS | Tera Operations Per Second, трильйони операцій за секунду |
| ID | Identifier, ідентифікатор завдання |
