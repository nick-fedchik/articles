## Анотація

Усі попередні розділи цієї монографії послідовно довели фундаментальну тезу: надійна експертна система не може базуватися на стохастичних узагальненнях великих мовних моделей чи неперевірених базах фактів. Справжня експертність вимагає математичного детермінізму, формального виведення, побайтової кустодії першоджерел ($ZHR = 1.00$) та незалежного аудиту. Проте вихід системи за межі дослідницького стенда у реальне промислове середовище R&D ставить перед архітектором новий критичний виклик: **масштабованість, розподіленість і повсюдну доступність**.

Ця глава завершує теоретичний цикл монографії, формуючи для читача **референсний архітектурний прототип промислової доказової експертної системи**. Абстрагуючись від конкретних комерційних брендів мікросхем чи приватних специфікацій, глава визначає функціональні класи апаратних і програмних обчислювачів, необхідних для побудови масштабованої системи. Розглядається триланкова епістемічна сервіс-орієнтована архітектура (Epistemic SOA), де тонкі мобільні клієнти (смартфони, термінали) взаємодіють із кластером доменних сервісів через інтелектуальний семантичний брокер. Формалізується багаторівнева ієрархія пам'яті: математично доводиться умова безперервності конвеєра та повного приховування затримок ($T_{\mathrm{refill}} \ll T_{\mathrm{execute}}$) через механізм активних робочих наборів знань і симетричну подвійну буферизацію (Ping-Pong Pipeline). Для випадків неповноти окремих баз знань розроблено модель федеративного пошуку (Scatter-Gather) та багатоджерельної дефезитивної агрегації свідчень (ASPIC+). Окрему увагу приділено розподіленому семантичному тріажу дефіцитів знань на базі 64-бітного SimHash і BK-дерев із захистом від виродження простору ознак (Degeneracy Guard) та автономними WAL-буферами, а також формуванню незмінного журналу рішень (Immutable Decision Ledger) на ієрархічних Merkle-деревах із WORM-анкорингом для забезпечення юридичної та технічної неспростовності аудиту ASIL D. Наприкінці наведено інженерну матрицю вибору технологій, яка дозволяє системному архітектору розгорнути працездатний прототип на доступному йому обладнанні відповідно до бюджету проєкту.

## 1. Синтез монографії: від локальної моделі до референсного архітектурного прототипу

Тридцять дев'ять попередніх глав цієї книги детально препарували анатомію доказового штучного інтелекту. У монографії розглянуто гносеологію машинного знання ([Глава 2](ch02-epistemology-of-machine-knowledge.md)), моделі та типологію баз знань ([Глава 7](ch07-knowledge-base-typology.md)), автоматизоване вилучення норм із першоджерел ([Глава 15](ch15-knowledge-extraction-and-kb-construction.md)), строге детерміноване виведення ([Глава 16](ch16-expert-systems-architecture.md), [Глава 31](ch31-syllogistic-reasoning-and-relation-lattices.md)), подолання машинних галюцинацій ([Глава 38](ch38-curing-machine-hallucinations-and-knowledge-deficits.md)) та попперівський комплаєнс-аудит ([Глава 39](ch39-active-compliance-auditor-and-popperian-testing.md)).

Однак у практичній інженерії виникає закономірне запитання: **як зібрати всі ці теоретичні концепції в єдину працюючу систему корпоративного рівня?**

У реальних високотехнологічних R&D проєктах (автомобілебудування, авіоніка, медичне приладобудування) нормативна база налічує десятки чинних стандартів (ISO, IEC, DO, IEEE, RFC), які разом із вербатім-першоджерелами, таблицями відповідності та дефітерами займають десятки гігабайтів інформації. Водночас інженерам-дослідникам, аудиторам і розробникам необхідний повсякденний доступ до системи:
- на робочому місці за десктопом під час проєктування архітектури;
- у випробувальній лабораторії чи на полігоні з планшета або смартфона;
- в автоматизованому конвеєрі неперервної інтеграції (CI/CD) під час нічних аудитів коду.

Спроба вирішити цю задачу створенням «товстого» локального моноліту зазнає фіаско. Мобільний пристрій не здатний утримувати в оперативній пам'яті багатогігабайтні бази знань і не має обчислювальних потужностей для глибокого семантичного аналізу. З іншого боку, звичайний хмарний сервіс із популярною мовною моделлю не гарантує ні детермінізму, ні захисту від галюцинацій, ні побайтової кустодії першоджерел.

Потрібен **розподілений референсний архітектурний прототип**, побудований на принципах сервіс-орієнтованої архітектури (SOA), чіткого розмежування зон відповідальності та математично обґрунтованої ієрархії пам'яті.

## 2. Епістемічна сервіс-орієнтована архітектура (Epistemic SOA) та тонкі клієнти

Сервіс-орієнтована архітектура в інженерії програмного забезпечення традиційно вирішує задачі слабкого зв'язування компонентів, незалежного розгортання та повторного використання бізнес-функцій [[4]](#src-4). В **епістемічних доказових системах** парадигма SOA набуває якісно нового сенсу: вона забезпечує **ізоляцію контекстів істинності** та **повсюдний доступ користувачів** без ризику втрати кустодії доказів.

### 2.1. Концепція тонкого клієнта (Thin Interaction Client)

Клієнтський пристрій кінцевого користувача (інженера з якості, розробника чи аудитора) визначається як **ультратонкий агент взаємодії**:
1. **Нульове сховище знань ($S_{\mathrm{client}} = 0$):** Клієнтська програма не зберігає бази знань і не кешує локальні копії стандартів. Це усуває проблему розсинхронізації версій норм між членами інженерної команди.
2. **Абстрагування від обчислювачів:** Клієнту не потрібні апаратні прискорювачі нейромереж (NPU/GPU) чи спеціалізовані процесори правил. Завдяки цьому клієнтський інтерфейс експертної системи легко функціонує на звичайних смартфонах під керуванням мобільних ОС, у веб-браузерах через WebAssembly/PWA або у текстовому терміналі інженерної робочої станції.
3. **Строга типізація запитів та відповідей:** Обмін здійснюється через високоефективні бінарні RPC-контракти (наприклад, Protocol Buffers над gRPC чи захищені WebSockets):
   - Запит від клієнта: рядок природної мови або структурований ідентифікатор інженерного артефакту (обсяг пакета $\le 2\text{--}4\,\text{КБ}$).
   - Відповідь клієнту: структурований доказовий кортеж, що містить вердикт (`ACCEPT`, `REFUSAL`, `QUALIFIED`), ідентифікатори застосованих правил, дослівні цитати з байтовими координатами у першоджерелі та 256-бітні криптографічні геші кустодії.

> [!NOTE]
> **Три характеристики ультратонкого агента взаємодії за моделлю автора**
> 1. *Нульове сховище знань ($S_{\mathrm{client}} = 0$)*: клієнтська програма не зберігає бази знань і не кешує локальні копії стандартів, що усуває проблему розсинхронізації версій.
> 2. *Абстрагування від апаратних обчислювачів*: клієнту не потрібні прискорювачі NPU/GPU чи процесори правил, що дозволяє запуск на мобільних пристроях, браузерах та CLI.
> 3. *Строга типізація RPC-контрактів*: компактний вхідний запит (до $4\,\text{КБ}$) та структурована відповідь із повним доказовим кортежем і цифровим підписом Ed25519.
> *Керування рантаймом / Інженерний інваріант:* Тонкий клієнт суворо зберігає інваріант $ZHR = 1.00$, виконуючи суто репрезентативну функцію відображення криптографічно підписаного доказового пакета.

### 2.2. Збереження інваріанта $ZHR = 1.00$ на клієнті

Критично важливо, що тонкий клієнт не має права інтерпретувати чи самостійно узагальнювати отриману відповідь. Він виконує суто репрезентативну функцію:

```math
\text{Display}(\text{Response}) = \text{Render}(\text{Verdict}, \text{EvidenceMap}, \text{Signature})
```

де:
- $\text{Verdict} \in \{\text{ACCEPT}, \text{REFUSAL}, \text{QUALIFIED}\}$ — формальний логічний статус виведення, сформований сервером;
- $\text{EvidenceMap}$ — побайтове відображення термів виведення на координати у вихідних першоджерелах;
- $\text{Signature}$ — криптографічний цифровий підпис Ed25519 доказового пакета для гарантування незмінності.

Навіть якщо зв'язок між клієнтом і брокером тимчасово переривається під час польових випробувань, отриманий результат не втрачає юридичної та технічної сили: кожен показаний інженеру факт залишається підтвердженим цифровим підписом та гешем першоджерела.

## 3. Семантичний брокер, препроцесор дискурсу та маршрутизація за змістом

Коли в інженерній екосистемі функціонує не одна база знань, а кластер спеціалізованих сервісів, виникає ключове завдання координації: **хто і як визначає, куди саме спрямувати запит інженера?**

У класичних веб-системах маршрутизація здійснюється за мережевими адресами чи префіксами URL (наприклад, `/api/v1/orders`). В експертних системах адресація є суто **семантичною (Content-Based Semantic Routing)** і спирається на результати роботи лінгвістичного препроцесора.

### 3.1. Синтаксично-лексичний препроцесор дискурсу

Отримавши запит, Семантичний Брокер пропускає його крізь конвеєр первинного семантичного розбору:

```mermaid

    accTitle: Конвеєр синтаксично-лексичного розбору дискурсу в Семантичному Брокері
    accDescr: Поетапна трансформація природномовного запиту інженера у структуровану онтологічну сигнатуру для маршрутизації доменних правил.
```

### 3.2. Динамічний реєстр сервісів знань (Knowledge Service Registry)

Семантичний Брокер підтримує в пам'яті актуальний реєстр доступних у кластері доменних сервісів. Кожен сервіс при реєстрації публікує формальний маніфест:
- **Ідентифікатор та ендпоінт:** Мережева адреса (IP/порт або черга повідомлень);
- **Простір знань (Knowledge Domain):** Набір обслуговуваних стандартів та версій онтологій (відповідно до вимог SemVer 2.0.0);
- **Клас обчислювача:** Програмний CPU, масив векторних процесорів або спеціалізоване апаратне ядро детермінованого виведення;
- **Метрики пропускної здатності:** Поточна глибина черги запитів та оцінка затримки обчислення.

Брокер обчислює функцію відповідності між онтологічною сигнатурою запиту $\mathcal{S}_{\mathrm{query}}$ та простором знань $\mathcal{P}_{\mathrm{domain}}$ у паспорті сервісу $\mathcal{P}_{\mathrm{service}}$:

```math
\mathrm{Affinity}(\mathcal{S}_{\mathrm{query}}, \mathcal{P}_{\mathrm{service}}) = \frac{\lvert\mathcal{S}_{\mathrm{query}} \cap \mathcal{P}_{\mathrm{domain}}\rvert}{\lvert\mathcal{S}_{\mathrm{query}}\rvert}
```

де:
- $\mathcal{S}_{\mathrm{query}}$ — множина онтологічних концептів і доменних маркерів, екстрагованих із запиту інженера;
- $\mathcal{P}_{\mathrm{domain}}$ — множина підтримуваних стандартів та версій онтологій у паспорті сервісу $\mathcal{P}_{\mathrm{service}}$;
- $\lvert \mathcal{S}_{\mathrm{query}} \cap \mathcal{P}_{\mathrm{domain}} \rvert$ — потужність перетину онтологічних сигнатур (число зіставлених концептів);
- $\lvert \mathcal{S}_{\mathrm{query}} \rvert$ — загальна кількість онтологічних маркерів у вхідному запиті;
- $\mathrm{Affinity}(\mathcal{S}_{\mathrm{query}}, \mathcal{P}_{\mathrm{service}}) \in [0, 1]$ — нормований коефіцієнт семантичної спорідненості (значення $1.0$ відповідає повному охопленню домену запиту).

Сервіс із найвищим показником близькості призначається головним виконавцем (*Primary Evaluator*).

## 4. Теоретична модель багаторівневої ієрархії пам'яті та подвійної буферизації

3. **Пропускна здатність каналу обміну ($B_{\mathrm{channel}}$):** Передавання повного масиву знань на обчислювач під час кожного запиту спричиняє неприпустимий простій системи ($> 1$ хвилини), що руйнує комфортний діалог інженера ($0.5\text{--}2.0\,\text{с}$).

### 4.1. Концепція Активного робочого набору (Active Working Set — AWS)

Замість переміщення всього корпусу знань, семантичний диспетчер формує **Активний робочий набір (AWS)**:

```math
\mathrm{AWS} = \mathrm{Closure}(\mathcal{R}_{\mathrm{target}}) = \mathcal{R}_{\mathrm{target}} \cup \mathrm{Prerequisites}(\mathcal{R}_{\mathrm{target}}) \cup \mathrm{Defeaters}(\mathcal{R}_{\mathrm{target}})
```

де:
- $\mathcal{R}_{\mathrm{target}}$ — множина цільових правил, активована онтологічною сигнатурою запиту;
- $\mathrm{Prerequisites}(\mathcal{R}_{\mathrm{target}})$ — предикати-передумови, необхідні для детермінованого розв'язання залежностей;
- $\mathrm{Defeaters}(\mathcal{R}_{\mathrm{target}})$ — множина асоційованих дефітерів (винятків і контрправил);
- $\mathrm{AWS}$ — транзитивне логічне замикання правил без текстових цитат першоджерел, оптимізоване для миттєвого завантаження в локальний кеш обчислювача.

AWS містить лише математичний скелет правил: числові ліміти, логічні умови, ідентифікатори дефітерів та 256-бітні геші цитат. Вербатім-тексти першоджерел залишаються у сховищі Рівня 0. Обсяг AWS зменшується до **$8\text{--}32\,\text{МБ}$**, що передається стандартними промисловими шинами за лічені частки секунди.

> [!NOTE]
> **Три компоненти Активного робочого набору (AWS) за моделлю автора**
> 1. *Цільовий пул правил ($\mathcal{R}_{\mathrm{target}}$)*: множина актуальних нормативних вимог, активованих онтологічною сигнатурою запиту.
> 2. *Транзитивні передумови ($\mathrm{Prerequisites}$)*: предикати та залежності, необхідні для замкненого детермінованого логічного виведення.
> 3. *Асоційовані дефітери ($\mathrm{Defeaters}$)*: повний перелік винятків і контрправил, що можуть підірвати або обмежити застосування цільової норми.
> *Керування рантаймом / Інженерний інваріант:* Обсяг AWS стискається до $8\text{--}32\,\text{МБ}$ шляхом відокремлення вербатім-цитат, забезпечуючи передачу по шині за частки секунди.

### 4.2. Математична умова безперервності конвеєра подвійної буферизації (Ping-Pong Pipeline)

У детермінованих експертних системах неприпустима ситуація, коли високопродуктивне обчислювальне ядро зупиняється в очікуванні надходження чергової порції правил із повільного зовнішнього накопичувача. Для усунення затримок пам'ять процесора правил організовується як два симетричні незалежні банки однакового розміру: Банк A та Банк B. Поки процесор опрацьовує правила в одному банку, контролер прямого доступу до пам'яті (DMA) у фоновому режимі заповнює інший банк наступною порцією знань.

Час заповнення одного банку даними з локального системного ОЗП ($T_{\mathrm{refill}}$) визначається відношенням місткості банку до реальної пропускної здатності шини передавання:

```math
T_{\mathrm{refill}} = \frac{V_{\mathrm{bank}}}{B_{\mathrm{bus}}}
```

де:
- $V_{\mathrm{bank}}$ — місткість одного банку швидкої внутрішньокристальної пам'яті (наприклад, $256\,\text{КБ}$ Block RAM на FPGA або виділеного статичного ОЗП SRAM у кристалі);
- $B_{\mathrm{bus}}$ — ефективна пропускна здатність внутрішньої шини підкачування знань (наприклад, $1.2\,\text{ГБ/с}$ для шини AXI4-Stream / PCIe DMA);
- $T_{\mathrm{refill}}$ — розрахунковий час фонового наповнення банку даними без участі процесора правил;
- $T_{\mathrm{execute}}$ — час, необхідний процесору правил для повного систолічного зіставлення вхідного пакета вимог із блоком знань місткістю $V_{\mathrm{bank}}$.

**Теорема приховування затримок (Latency Hiding Invariant):**
Конвеєр виведення функціонує з максимальним коефіцієнтом використання обчислювальних ресурсів ($\eta = 1.00$) без жодного такту простою процесора (zero wait-states) тоді й тільки тоді, коли час фонового наповнення не перевищує часу обчислення поточної порції правил:

```math
T_{\mathrm{refill}} \le T_{\mathrm{execute}}
```

**Практичне інженерне застосування результату розрахунку:**

Отримане значення $T_{\mathrm{refill}}$ та його співвідношення з $T_{\mathrm{execute}}$ є не просто теоретичною оцінкою, а **робочим інструментом системного проєктування та динамічного диспетчеризування**:

1. **Апаратний сайзинг (Hardware Dimensioning):**
   Формула задає гранично допустимий розмір банку швидкої пам'яті $V_{\mathrm{bank}}$ під час проєктування апаратного комплексу:

```math
V_{\mathrm{bank}} \le B_{\mathrm{bus}} \cdot T_{\mathrm{execute}}
```

   Якщо архітектор помилково виділить надмірно великий банк (наприклад, $V_{\mathrm{bank}} = 16\,\text{МБ}$), шина з пропускною здатністю $1.2\,\text{ГБ/с}$ потребуватиме на його заповнення:

```math
T_{\mathrm{refill}} = \frac{16\,\text{МБ}}{1.2\,\text{ГБ/с}} \approx 13.3\,\text{мс}
```

   Якщо процесор завершує перевірку правил за $T_{\mathrm{execute}} = 2.0\,\text{мс}$, виникає деградація конвеєра (*Pipeline Stall*): процесор примусово зупиняється на $11.3\,\text{мс}$ в очікуванні шини, а коефіцієнт корисної дії ядра падає до:

```math
\eta = \frac{T_{\mathrm{execute}}}{T_{\mathrm{refill}}} = \frac{2.0\,\text{мс}}{13.3\,\text{мс}} \approx 0.15
```

   (85% тактової частоти дорогого кремнієвого ядра втрачається вхолосту). Розрахунок доводить: для збереження безперервності розмір порції правил не повинен перевищувати $256\text{--}512\,\text{КБ}$.

2. **Динамічне планування порцій правил (Adaptive Chunk Sizing) у софтверному рантаймі:**
   Під час формування Активного робочого набору (AWS) семантичний диспетчер динамічно оцінює складність правил у черговій порції. Якщо правила прості й прогнозований час виконання зменшується ($T_{\mathrm{execute}} \to 0.5\,\text{мс}$), диспетчер автоматично пакує правила в менші фрагменти або активує burst-режим шини DMA, запобігаючи зупинці обчислювального ядра.

3. **Режими функціонування та інженерні рішення за результатами зіставлення:**
   - **Оптимальний детермінований режим ($T_{\mathrm{refill}} \ll T_{\mathrm{execute}}$, запас $\ge 2\times$):**
     Для типового блоку знань у $256\,\text{КБ}$ час підкачування становить $T_{\mathrm{refill}} = \frac{256\,\text{КБ}}{1.2\,\text{ГБ/с}} \approx 218\,\mu\text{с}$. Систолічне зіставлення пакета складних інженерних вимог проти цих правил займає $T_{\mathrm{execute}} \approx 1.5\text{--}5.0\,\text{мс}$. Запас часу складає від 7 до 23 разів.
     **Дія системи:** Пасивний банк гарантовано заповнюється задовго до завершення розрахунків. У момент готовності процесора апаратний комутатор за **1 такт** перемикає банки ($A \leftrightarrow B$), забезпечуючи наскрізну продуктивність $\eta = 1.00$ та повну детермінованість часу відповіді (WCET).
   - **Гранична зона конкуренції за шину ($0.8 \cdot T_{\mathrm{execute}} < T_{\mathrm{refill}} \le T_{\mathrm{execute}}$):**
     Запас мінімальний. Будь-яка тимчасова колізія на внутрішній шині (сторонні переривання, звернення периферії) здатна спричинити прострочення дедлайну конвеєра.
     **Дія системи:** Диспетчер активує пріоритетний арбітраж шини (*DMA Channel Priority / QoS*), надаючи потоку знань найвищий рівень пріоритету перед іншими системними процесами.
   - **Аварійний режим дефіциту пропускної здатності ($T_{\mathrm{refill}} > T_{\mathrm{execute}}$):**
     **Дія системи:** Апаратний сторожовий таймер фіксує простій конвеєра. Семантичний диспетчер активує режим деградації: тимчасово обмежує паралелізм векторного ядра або відсікає необов'язкові дефітери другого порядку, повертаючись до стабільного стану $T_{\mathrm{refill}} \le T_{\mathrm{execute}}$.

> [!NOTE]
> **Три інженерні виміри теореми приховування затримок подвійної буферизації за моделлю автора**
> 1. *Апаратний сайзинг швидкої пам'яті*: обмеження розміру банку Block RAM умовою $V_{\mathrm{bank}} \le B_{\mathrm{bus}} \cdot T_{\mathrm{execute}}$ (оптимально $256\text{--}512\,\text{КБ}$) для запобігання апаратному простою конвеєра.
> 2. *Динамічне адаптивне пакування правил*: автоматичне коригування розміру блоків диспетчером у рантаймі відповідно до обчислювальної складності порції та пропускної здатності шини DMA.
> 3. *Трьохрежимний арбітраж перемикання*: функціонування в детермінованому режимі ($T_{\mathrm{refill}} \ll T_{\mathrm{execute}}$) з однотактним перемиканням банків, пріоритезація шини при конкуренції та деградація при аварії.
> *Керування рантаймом / Інженерний інваріант:* Виконання умови $T_{\mathrm{refill}} \le T_{\mathrm{execute}}$ гарантує безперервність роботи ядра з нульовими тактами простою ($\eta = 1.00$).

### 4.3. Систолічний пакетний аудит (Batch Compliance Sweeps)

Для масової верифікації (наприклад, одночасна перевірка $M = 1\,500$ вимог безпеки проти $K = 500$ нормативних правил):
- Вимоги подаються як конвеєрний векторний потік;
- Елементарні атомарні порівняння виконуються за $1\text{--}4$ такти апаратної частоти;
- Загальний час апаратної перевірки $750\,000$ пар становить менше **$30\text{--}50\,\text{мс}$**, що забезпечує наскрізний час відповіді менше $1.0\,\text{с}$ для всієї системи.

## 5. Багатоджерельна дефезитивна агрегація знань (ASPIC+ / Dung)

В інженерних R&D проєктах високої складності жодна окрема база знань не володіє абсолютною монополією на повноту інформації. Окремий доменний сервіс може повернути результат, який не є однозначним.

### 5.1. Тригери неповноти знань (Uncertainty Triggers)

Семантичний Брокер ідентифікує необхідність підключення додаткових сервісів за трьома строгими ознаками:
1. **Низький дискретний бал достовірності ($Score < 70/100$):** Посилання походить з негармонізованого або вторинного джерела;
2. **Неімперативний нормативний статус (Informative vs Normative):** Правило вилучено з довідкового розділу або додатку (*Guideline / May / Informative Annex*), тоді як інженер вимагає сертифікаційного вердикту;
3. **Відкритий дефіцитний стан (Ungrounded Defeater):** Правило містить умову-виняток `unless condition_X`, але в локальній базі знань факт `condition_X` відсутній.

#### 5.2.1. Короборація свідчень (Corroboration)

Під час аудиту критичних систем (наприклад, вимог ISO 26262 ASIL-D [[5]](#src-5) або DO-178C DAL-A [[6]](#src-6)) свідчення від одного доменного сервісу може мати ненульовий епістемічний дефіцит або недостатній рівень довіри для безумовного автоматичного висновку. Механізм короборації усуває суб'єктивність шляхом об'єднання незалежних доказів від суміжних вузлів кластера. Якщо два або більше сервісів незалежно доходять узгодженого твердження, сукупна ймовірнісна довіра до висновку математично зростає за теоремою про ймовірність об'єднання незалежних подій:

```math
\mathrm{Conf}(A_1 \cup A_2) = 1 - (1 - \mathrm{Cred}(A_1)) \cdot (1 - \mathrm{Cred}(A_2))
```

де:
- $\mathrm{Cred}(A_i) \in [0, 1)$ — дискретний рівень достовірності свідчення, наданого доменним сервісом $i$ (визначається авторитетністю джерела знань та глибиною трасованості);
- $\mathrm{Conf}(A_1 \cup A_2) \in [0, 1)$ — сукупна ймовірнісна довіра до скороборованого висновку після агрегації незалежних аргументів $A_1$ та $A_2$.

**Практичне застосування та інженерні висновки з результату обчислень:**
1. **Точка виклику в життєвому циклі:** Розрахунок виконується семантичним брокером на етапі зведення (Gather-фаза), коли надіслані від кількох вузлів докази узгоджуються щодо одного цільового предикату.
2. **Критерії прийняття системних рішень за числовими порогами:**
   - **Поріг автоматичного закриття вимоги ($\mathrm{Conf} \ge \tau_{\mathrm{accept}} = 0.95$):** Доказ вважається вичерпним. Система автоматично присвоює вердикт `ACCEPT`, накладає криптографічний підпис Ed25519 та передає підтверджений артефакт у сертифікаційний пакет без потреби участі експерта.
   - **Зона експертного доопрацювання ($0.80 \le \mathrm{Conf} < 0.95$):** Система формує кваліфікований вердикт `QUALIFIED`. Доказовий пакет маркується як умовно прийнятний та автоматично ескалується провідному архітектору (людина в циклі керування, *Human-in-the-Loop*) із побайтовим зазначенням слабких місць аргументації.
   - **Зона недостатності свідчень ($\mathrm{Conf} < 0.80$):** Система блокує перевірку зі статусом `REFUSAL`. Запит відхиляється через відсутність достатнього теоретичного підґрунтя в базі знань.
3. **Числовий інженерний приклад:**
   Нехай вузол аналізу архітектурних патернів повертає твердження $A_1$ із довірою $\mathrm{Cred}(A_1) = 0.85$ (окремо цього недостатньо для автоматичної сертифікації ASIL-D, де поріг становить $0.95$). Суміжний вузол аудиту пам'яті незалежно підтверджує безпеку того ж фрагмента аргументом $A_2$ з достовірністю $\mathrm{Cred}(A_2) = 0.80$. Підсумкова довіра:

```math
\mathrm{Conf}(A_1 \cup A_2) = 1 - (1 - 0.85) \cdot (1 - 0.80) = 1 - (0.15 \cdot 0.20) = 1 - 0.03 = 0.97
```

   Оскільки $0.97 \ge \tau_{\mathrm{accept}} = 0.95$, взаємне підтвердження двох незалежних джерел успішно подолало поріг автоматичного допуску, усунувши необхідність ручної експертизи.

#### 5.2.2. Анулювання слабких тверджень (Defeat / Undercutting)

В інженерних регламентах нормативні вимоги поділяються за строгістю модальності: імперативні обов'язкові правила (*Shall / Must*), рекомендаційні настанови (*Should / Recommended*) та довідкові примітки (*May / Informative*).

Якщо під час федеративного пошуку виявляється конфлікт між висновками сервісів, система не застосовує ймовірнісне зважування. Відповідно до правил недемонстративного виведення ASPIC+, імперативна норма з вищим пріоритетом ($\mathrm{Rank} = \text{Shall}$) безумовно анулює (*undercuts*) рекомендаційний або довідковий аргумент нижчого рангу ($\mathrm{Rank} = \text{Should/May}$). Слабкий аргумент вилучається з кінцевого графа обґрунтування, а в аудиторському протоколі фіксується точне посилання на анульований пункт стандарту.

#### 5.2.3. Кваліфікована відмова при нормативній колізії (Qualified Conflict)

Критична ситуація виникає тоді, коли два незалежні гармонізовані стандарти однакової юридичної сили (наприклад, вимоги функціональної безпеки ISO 26262 та специфікації кібербезпеки ISO/SAE 21434 на рівні модальності *Shall*) містять взаємовиключні імперативи щодо однієї архітектурної операції.

У такій ситуації, згідно з рекомендаціями стандартів довіреного штучного інтелекту (зокрема, NIST AI RMF 1.0 [[7]](#src-7)), експертна система **категорично забороняє стохастичне вгадування компромісу** чи вибір «найбільш імовірного» варіанта нейромережею. Система активує захисний шлюз **Fail-Closed**:
1. Формує типізований вердикт `QUALIFIED_CONFLICT`;
2. Генерує двостороннє дерево колізії із зазначенням конкретних пунктів обох стандартів;
3. Блокує автоматичний випуск артефакту в CI/CD та ескалує проблему на головного системного архітектора для формування офіційного інженерного обґрунтування винятку (*Safety Deviation Justification*).

> [!NOTE]
> **Три гілки федеративного аргументаційного арбітражу ASPIC+ за моделлю автора**
> 1. *Короборація свідчень (Corroboration)*: підвищення ймовірнісної довіри $\mathrm{Conf}(A_1 \cup A_2)$ при узгодженні незалежних сервісів із порогом автоматичного допуску $\tau_{\mathrm{accept}} = 0.95$.
> 2. *Анулювання тверджень (Undercutting Defeat)*: безумовне скасування рекомендацій нижчого рангу (Should/May) імперативною нормою вищого пріоритету (Shall/Must).
> 3. *Кваліфікована відмова при нормативній колізії (Qualified Conflict)*: блокування виведення через захисний шлюз Fail-Closed при взаємовиключних імперативах однакової сили без права стохастичного вгадування.
> *Керування рантаймом / Інженерний інваріант:* Заборона неконтрольованих компромісів гарантує бездоганне дотримання нормативного статусу $ZHR = 1.00$.

## 6. Розподілений тріаж дефіцитів знань: кластеризація SimHash, захист від виродження та автономний WAL-буфер

У розподіленій архітектурі доказових експертних систем, де кожен вузол керується безкомпромісним принципом блокування за неповноти знань (Fail-Closed, $\mathrm{ZHR} = 1{,}00$), будь-який відсутній факт, нерозв'язана нормативна амбівалентність або конфлікт правил призводить до автоматичного формування тікета дефіциту знань (*Knowledge Gap Ticket*). У масштабних промислових розгортаннях (сотні бортових контролерів або тисячі агентів неперервного аудиту CI/CD) виникає системна загроза шторму дефіцитних тікетів (*Gap-Ticket Storm*): наївна лінійна агрегація запитів під глобальними блокуваннями призводить до вичерпання пулу потоків брокера повідомлень, переповнення черг оперативної пам'яті та відмови в обслуговуванні (*Denial of Memory*). Для подолання цієї кризи розподілена система знань спирається на трирівневу підсистему семантичного тріажу.

### 6.1. Математична модель 64-бітної кластеризації SimHash та BK-дерева

Для ліквідації надлишкового дублювання та об'єднання однотипних дефіцитів у єдині інженерні задачі кожен вхідний тікет дефіциту токенізується та згортається у 64-бітний локально-чутливий відбиток (*Locality-Sensitive Hash, LSH*) за алгоритмом SimHash [[8]](#src-8). На відміну від криптографічних хеш-функцій (SHA-256), де зміна одного біта повністю змінює результат (лавинний ефект), SimHash зберігає топологічну близькість вихідних векторів у просторі Геммінга: подібні формулювання дефіциту отримують близькі двійкові вектори.

Кожен $i$-й біт 64-бітного відбитка $h(\mathbf{t}) \in \{0, 1\}^{64}$ тікета $\mathbf{t}$ обчислюється як зважена сума проекцій ознак:

```math
h_i(\mathbf{t}) = \frac{1 + \mathrm{sign}\left(\sum_{w \in \mathbf{t}} \mathrm{weight}(w) \cdot \bigl(2 \cdot b_i(w) - 1\bigr)\right)}{2}, \quad i \in [0, 63]
```

де:
- $\mathbf{t} = \{w_1, w_2, \dots, w_k\}$ — множина токенів (предикатів, ідентифікаторів стандартів, семантичних лексем контексту дефіциту);
- $\mathrm{weight}(w)$ — ваговий коефіцієнт токена (наприклад, оцінка TF-IDF або інформаційна вага онтологічного концепту, $\mathrm{weight}(w) > 0$);
- $b_i(w) \in \{0, 1\}$ — $i$-й біт 64-бітного базового гешу токена $w$ (отриманий швидкою некриптографічною функцією xxHash64);
- $\mathrm{sign}(x)$ — функція знака ($+1$ при $x \ge 0$ та $-1$ при $x < 0$).

Два дефіцитні тікети $\mathbf{t}_1$ та $\mathbf{t}_2$ вважаються належними до одного структурного кластера дефіциту, якщо їхня бітова відстань Геммінга не перевищує поріг кластеризації:

```math
D_{\mathrm{Hamming}}\bigl(h(\mathbf{t}_1), h(\mathbf{t}_2)\bigr) = \sum_{i=0}^{63} \Bigl(h_i(\mathbf{t}_1) \oplus h_i(\mathbf{t}_2)\Bigr) \le \tau_{\mathrm{gap\_cluster}} = 3
```

де $\oplus$ — операція побітового виключного АБО (XOR), а поріг $\tau_{\mathrm{gap\_cluster}} = 3$ відповідає близькості змісту понад $95\%$.

Для уникнення лінійного перебору існуючих кластерів ($O(N)$), що викликає зупинку обробки під час шторму, збережені відбитки кластерів організуються у метричне дерево Буркхарда-Келлера (*BK-Tree*) [[9]](#src-9). Оскільки відстань Геммінга задовольняє аксіоми метрики (зокрема нерівність трикутника), пошук найближчого кластера виконується за логарифмічний час $O(\log N)$, скорочуючи обсяг обчислень на три порядки.

#### 6.1.1. Замкнений цикл інженерного розрахунку SimHash-кластеризації

1. **Керування рантаймом і потоком обчислень (Control Flow & Runtime Decisions):**
   - Коли агент виявляє відсутність правила, він генерує тікет дефіциту й передає його в локальний модуль тріажу. Якщо $D_{\mathrm{Hamming}}(h(\mathbf{t}), h_{\mathrm{existing}}) \le 3$, новий тікет не публікується в центральну шину подій NATS, а локально агрегується як лічильник повторень інциденту (`IncClusterHit(ClusterID)`);
   - Якщо відстань Геммінга до всіх відомих вершин BK-дерева $D_{\mathrm{Hamming}} > 3$, система реєструє новий унікальний кластер дефіциту знань, додає його у BK-дерево та публікує подію `vida.gap.discovered` у шину NATS для подальшого розслідування інженерами знань.
2. **Апаратний сайзинг та інфраструктурні обмеження (Hardware Dimensioning):**
   - Кожна вершина BK-дерева займає $64\,\text{байти}$ в оперативній пам'яті (64-бітний ключ, лічильник, покажчики на дочірні гілки від $0$ до $64$). Для пулу з $100\,000$ унікальних кластерів дефіцитів уся структура BK-дерева потребує лише $6{,}4\,\text{МБ}$ RAM, що дозволяє утримувати її навіть у L3-кеші процесора, уникаючи затримок звернення до зовнішньої пам'яті DRAM.
3. **Практичний числовий приклад (Worked Numerical Example):**
   - Під час нічного циклу тестування системи автономного маневрування $1\,000$ віртуальних агентів згенерували $50\,000$ дефіцитних тікетів через відсутність специфікації на гальмування при кутовому занесенні на льоду.
   - Завдяки розрахунку $D_{\mathrm{Hamming}} \le 3$ у BK-дереві система згорнула $50\,000$ однотипних запитів у рівно $2$ кореневі кластери дефіцитів (коефіцієнт дедуплікації $99{,}996\%$). Навантаження на комунікаційну шину знизилося з $50\,000$ до $2$ повідомлень, запобігши колапсу черги завдань.

### 6.2. Захист від виродження простору ознак (SimHash Degeneracy Guard) та сувора валідація контрактів

У реальній розподіленій експлуатації асинхронні брокери (NATS JetStream, Apache Kafka) стикаються з критичною прихованою відмовою: **тихим виродженням метричного простору хешування** (*Contract Drift Collapse*) [[7]](#src-7). Якщо агент-відправник через зміну версії серіалізатора передає тікет із розбіжністю назв полів контракту (наприклад, `ticket_id` замість очікуваного приймачем `TicketID`, або `context` замість `Query`), гнучкий десеріалізатор JSON мовчки залишає поля порожніми рядками (`""`).

Векторизатор тексту отримує порожній вхід. Алгоритм SimHash над порожньою множиною токенів детерміновано повертає нульовий константний вектор:

```math
\mathrm{SimHash}(\emptyset) = \mathrm{0x0000000000000000}
```

У результаті всі різнорідні дефіцити знань із різних підсистем (від збою калібрування сенсора струму до правової колізії в директивах) отримують однаковий відбиток `0x0000000000000000`. Оскільки відстань Геммінга між ними $D_{\mathrm{Hamming}} = 0 \le 3$, система зливає абсолютно непов'язані відмови в один гігантський вироджений псевдокластер, паралізуючи роботу інженерів знань.

Для усунення цієї вразливості запроваджується комбінований архітектурний захист (*Degeneracy Guard*):

1. **Інваріант мінімальної лексичної складності (Distinct Tokens Invariant):**
   Перед обчисленням згортки SimHash перевіряється умова достатності ентропії ознакового простору:
```math
\mathrm{DistinctTokens}(T) \ge K_{\mathrm{min}} \quad (K_{\mathrm{min}} = 2)
```
   Якщо кількість унікальних семантичних токенів $\mathrm{DistinctTokens}(T) < 2$ або довжина вхідного тексту дорівнює нулю, виклик негайно завершується помилкою `ErrDegenerateFeatureSpace`. Значення `0x0000000000000000` та `0xFFFFFFFFFFFFFFFF` резервуються як маркери аномалії та апаратно блокуються від додавання до BK-дерева;

2. **Суворе двостороннє узгодження контрактів (Strict Unmarshal):**
   Десеріалізатори системних повідомлень у розподіленій шині налаштовуються на абсолютну заборону невідомих або пропущених обов'язкових полів:
   ```go
   decoder := json.NewDecoder(streamReader)
   decoder.DisallowUnknownFields()
   ```
   Повідомлення з відсутніми або спотвореними полями миттєво відхиляються й перенаправляються до карантинної черги недоставлених повідомлень (*Dead-Letter Queue, DLQ*);

3. **Стандартизація багатотокенових ієрархічних масок шини:**
   У брокері NATS маска із зірочкою (`vida.tasks.*`) фільтрує **строго один токен** ієрархії. Для гарантування проходження повідомлень від складнопідрядних вузлів усі системні підписки стандартизуються на оператор повного піддерева `>`:
```math
\mathrm{SubSubject} = \text{"vida.tasks.>"} \quad (\text{замість помилкового } \text{"vida.tasks.*"})
```

> [!NOTE]
> **Три ешелони захисту від виродження простору ознак SimHash за моделлю автора**
> 1. *Інваріант мінімальної лексичної складності*: детермінована вимога $\mathrm{DistinctTokens}(T) \ge 2$ із блокуванням вироджених векторів `0x0000000000000000` та `0xFFFFFFFFFFFFFFFF`.
> 2. *Суворе двостороннє узгодження контрактів*: конфігурація десеріалізатора `DisallowUnknownFields` для негайного відкидання розбіжностей у назвах полів схеми до карантинної черги DLQ.
> 3. *Стандартизація багатотокенових масок підписки*: обов'язкове застосування оператора повного піддерева `>` замість одинарного токена `*` для запобігання втраті повідомлень від складнопідрядних вузлів.
> *Керування рантаймом / Інженерний інваріант:* Захист від виродження відбитків запобігає колапсу семантичного індексу при збоях формату серіалізації в розподіленій шині.

#### 6.2.1. Замкнений цикл інженерного розрахунку захисту від виродження

1. **Керування рантаймом і потоком обчислень (Control Flow & Runtime Decisions):**
   - Якщо вхідне повідомлення не містить обов'язкових полів схеми або містить $\mathrm{DistinctTokens} < 2$, модуль тріажу генерує подію `ALERT_CONTRACT_DEGENERACY` та скидає тікет у DLQ. Потік виконання блокує потрапляння спотворених даних у BK-дерево;
   - Якщо контракт валідний і $\mathrm{DistinctTokens} \ge 2$, система обчислює повноцінний 64-бітний відбиток SimHash і направляє його в алгоритм кластеризації.
2. **Апаратний сайзинг та інфраструктурні обмеження (Hardware Dimensioning):**
   - Карантинний буфер DLQ виділяється на окремому SSD-накопичувачі з обмеженням розміру $10\,\text{ГБ}$ і сповіщенням чергового інженера при заповненні понад $50\%$;
   - Перевірка `DisallowUnknownFields` додає не більше $1{,}2\,\mu\text{s}$ на повідомлення, зберігаючи пропускну здатність вузла понад $80\,000$ повідомлень/сек на одному ядрі CPU.
3. **Практичний числовий приклад (Worked Numerical Example):**
   - Після оновлення прошивки сенсорного модуля польотного контролера поле контексту було випадково перейменовано з `context_spec` на `ctx_spec`.
   - Захисний шлюз `decoder.DisallowUnknownFields()` зафіксував невпізнане поле `ctx_spec` за $0{,}8\,\mu\text{s}$ і перенаправив запит у DLQ із генерацією аварійного журналу. Запобігли аварійному виродженню $15\,000$ тікетів у нульовий відбиток `0x0`, зберегли чистоту семантичного індексу дефіцитів у корпоративному репозиторії.

### 6.3. Автономний локальний WAL-буфер та протокол виведення з експлуатації (Lame Duck Mode)

У промислових розподілених системах зв'язок між периферійними вузлами (робочими станціями, бортовими комп'ютерами) та центральним брокером знань не є абсолютно надійним: електромагнітні завади, перепідключення мережі або технічне обслуговування серверів спричиняють тимчасову ізоляцію вузлів (*Network Partitions*). Якщо в цей момент граничний агент виявляє дефіцит знань, відсутність буферизації призводить або до аварійного зависання робочого процесу, або до тихої втрати інформації про прогалини в безпеці.

Для забезпечення безперервності аудиту граничний вузол оснащується автономним локальним журналом випереджального запису (*Write-Ahead Log, WAL*):
1. **Кільцевий шифрований WAL-буфер:** Тікети дефіциту негайно фіксуються в локальному журналі на диску, захищеному асиметричним ключем сесії. Журнал має фіксовану максимальну дискову квоту (наприклад, $500\,\text{МБ}$). За досягнення квоти активується кільцева ротація, де старі дубльовані записи витісняються, але унікальні критичні вердикти зберігаються;
2. **Відновлення зв'язку та FIFO-дренаж:** Щойно мережевий стек виявляє відновлення з'єднання з брокером знань, фоновий агент виконує послідовне вичитування локального WAL і пакетну публікацію накопичених тікетів за принципом FIFO без блокування основного циклу перевірки інваріантів;
3. **Режим контрольованого виведення з експлуатації (Lame Duck Mode):**
   Під час планового оновлення або вимкнення вузла кластера активується двоетапний протокол безпечної зупинки:
   - Вузол негайно знімає себе з реєстрації в динамічному реєстрі брокера (`UNREGISTER_PENDING`), припиняючи прийом нових запитів від тонких клієнтів;
   - Усі активні сесії логічного виведення доводяться до завершення, а проміжні черги дефіцитів повністю синхронізуються на диск у WAL і передаються на сусідній резервний вузол;
   - Лише після підтвердження скидання буферів процес коректно завершує роботу (`SHUTDOWN_CLEAN`).

## 7. Незмінний журнал рішень (Immutable Decision Ledger) на Merkle-деревах

У критичних галузях застосування експертних систем — функціональній безпеці безпілотного транспорту (ISO 26262 ASIL D), сертифікації бортового програмного забезпечення (DO-178C DAL A) та медичній діагностиці — ключовою юридичною та технічною вимогою є **неспростовність рішень (Non-Repudiation)**. Звичайні реляційні бази даних (PostgreSQL, SQLite) або текстові логи операційної системи непридатні для цієї ролі: будь-який привілейований адміністратор сервера може заднім числом змінити запис у базі, підробити вердикт або приховати факт порушення норм безпеки під час ретроспективного розслідування аварії. З іншого боку, наївна спроба записувати весь гігабайтний обсяг доказів у публічний блокчейн спричиняє неприпустимі затримки (секунди замість мікросекунд), колосальні фінансові витрати та розкриття конфіденційної інформації підприємства.

Доказова архітектура розв'язує цю дилему через побудову **незмінного журналу рішень (Immutable Decision Ledger)** на основі локальних Merkle-дерев та розподіленої фіксації контрольних коренів.

### 7.1. Структура криптографічного пакета рішення (Decision Evidence Bundle)

Кожен факт логічного виведення перед відправленням замовнику упаковується в криптографічно цілісний двійковий пакет доказів (*Decision Evidence Bundle*), що містить чотири взаємопов'язані хеш-дескриптори:

```math
\mathrm{EvidenceBundle} = \mathrm{Sign}_{\mathrm{Ed25519}}\Bigl(H(I) \mathbin{\Vert} H(V_{\mathrm{KB}}) \mathbin{\Vert} H(G_{\mathrm{proof}}) \mathbin{\Vert} H(\mathrm{Verdict})\Bigr)
```

де:
- $H(I)$ — криптографічний хеш SHA-256 вхідного вектора спостережень, телеметрії або тексту нормативного запиту $I$;
- $H(V_{\mathrm{KB}})$ — хеш поточної версії бази знань, нормативних онтологій та дефітерів (гарантує побайтову фіксацію стану правил на момент виведення);
- $H(G_{\mathrm{proof}})$ — хеш структури графа аргументації ASPIC+ або GSN-дерева доведення цілі (включаючи всі активовані предикати та анульовані гілки);
- $H(\mathrm{Verdict})$ — хеш результуючого вердикту (`ACCEPT`, `REFUSAL`, `QUALIFIED`);
- $\mathbin{\Vert}$ — операція двійкової конкатенації;
- $\mathrm{Sign}_{\mathrm{Ed25519}}$ — цифровий підпис на асиметричному ключі обчислювального вузла за схемою Ed25519 (RFC 8032).

Ця структура забезпечує математичний доказ: ані вхідні параметри, ані застосовані версії правил, ані сам вердикт не можуть бути підроблені без порушення валідності цифрового підпису.

### 7.2. Ієрархічне Merkle-дерево та WORM-анкоринг

Для забезпечення високої пропускної здатності пакети рішень не записуються поодинці в повільні зовнішні реєстри. Замість цього вони об'єднуються в локальні бінарні дерева Merkle [[10]](#src-10) в оперативній пам'яті вузла в режимі реального часу:

```math
\mathrm{Root}_{\mathrm{Merkle}} = \mathrm{Hash}\bigl(\mathrm{Node}_{\mathrm{left}} \mathbin{\Vert} \mathrm{Node}_{\mathrm{right}}\bigr)
```

Кожні $T_{\mathrm{epoch}}$ секунд (або після накопичення $K_{\mathrm{batch}}$ рішень, наприклад $1\,000$ пакетів) обчислений корінь дерева $\mathrm{Root}_{\mathrm{Merkle}}$ фіксується у захищеному сховищі типу WORM (*Write Once Read Many*, оптичний носій або хмарний накопичувач із блокуванням видалення S3 Object Lock) або реєструється в консорціумному розподіленому реєстрі.

Для доведення автентичності будь-якого окремого історичного рішення аудитору достатньо надати компактний аудиторський шлях (*Merkle Audit Trail*) завдовжки $\lceil \log_2 N \rceil$ хешів. Аудитор перевіряє ланцюжок від листа до публічно зафіксованого кореня за кілька мікросекунд без необхідності читання всього масиву рішень.

#### 7.2.1. Замкнений цикл інженерного розрахунку та верифікації незмінного журналу

1. **Керування рантаймом і потоком обчислень (Control Flow & Runtime Decisions):**
   - Після формування вердикту сервіс знань створює `EvidenceBundle` і додає його як лист у поточне дерево епохи;
   - Якщо під час валідації історичного запиту розрахований хеш $\mathrm{Root}_{\mathrm{computed}} \ne \mathrm{Root}_{\mathrm{WORM}}$, система генерує тривогу першого пріоритету `AUDIT_CORRUPTION_DETECTED` та блокує сертифікаційний статус вузла до з'ясування причин підробки даних;
   - Якщо корені збігаються, аудиторський інспектор видає сертифікат юридичної та технічної неспростовності вердикту (`NON_REPUDIATION_VERIFIED`).
2. **Апаратний сайзинг та інфраструктурні обмеження (Hardware Dimensioning):**
   - Обчислення одного вузла дерева на базі SHA-256 або BLAKE3 займає менше $0{,}15\,\mu\text{s}$ на сучасному процесорі з підтримкою апаратних інструкцій SHA-NI;
   - Для кластера з інтенсивністю $10\,000$ рішень/сек епоха $T_{\mathrm{epoch}} = 10\,\text{с}$ генерує Merkle-дерево з $100\,000$ листів. Розмір аудиторського шляху становить лише $\lceil \log_2 100\,000 \rceil = 17$ хешів ($17 \times 32 = 544\,\text{байти}$), що мінімізує трафік сертифікаційного аудиту.
3. **Практичний числовий приклад (Worked Numerical Example):**
   - Під час аудиту автомобільної системи ASIL D на відповідність ISO 26262 виникла підозра щодо вердикту екстреного гальмування, ухваленого 6 місяців тому.
   - Експертна система надала криптографічний пакет рішення із 17 хешами Merkle-шляху.
   - Незалежний верифікатор відновив корінь дерева за 17 операцій хешування ($2{,}5\,\mu\text{s}$) і звірив його з публічним коренем, зафіксованим у WORM-реєстрі на дату події. Повний збіг побайтово довів, що ані сенсорні дані занесення автомобіля, ані версія правил гальмування не змінювалися заднім числом, захистивши виробника від судових позовів.

## 9. Холодна готовність динамічного реєстру знань (Tabula Rasa), чистота діагностичних доказів та субмілісекундний фонотактично-ентропійний санітайзер входу

Класичні експертні системи та корпоративні пошукові рушії зазвичай проєктуються в парадигмі статичного зв'язування (*Static Knowledge Binding*): інтерфейс користувача або клієнтський демон вимагає явної конфігурації шляхів до файлів баз знань під час запуску (`--kb /path/to/domain.pack`) і аварійно завершується, якщо сховище порожнє. У розподіленій епістемічній архітектурі (Epistemic SOA) такий підхід є неприпустимим: тонка операторська консоль та інференс-вузли повинні стартувати з нульовою конфігурацією (*Zero-Configuration Startup*) і зберігати повну працездатність навіть у стані «чистого аркуша» (**Tabula Rasa**, коли кількість змонтованих пакетів $N_{\mathrm{packs}} = 0$).

### 9.1. Реактивний життєвий цикл динамічного реєстру знань та біфуркація телеметрії

Розподілений реєстр знань функціонує як реактивний автомат станів над спільною пам'яттю `mmap(MAP_SHARED)` та шиною подій публікації/підписки (*Pub/Sub Event Bus*), керований фоновим хост-демоном без жодного втручання клієнтського інтерфейсу:

```mermaid
sequenceDiagram
    participant UI as Тонка консоль оператора (Thin Console)
    participant San as Фонотактично-ентропійний санітайзер
    participant Reg as Динамічний реєстр знань (RCU Registry)
    participant Host as Фоновий демон сховища (Shared-Memory Host)

    Note over UI,Host: Фаза 1: Холодний старт над порожнім сховищем (Tabula Rasa, N_packs = 0)
    UI->>Reg: Запит Q1 ("Який максимальний час відгуку гальм?")
    Reg-->>UI: REFUSAL (NO_KNOWLEDGE_PACKS_MOUNTED)<br/>EvidenceList = ∅, Diagnostics = {MountedPacks: 0}

    Note over UI,Host: Фаза 2: Асинхронна компіляція та гаряче монтування (Hot-Mount)
    Host->>Reg: Подія bus.events.pack.mounted (Domain: Automotive, SHA-256)
    Reg->>Reg: Атомарне оновлення RCU-вказівника активної епохи

    Note over UI,Host: Фаза 3: Захист входу та доказове виведення (N_packs > 0)
    UI->>San: Запит Q2 ("asdfghjkl qwerty 123")
    San-->>UI: REFUSAL (UNINTELLIGIBLE_INPUT, t < 50 мкс)
    UI->>San: Запит Q3 ("Який максимальний час відгуку гальм?")
    San->>Reg: Валідний запит (ρ_V ∈ [0.15, 0.85], L_C ≤ 5)
    Reg-->>UI: ACCEPT + Побайтова цитата з пакета Automotive [byte_start..byte_end]
```

Для запобігання підміні понять між реальними доказами першоджерела та внутрішньою системною діагностикою вводиться **Закон нульових синтетичних доказів** (*Zero Synthetic Evidence Law*):

$$\forall r \in \mathrm{Response.\mathbf{EvidenceList}}: \quad \mathcal{G}(r) \ne \varnothing \;\land\; \mathrm{SHA256}\!\left(\mathrm{Source}[b_{\mathrm{start}}:b_{\mathrm{end}}]\right) = r.\mathrm{QuoteHash}$$

Якщо система повертає відмову (наприклад, через відсутність змонтованих баз знань у стані *Tabula Rasa* або відсутність факту у змонтованих пакетах), масив доказів `EvidenceList` зобов'язаний бути **математично порожнім** ($\mathbf{EvidenceList} = \varnothing$). Категорично забороняється записувати системні повідомлення чи діагностичні рядки компілятора у поле цитати `EvidenceQuote` з фіктивними байтовими координатами `[0:0]`, оскільки це фальсифікує криптографічну кастодію. Вся операційна телеметрія передається виключно в окремому діагностичному полі `Diagnostics` і відображається в операторському інтерфейсі за принципом **когнітивно-криміналістичної біфуркації** (*Cognitive-Forensic UI Bifurcation*):
- **Когнітивний потік чату** містить лаконічну природномовну відповідь або чітке пояснення причини відмови для оператора;
- **Інспекційна панель аудитора** відображає криптографічні хеші змонтованих пакетів, байтові зміщення цитат та телеметрію співпроцесорів без засмічення діалогового вікна.

### 9.2. Математична модель субмілісекундного фонотактично-ентропійного санітайзера входу

Перш ніж запит оператора потрапить до семантичного брокера, локальної мовної моделі (SLM) чи апаратного ядра виведення, він проходить через детермінований **фонотактично-ентропійний санітайзер входу** (*Phonotactic-Entropic Input Sanitizer*). Його мета — за час $t < 50\,\mu\text{s}$ відсіяти випадковий набір символів («клавіатурний шум» на кшталт `asdfghjkl`, пошкоджені кодування або спроби переповнення буфера токенізатора), не витрачаючи ресурси GPU/NPU та не генеруючи хибних тікетів дефіциту знань.

Спираючись на теорію ентропії друкованої мови Клода Шеннона [[11]](#src-11) та фонотактичні обмеження сполучуваності фонем у природних мовах Ноама Чомскі й Морріса Галле [[12]](#src-12), кожен алфавітний токен $w$ запиту $Q = (w_1, \dots, w_m)$ (довжиною $|w| \ge 4$ символів, що не входить до білого списку відомих інженерних абревіатур $\mathcal{A}_{\mathrm{tech}}$ на кшталт `HTML`, `HTTP`, `DBMS`, `FPGA`, `RTOS`, `UTF8`) перевіряється за трьома інваріантами:

1. **Інваріант вокалічної щільності ($\rho_V$):** відношення кількості голосних літер $V(w)$ (для латиниці `{a, e, i, o, u, y}` та кирилиці `{а, е, є, и, і, ї, о, у, ю, я}`) до загальної довжини слова $|w|$ повинно лежати у фізіологічно допустимому коридорі природної мови:

$$\rho_V(w) = \frac{V(w)}{|w|} \in [0{,}15; \; 0{,}85]$$

2. **Інваріант максимального консонантного кластера ($L_C$):** довжина найдовшої неперервної послідовності приголосних літер $L_C(w)$ у слові не може перевищувати фонотактичного порогу природних індоєвропейських мов [[12]](#src-12):

$$L_C(w) = \max_{[i, j] \subseteq [1, |w|]} \left\{ j - i + 1 \;\middle|\; \forall k \in [i, j]: w[k] \in \mathrm{Consonants} \right\} \le 5$$

3. **Інваріант ентропії Шеннона та біграмної правдоподібності ($H_1$):** для довгих рядків ($|Q| \ge 12$) посимвольна ентропія Шеннона [[11]](#src-11) не повинна вказувати ані на вироджений повтор одного символу (`aaaaaaaaaa`, $H_1 \to 0$), ані на рівномірний псевдовипадковий шум високої ентропії з нульовою часткою валідних мовних біграм:

$$H_1(Q) = -\sum_{c \in \Sigma} p(c) \log_2 p(c) \in [1{,}5; \; 4{,}7]\,\text{біт/символ}$$

Якщо частка фонотактично невалідних токенів у запиті перевищує поріг $\theta_{\mathrm{gibberish}} = 0{,}50$, санітайзер миттєво блокує запит зі статусом `REFUSAL (UNINTELLIGIBLE_INPUT)` за мікросекунди, повністю захищаючи обчислювальний кластер і черги подій від сміттєвого трафіку.

> [!NOTE]
> **Три закони реактивної готовності реєстру знань та гігієни вхідного потоку (авторська модель Миколи Федчика)**
> 1. **Закон холодної готовності Tabula Rasa (Zero-Config Tabula Rasa Readiness):** тонка операторська консоль та вузли виведення стартують без жодної прив'язки до шляхів баз знань і при порожньому реєстрі ($N_{\mathrm{packs}} = 0$) повертають детерміновану типізовану відмову `NO_KNOWLEDGE_PACKS_MOUNTED`, миттєво переходячи в робочий режим при отриманні події гарячого монтування від хост-демона.
> 2. **Закон нульових синтетичних доказів (Zero Synthetic Evidence Law):** жодне діагностичне повідомлення, підказка чи опис помилки рантайму не може бути поміщене в масив доказів `EvidenceList` під виглядом цитати з нульовими координатами `[0:0]`; за будь-якої відмови масив доказів залишається строго порожнім ($\mathbf{EvidenceList} = \varnothing$), а телеметрія ізолюється в інспекційній панелі аудитора.
> 3. **Закон субмілісекундної фонотактично-ентропійної фільтрації (Phonotactic-Entropic Pre-Brokering Guard):** перевірка вокалічної щільності $\rho_V \in [0{,}15; 0{,}85]$, довжини консонантних кластерів $L_C \le 5$ та символьної ентропії Шеннона $H_1$ відсікає нечленороздільний ввід на вхідному периметрі за $< 50\,\mu\text{s}$ до виклику мовних моделей чи брокера.
> *Керування рантаймом / Інженерний інваріант:* оновлення списку активних пакетів у динамічному реєстрі при подіях `MOUNT / UNMOUNT / SWAP` здійснюється за безблокувальним протоколом Read-Copy-Update (RCU [[13]](#src-13)), що гарантує нульовий час простою читачів під час гарячого поповнення сховища знань.

### 9.3. Федеративна Zero-Copy Арена міжпакетного виведення та три покоління апаратних прискорювачів синтезу

Коли у динамічному реєстрі одночасно змонтовано $m \ge 2$ пакетів знань $\mathcal{P} = \{P_1, P_2, \dots, P_m\}$, послідовне опитування кожного пакета в ізольованому циклі (`Single-Pack Evaluation Silo`) унеможливлює побудову наскрізних логічних ланцюгів, де передумова $A \to B$ міститься в пакеті $P_1$, проміжний перехід $B \to C$ — у пакеті $P_2$, а нормативне обмеження безпеки — у пакеті $P_3$. Щоб забезпечити **доказовий міжпакетний синтез** без порушення інваріанта нульового копіювання (`Zero-Copy Invariant`), у розподіленому рантаймі запроваджується **Федеративна Арена Виведення** (`pkg/reasoning/arena`).

Федеративна Арена відображає бінарні секції всіх активних контейнерів `.kp` у спільний віртуальний адресний простір через `mmap(MAP_SHARED)` та будує над ними єдине поле канонічної еквівалентності концептів $\Phi: \bigcup_{i=1}^m A_i \to \mathcal{G}_{\text{canon}}$:

$$\mathcal{S}^*(Q) = \left\{ \pi = \left(r_{i_1}^{(1)}, r_{i_2}^{(2)}, \dots, r_{i_k}^{(k)}\right) \;\middle|\; \begin{aligned}
& \forall j \in [1..k]: r_{i_j}^{(j)} \in R_{i_j}, \; \mathrm{Custody}_{i_j}\!\left(r_{i_j}^{(j)}\right) = \mathrm{VALID}, \\
& \Phi\!\left(\mathrm{Consequent}(r_{i_j}^{(j)})\right) \equiv \Phi\!\left(\mathrm{Antecedent}(r_{i_{j+1}}^{(j+1)})\right), \\
& \Omega^*(\pi) = \bigcap_{j=1}^k \left[\underline{v}_j, \overline{v}_j\right] \neq \varnothing, \; \neg \exists u \in \bigcup_{l=1}^m R_l : \mathrm{Defeats}(u, \pi)
\end{aligned} \right\}$$

Якщо знайдений ланцюг $\pi \in \mathcal{S}^*(Q)$ охоплює щонайменше два різні першоджерела ($|\{i_1, \dots, i_k\}| \ge 2$), жодне з яких самостійно не містить повного висновку, ядро генерує вердикт **`SYNTHESIZED`** із векторним побайтовим паспортом $\vec{E}(\pi) = \langle (P_{i_1}, [\text{start}_1..\text{end}_1], H_1), \dots, (P_{i_k}, [\text{start}_k..\text{end}_k], H_k) \rangle$ та обчисленим вікном параметричної збіжності $\Omega^*(\pi)$.

Оскільки зі зростанням кількості змонтованих пакетів $m$ та глибини композиції $k$ обчислювальне навантаження на перетин обмежень зростає нелінійно, автором сформульовано **прогноз трьох поколінь апаратних засобів федеративного синтезу**:

| Покоління апаратури | Базова обчислювальна платформа | Ємність активного поля правил | Пропускна здатність селектора | Цільовий клас задач синтезу |
|---|---|---|---|---|
| **Покоління I (Лабораторний гетерогенний стенд)** | NVIDIA Jetson AGX Orin 64 GB UMA (275 TOPS) + кластер **2× PYNQ-Z1 FPGA** (Zynq-7020, BRAM 630 KB) | До $10^4$ активних правил у вікнах BRAM | $\sim 10^6$ перевірок/с ($< 1\,\text{мкс}$ на ланцюг) | Міжпакетний синтез глибини $d \le 5$ над $5\text{–}15$ доменами `.kp` |
| **Покоління II (Масштабований HBM-EPU вузол)** | Серверний процесор 128+ GB UMA + прискорювач **FPGA з пам'яттю HBM2e / UltraRAM** (Alveo / Versal HBM, 16–32 GB на кристалі, 460 GB/s) | До $10^7$ правил без зовнішніх підкачок DMA | $\sim 10^8$ графових транзицій/с | Повномасштабний промисловий аудит та синтез над сотнями стандартів у реальному часі |
| **Покоління III (Когерентна фабрика CXL 3.0 + Ізінговий контур)** | Когерентний пул пам'яті **CXL 3.0** (терабайти спільних `.kp`) + **цифрові ізінгові відпалювачі (Digital Annealers / Ising Machines на FPGA)** | Понад $10^9$ правил у єдиному адресному просторі | Миттєвий пошук глобального мінімуму енергії обмежень | Розв'язання надскладних задач комбінаторної оптимізації Max-SAT у багатовимірних просторах вимог |

> [!NOTE]
> **Три покоління апаратної еволюції федеративної арени синтезу за прогнозом М. М. Федчика**
> 1. **Покоління I — Гетерогенний тандем UMA + BRAM FPGA (Jetson AGX Orin + 2× PYNQ-Z1):** автором реалізовано архітектуру початкового рівня, де уніфікована пам'ять 64 GB утримує змонтовані пакети `.kp` і локальні моделі-мутатори, а спарені плати FPGA виконують субмікросекундне відсікання конфліктів ASPIC+ над активними вікнами правил.
> 2. **Покоління II — Процесори епістемічного синтезу з високошвидкісною пам'яттю на кристалі (HBM2e-EPU):** у авторському прогнозі обґрунтовано перехід до FPGA-прискорювачів із інтегрованими стеками HBM2e (пропускна здатність $> 460\,\text{ГБ/с}$), що повністю усуває вузьке місце шинної підкачування при зшиванні десятків тисяч міждоменних правил.
> 3. **Покоління III — Когерентні фабрики CXL 3.0 та спеціалізовані ізінгові розв'язувачі (Digital Annealers):** автором сформульовано перспективну концепцію поєднання терабайтних пулів Zero-Copy пам'яті CXL 3.0 із цифровими ізінговими машинами на базі FPGA, які перетворюють задачу багатоджерельного синтезу Max-SAT на фізичний процес швидкої релаксації спінової решітки до стану з нульовою кількістю конфліктів.
> *Керування рантаймом / Інженерний інваріант:* Федеративна Арена (`pkg/reasoning/arena`) формує вердикт `SYNTHESIZED` виключно за умови, що кожен елемент векторного доказу $\vec{E}(\pi)$ пройшов криптографічну перевірку кастодії у своєму вихідному відображеному сегменті `mmap` без проміжного копіювання рядків у купу (heap).

## 10. Діалог Pro et Contra

До віртуальної інтелектуальної дискусії запрошено визнаних архітекторів розподілених систем, чиї фундаментальні теореми та праці визначають сучасний ландшафт глобальних обчислень: Мартіна Клеппмана (Martin Kleppmann, наукового співробітника University of Cambridge, автора класичної монографії *Designing Data-Intensive Applications* та провідного дослідника конфліктно-вільних реплікованих типів даних CRDT і локально-орієнтованого ПЗ Local-First Software) та Еріка Брюера (Eric Brewer, почесного професора University of California, Berkeley, віце-президента Google з інфраструктури, автора фундаментальної теореми CAP). Їхні теоретичні відкриття щодо фізичних меж розподіленого консенсусу, компромісів між узгодженістю та доступністю в умовах мережевих розривів і структури реплікації стану створюють неперевершений фундамент для всебічної перевірки запропонованої автором сервіс-орієнтованої епістемічної архітектури (Epistemic SOA) та незмінного журналу рішень на Merkle-деревах.

*Дисклеймер:* Ця дискусія є евристичним віртуальним моделюванням у науково-педагогічному контексті монографії. Позиції та аргументи опонентів синтезовані на основі їхніх публічних праць, наукових публікацій та монографій, не є прямими реальними цитатами й слугують для критичної раціоналізації (фальсифікації за Поппером) інженерних рішень автора.

**Теза глави.** Масштабування промислової доказової експертної системи за межі лабораторії вимагає переходу до триланкової сервіс-орієнтованої архітектури (Epistemic SOA) з тонким клієнтом ($S_{\mathrm{client}} = 0$), холодною готовністю динамічного реєстру знань (*Tabula Rasa*), фонотактично-ентропійним санітайзером входу, семантичним брокером та доменними кластерами знань. Неминучі компроміси розподілених обчислень вирішуються математично: умова приховування затримок ($T_{\mathrm{refill}} \ll T_{\mathrm{execute}}$) усуває простій конвеєра BRAM/DMA; дефезитивна агрегація ASPIC+/Dung децентралізує аргументацію; 64-бітний SimHash та BK-дерева виконують розподілений тріаж дефіцитів знань; теорема CAP підпорядковується принципу Safety-First Partitioning (строгий CP-режим для ASIL D та локальні сертифікати епох для периферії); а незмінний журнал рішень (Immutable Decision Ledger) на деревах Меркла з WORM-анкорингом забезпечує довічну юридичну неспростовність аудиту без ретроактивних спотворень.

**Діалог з Мартіном Клеппманом: продуктивність розподілених незмінних журналів рішень на деревах Меркла**

- **Мартін Клеппман:** Пане Миколо, досліджуючи розподілені сховища даних та локально-орієнтовані системи (Local-First Software), ми переконалися, що спроба побудови розподіленого незмінного журналу рішень (Immutable Decision Ledger) на основі Merkle-дерев і повного криптографічного консенсусу неминуче стикається з важкими проблемами масштабування, затримок координації та складності міграції схем. Якщо кожен сервіс у вашій Epistemic SOA зобов'язаний фіксувати кожен мікровердикт, доказовий кортеж і стан розв'язання аргументаційного графа ASPIC+ у спільному криптографічному журналі, ви створюєте глобальне вузьке місце. За високого навантаження перерахунок коренів Merkle, перевірка підписів Ed25519 та синхронізація через мережу призведуть до неприйнятних для систем реального часу затримок (Latency Spikes). Як ваша архітектура уникає перетворення незмінного журналу на гальмо для всієї розподіленої системи?

- **Микола Федчик:** Пане Мартіне, ваша праця з проектування високонавантажених систем застерігає інженерів від наївного захоплення глобальними синхронними логами, і ми врахували це застереження на рівні апаратного сайзингу. В архітектурі Epistemic SOA журнал рішень не є монолітним синхронним блокчейном. Ми застосовуємо локально-автономну асинхронну буферизацію: кожен сервіс записує вердикти у локальний автономний кільцевий буфер (Ring Buffer) у захищеній пам'яті, миттєво повертаючи результат клієнту із затримкою до 200 мікросекунд. Агрегація вердиктів у Merkle-дерево виконується фоновим асинхронним пакетизатором (Epoch Batcher) з фіксованими квантами часу (наприклад, 100 мс). Крім того, для синхронізації знань між вузлами ми використовуємо саме ваш підхід — напіврешітки CRDT: злиття епістемічних дефіцитів і станів аргументації відбувається без центрального координатора за монотонними законами операційного злиття, що гарантує збіжність стану без блокування рантайму.

**Продовження діалогу з Мартіном Клеппманом: багатоджерельна аргументація ASPIC+ у розподілених кластерах**

- **Мартін Клеппман:** У розподілених системах пошук консенсусу над графовими структурами з циклами атак (Dung argumentation frameworks) неминуче призводить до комбінаторного вибуху та зациклення координації. Якщо федеративні доменні сервіси одночасно висувають взаємовиключні аргументи та контраргументи через семантичний брокер, розподілений пошук циклів і обчислення обґрунтованих розширень (grounded extensions) через мережеві RPC викличуть каскадні тайм-аути та взаємні блокування (distributed deadlocks). Як ви гарантуєте детермінований і обмежений у часі розв'язок аргументації без глобального синхронного арбітра?

- **Микола Федчик:** В Epistemic SOA аргументаційний рушій принципово уникає розподілених рекурсивних RPC-обходів графа. Ми впровадили стратифікований протокол: доменні сервіси генерують лише локально замкнені фрагменти аргументів (*Argument Chunks*), супроводжуючи їх формальними правилами, вихідними посилками та криптографічними гешами походження. Семантичний брокер виконує фінальне злиття та обчислення обґрунтованого розширення локально в оперативній пам'яті за детермінований час за допомогою інваріанта пріоритетного порядку правил (*Rule Priority Lattice*). Цикли атак розриваються детерміновано через відношення переваги аргументів (*Strict Defeat Ordering*), гарантуючи обчислення результуючого вердикту в межах жорсткого часового бюджету $T_{\mathrm{eval}} \le \tau_{\mathrm{deadline}}$ без жодних додаткових мережевих запитів.

**Діалог з Еріком Брюером: стійкість епістемічних сервіс-орієнтованих архітектур в умовах теореми CAP**

- **Ерік Брюер:** Пане Миколо, формулюючи теорему CAP, я встановив фундаментальний закон розподілених систем: під час неминучого мережевого розриву (Network Partition) система зобов'язана пожертвувати або лінійною узгодженістю (Consistency), або доступністю (Availability). У вашій Epistemic SOA ви пропонуєте розділення на тонкі клієнти, брокери та федеративні доменні сервіси. Але якщо між семантичним брокером і кластером доменних сервісів стається розрив зв'язку, як поведеться система? Якщо ви оберете доступність (AP), сервіси почнуть приймати рішення на основі застарілих або локально фрагментованих фактів, що призведе до катастрофічного порушення інваріанта $ZHR = 1.00$ і появи взаємно суперечливих юридичних вердиктів. Якщо ж ви оберете сувору узгодженість (CP), відмова мережі повністю паралізує обслуговування критичного об'єкта. Чи не ігнорує ваша епістемічна SOA непохитні закони теореми CAP?

- **Микола Федчик:** Пане Еріку, теорема CAP є фізичним законом для нашого розподіленого стека, і ми не намагаємося її «обійти» — ми робимо усвідомлений інженерний вибір у межах вимог функціональної безпеки (Safety-First Partitioning). В архітектурі доказових експертних систем за мережевого розриву система категорично відкидає компроміс на користь наївної доступності: вона є строго CP-орієнтованою для рішень, що мають критичні наслідки (ASIL C/D). Якщо зв'язок із доменним сервісом втрачено, семантичний брокер не генерує здогадок; він детерміновано активує протокол захисної відмови `DISP_REFUSE` із кодом `EP_NET_PARTITION`. Проте для некритичних запитів у системі реалізовано режим локально-герметичного виведення: тонкий клієнт або периферійний шлюз продовжує автономно функціонувати на базі локально кешованого, криптографічно підписаного бінарного пакета знань. Поки не вичерпано локальне вікно чинності сертифіката епохи (Epistemic Epoch), клієнт володіє абсолютною локальною узгодженістю, зберігаючи працездатність без ризику суперечливості.

**Продовження діалогу з Еріком Брюером: відновлення після мережевих розривів та обробка ретроактивних спростувань**

- **Ерік Брюер:** Найскладніший виклик у розподілених системах — не витримати розрив зв'язку, а коректно відновити цілісність після його усунення (*Partition Recovery*). Коли зв'язок відновлюється, периферійні вузли з локальними WAL-буферами почнуть синхронізуватися з центральним Merkle-журналом. Якщо під час розриву на різних вузлах з'явилися суперечливі знання або були прийняті автономні рішення, ретроактивне злиття здатне скасувати раніше зафіксовані факти. Якщо вердикт безпеки, на основі якого спрацював виконавчий механізм, раптом оголошується спростованим заднім числом, виникає правовий та інженерний хаос. Як Epistemic SOA уникає ретроактивної деструкції під час зцілення мережі?

- **Микола Федчик:** Відновлення після розриву мережі ніколи не переписує минулого. У нашому незмінному журналі рішень на Merkle-деревах діє принцип суворої монотонності (Append-Only): записи історичних вердиктів не підлягають модифікації. Коли ізольований вузoл відновлює зв'язок, його накопичений WAL-буфер фіксується як окрема гілка нової епохи. Будь-які суперечності вирішуються як нові дефезитивні аргументи вперед у часі (*Forward-Only Defeasibility*): вони можуть модифікувати лише майбутній стан бази знань, але не мають зворотної сили щодо рішень попередніх епох. Кожен випущений вердикт містить часову мітку RFC 3161 та підпис епохи, зберігаючи повну доказову та юридичну чинність для моменту свого прийняття. Це усуває шторми реконсиліації та гарантує непорушність сертифікаційного аудиту ASIL D.

**Синтез.** Архітектурна дискусія з корифеями розподілених обчислень Клеппманом та Брюером утверджує фінальний синтез монографії:
1. Масштабованість корпоративної системи досягається триланковою Epistemic SOA, асинхронним пакетизуванням Merkle-дерев та стратифікацією дефезитивної аргументації ASPIC+;
2. Надійність в умовах мережевих збоїв забезпечується принципом Safety-First Partitioning: безкомпромісний CP-детермінізм для критичних рішень та криптографічні сертифікати епох для автономної периферії;
3. Відновлення після розривів мережі гарантується прямою монотонною дефезитивністю (Forward-Only Defeasibility) без переписування історії в журналі рішень, забезпечуючи вічну технічну та юридичну неспростовність доказового штучного інтелекту.

## Висновки

1. **Ізоляція рівнів відповідальності в Epistemic SOA:** Розподілена архітектура доказової експертної системи розв'язує фундаментальну дилему масштабованості. Поділ на рівень тонких клієнтів, семантичний координаційний брокер і федеративні доменні сервіси дозволяє ізолювати контексти істинності й усунути залежність від ресурсів термінала кінцевого користувача.
2. **Гарантія інваріанта $ZHR = 1.00$ на тонкому клієнті:** Клієнт взаємодії не утримує локальних баз знань ($S_{\mathrm{client}} = 0$) і не виконує логічного виведення. Його функція обмежена рендерингом криптографічно підписаного доказового кортежу $\langle\text{Verdict}, \text{EvidenceMap}, \text{Signature}\rangle$, що гарантує збереження юридичної сили й повної відсутності галюцинацій навіть на мобільних пристроях.
3. **Онтологічна маршрутизація запитів:** Семантичний брокер відкидає наївну URL-маршрутизацію на користь контентного аналізу. Синтаксично-лексичний препроцесор екстрагує доменні маркери, а динамічний реєстр сервісів призначає головного виконавця на основі обчислення нормованого коефіцієнта спорідненості $\mathrm{Affinity}(\mathcal{S}_{\mathrm{query}}, \mathcal{P}_{\mathrm{service}})$.
4. **Подолання розриву місткості пам'яті:** Сепарація статичних цитат від математичного скелета правил зменшує робочий набір до компактного Активного робочого набору ($\mathrm{AWS} \le 32\,\text{МБ}$). Двобанкова конвеєрна буферизація (Ping-Pong Pipeline) забезпечує повне приховування латентності за рахунок дотримання нерівності $T_{\mathrm{refill}} \ll T_{\mathrm{execute}}$, усуваючи простої обчислювального ядра ($\eta = 1.00$).
5. **Багатоджерельний аргументаційний арбітраж:** При виявленні неповноти знань шаблон Scatter-Gather агрегує свідчення суміжних сервісів кластера за формалізмом ASPIC+. Система підсилює впевненість через короборацію свідчень, детерміновано анулює слабкі рекомендації імперативними нормами вищого рангу та активує захисний шлюз *Fail-Closed* при виявленні нерозв'язних нормативних колізій.
6. **Практична еволюція за проєктним бюджетом:** Запропонований прототип є концептуальним вектором розвитку, що масштабується від одномашинного лабораторного стенда (Рівень 1) до корпоративного R&D-кластера (Рівень 2) і промислового апаратно-детермінованого комплексу рівня ASIL-D (Рівень 3).
7. **Тріаж дефіциту знань та кластеризація SimHash:** Децентралізована обробка виявлених прогалин знань через 64-бітний SimHash та BK-Tree усуває лавинні шторми повторних запитів і перевантаження сервісів. Локальний буфер WAL із жорсткою дисковою квотою гарантує збереження виявлених дефіцитів навіть під час обриву зв'язку з центральним брокером, а перехід у режим кульгавої качки (Lame Duck) унеможливлює видачу недоведених тверджень.
8. **Захист простору ознак та незмінний реєстр рішень:** Дегенерація токенів у запитах і схематичні аномалії блокуються на межі введення суворою десеріалізацією (`DisallowUnknownFields`) та інваріантом $\mathrm{DistinctTokens}(T) \ge 2$. Усі сформовані доказові пакети рішень незворотно фіксуються в деревах Меркла та носіях WORM, утворюючи неспростовний аудиторський слід із криптографічним зв'язуванням вхідних умов, вердикту та версії бази знань.
9. **Холодна готовність Tabula Rasa, чистота доказів та фонотактичний санітайзер:** Динамічний реєстр знань забезпечує старт тонкої консолі з нульовою конфігурацією при $N_{\mathrm{packs}} = 0$ із видачею типізованої відмови та строго порожнім списком доказів ($\mathbf{EvidenceList} = \varnothing$), а фонотактично-ентропійний санітайзер входу за $< 50\,\mu\text{s}$ відсікає клавіатурний шум за вокалічною щільністю $\rho_V \in [0{,}15; 0{,}85]$, довжиною консонантних кластерів $L_C \le 5$ та ентропією Шеннона.

## Запитання для самоперевірки

1. Чому спроба реалізувати експертну систему як товстий локальний моноліт на мобільному пристрої інженера порушує вимоги до масштабованості та синхронізації знань?
2. Яким чином тонкий клієнт забезпечує гарантію доказовості $ZHR = 1.00$, якщо він сам не виконує логічного виведення?
3. Чим відрізняється семантична маршрутизація (Content-Based Semantic Routing) від класичної веб-маршрутизації на рівні API-шлюзів?
4. Сформулюйте математичну умову повного приховування затримок у конвеєрі подвійної буферизації. Чому час фонового підкачування має бути меншим за час виконання блоку правил?
5. Які три епістемічні тригери сигналізують Семантичному Брокеру про необхідність переходу від локальної відповіді до федеративного опитування за шаблоном Scatter-Gather?
6. Як аргументаційний рушій ASPIC+ розв'язує ситуацію нормативної колізії, коли два однаково авторитетні гармонізовані стандарти висувають взаємовиключні вимоги?
7. Опишіть шлях еволюції експертної системи від одномашинного лабораторного прототипу до промислового гетерогенного комплексу за інженерною матрицею вибору технологій.
8. Яким чином 64-бітні відбитки SimHash та дерево метричних відстаней BK-Tree розв'язують проблему лавинного шторму тікетів дефіциту знань у розподіленому кластері?
9. Чому заміна символу підстановки `vida.tasks.>` на `vida.tasks.*` у черзі повідомлень NATS може призвести до системної втрати піддерев контексту знань?
10. Які чотири криптографічні хеші входять до структури Decision Evidence Bundle і як дерево Меркла гарантує незмінність та неспростовність прийнятих вердиктів?
11. Чому за Законом нульових синтетичних доказів заборонено передавати системні діагностичні повідомлення у масиві `EvidenceList` із координатами `[0:0]` під час роботи в стані *Tabula Rasa*?
12. За якими трьома фонотактичними та інформаційно-теоретичними критеріями вхідний санітайзер відрізняє осмислений інженерний запит від нечленороздільного набору символів за мікросекундний час?

## Словник

| Український термін | Англійський відповідник | Коротке пояснення |
|---|---|---|
| Епістемічна SOA | Epistemic Service-Oriented Architecture | Розподілена архітектура експертної системи з ізоляцією контекстів істинності між незалежними сервісами знань |
| Тонкий клієнт взаємодії | Thin Interaction Client | Клієнтський інтерфейс з нульовим локальним сховищем знань, призначений виключно для рендерингу підписаних доказів |
| Семантичний брокер | Semantic Broker | Центральний координатор кластера, що виконує синтаксичний препроцесинг і контентно-орієнтовану маршрутизацію запитів |
| Маршрутизація за змістом | Content-Based Semantic Routing | Спрямування запитів до сервісів знань на основі аналізу онтологічної сигнатури понять і цільових нормативів |
| Активний робочий набір | Active Working Set (AWS) | Компактне транзитивне логічне замикання цільових правил і дефітерів без текстових першоджерел |
| Подвійна буферизація Ping-Pong | Ping-Pong Double Buffering | Симетрична архітектура пам'яті з чергуванням фонового наповнення одного банку та паралельного виконання правил з іншого |
| Приховування затримок | Latency Hiding | Стан конвеєра виведення ($T_{\mathrm{refill}} \le T_{\mathrm{execute}}$), за якого час підкачування даних повністю маскується часом обчислення |
| Шаблон Scatter-Gather | Scatter-Gather Pattern | Паралельне опитування пулу розподілених сервісів кластера з подальшим зведенням результатів у єдиний аргументаційний висновок |
| Короборація свідчень | Corroboration | Математичне підсилення сукупної довіри до висновку при отриманні узгоджених доказів від незалежних джерел |
| Анулювання правила | Undercutting Defeat | Механізм немонотонної аргументації, за якого імперативна норма вищого рангу анулює дію суперечливої рекомендації |
| Кваліфікована колізія Fail-Closed | Fail-Closed Qualified Conflict Gate | Захисне блокування автоматичного компромісу при взаємовиключних вимогах рівносильних норм з ескалацією на архітектора |
| Тріаж дефіциту знань | Knowledge Gap Triage | Алгоритмічна кластеризація та дедуплікація виявлених відсутніх фактів у розподіленому середовищі |
| Відбиток SimHash | SimHash Fingerprint | 64-бітний хеш із властивістю локальної чутливості для вимірювання семантичної відстані Геммінга |
| Дерево Буркхарда-Келлера | Burkhard-Keller Tree (BK-Tree) | Метричне дерево для дискретного логарифмічного пошуку $O(\log N)$ найближчих векторів знань |
| Бар'єр дегенерації ознак | Feature Degeneracy Guard | Механізм валідації вхідних потоків, що відсікає тривіальні та аномальні вектори за ентропійними порогами |
| Доказовий пакет рішення | Decision Evidence Bundle | Криптографічний кортеж із гешів вхідних даних, версії бази знань, графа доказу та підпису Ed25519 |
| Незмінний реєстр рішень | Immutable Decision Ledger | Розподілена структура на базі дерев Меркла та сховищ WORM для неспростовного аудиту висновків |
| Стан Tabula Rasa | Tabula Rasa Cold-Readiness State | Режим холодної готовності системи за відсутності змонтованих пакетів знань ($N_{\mathrm{packs}} = 0$) із поверненням чесної типізованої відмови |
| Фонотактично-ентропійний санітайзер | Phonotactic-Entropic Input Sanitizer | Детермінований фільтр вхідного периметра, що відсікає клавіатурний шум за вокалічною щільністю, консонантними кластерами та ентропією Шеннона |
| Когнітивно-криміналістична біфуркація | Cognitive-Forensic UI Bifurcation | Розділення операторського інтерфейсу на чистий діалоговий потік та інспекційну панель криптографічного аудиту й телеметрії |

## Абревіатури

| Скорочення | Розшифрування | Значення |
|---|---|---|
| ASIL | Automotive Safety Integrity Level | Рівень повноти безпеки автомобільної електроніки за стандартом ISO 26262 (від A до D) |
| ASPIC+ | Argumentation Service Platform with Incomplete and Conflicting Information | Формальний апарат структурування аргументів, презумпцій та правил атаки/дефіту |
| AWS | Active Working Set | Активний робочий набір знань, мінімально необхідний для обчислення запиту |
| BK-Tree | Burkhard-Keller Tree | Метричне дерево для пошуку найближчих сусідів у просторах із дискретною метрикою |
| BRAM | Block Random Access Memory | Внутрішньокристальна швидка пам'ять апаратного процесора правил з фіксованим часом доступу |
| DLQ | Dead-Letter Queue | Черга недоставлених чи аномальних повідомлень для ізоляції збійних пакетів |
| DMA | Direct Memory Access | Прямий доступ до пам'яті для фонового апаратного перенесення даних повз ядро процесора |
| EVM | Epistemic Virtual Machine | Детермінована віртуальна машина доказового виведення логічних резолюцій |
| gRPC | Google Remote Procedure Call | Високопродуктивний бінарний RPC-фреймворк на базі HTTP/2 та Protocol Buffers |
| IPC | Inter-Process Communication | Комплекс системних механізмів обміну даними між процесами на одній машині |
| KTP | Knowledge Testing Pyramid | Багаторівнева методологія тестування баз знань від атомарних фактів до цілісних сценаріїв |
| LSH | Locality-Sensitive Hashing | Хешування, чутливе до локальності, для швидкого групування схожих об'єктів |
| NPU | Neural Processing Unit | Спеціалізований апаратний прискорювач тензорних операцій для штучних нейромереж |
| PWA | Progressive Web Application | Технологія створення веб-застосунків з можливістю автономного кешування інтерфейсу |
| RCU | Read-Copy-Update | Механізм неблокувальної синхронізації читачів під час гарячого оновлення вказівників на структури знань |
| RPC | Remote Procedure Call | Парадигма взаємодії розподілених компонентів через віддалений виклик процедур |
| SLM | Small Language Model | Компактна спеціалізована мовна модель (1B-7B) для лінгвістичного аналізу та класифікації |
| SOA | Service-Oriented Architecture | Сервіс-орієнтована архітектура програмного комплексу зі слабким зв'язуванням компонентів |
| TARA | Threat Analysis and Risk Assessment | Методологія оцінювання загроз і кібербезпекових ризиків за стандартом ISO/SAE 21434 |
| WAL | Write-Ahead Log | Журнал випереджального запису на диск для забезпечення атомарності та довговічності |
| WORM | Write Once, Read Many | Апаратний або програмний носій із однократним записом і багаторазовим зчитуванням без можливості модифікації |
| ZHR | Zero-Hallucination Rate | Метрика абсолютної відсутності безпідставних генерацій ($ZHR = 1.00$) у доказових ЕС |
