## Анотація

Заключна глава підручника розглядає **нижній, програмно-апаратний ешелон (Ешелон 3)** архітектури експертної системи: навчальне пониження (lowering) ациклічної гілки схеми правил у безцикловий мікрокод архітектурної моделі спеціалізованого регістрового виконавця (Epistemic Processing Unit — EPU), для якої в репозиторії немає ні компілятора, ні RTL, та фізичний синтез однотактового компаратора допуску на програмованих логічних інтегральних схемах (FPGA). У системах жорсткого реального часу недостатньо довести логічну коректність шлюзу на рівні високорівневої програми: необхідно також гарантувати детерміновану верхню межу часу виконання (WCET), розрахувати бітову місткість слів стану, пропускну здатність шини при подвійній буферизації пам'яті BRAM і переконатися, що комбінаційна логіка вкладається у тактовий період цільового кристала. У главі показано, чому пряма реалізація 64-бітних часових та інтервальних перевірок через послідовні ланцюги переносу не долає поріг $`100\text{ МГц}`$ на ПЛІС `iCE40HX8K` ($`57{,}3\text{–}59{,}7\text{ МГц}`$), і як заміна каскадного віднімання на 64-бітний суматор зі збереженням переносу (**Carry-Save Adder, `csa64`**) та 5-рівневе паралельно-префіксне дерево піднімає оцінку частоти однотактового ядра до **`104,50–110,57 МГц`** (статичний часовий аналіз nextpnr після розміщення й трасування для п'яти зерен, а не вимірювання плати) при нульовій кількості розбіжностей на $58\,627$ тестових векторах і SAT-доведеній комбінаційній еквівалентності прямого й префіксного ядер.

## 1. Нижній ешелон СТЕС: трансляція гілки схеми в безцикловий асемблер EPU

У Главі 1 (схема 1.2) встановлено, що високорівневий граф СТЕС (`reason`) виконує роль мови високого рівня, тоді як низькорівневий виконавець EPU працює на рівні **мови асемблера**. Розглянемо, як одна гілка правил могла б перетворюватися на лінійну послідовність регістрових інструкцій і які апаратні інваріанти при цьому мала б забезпечувати архітектура.

> [!IMPORTANT]
> **Статус EPU в цій книзі.** У репозиторії є компілятори правил у програми для Go-інтерпретаторів: `Compile` у [src/graph.go](src/graph.go), `CompileHorn` у [src/horn.go](src/horn.go) і `CompileNormative` у [src/normative.go](src/normative.go). Компілятора в описану нижче 32-бітну систему команд EPU немає, і RTL самого EPU також немає. Таблиця 7.1, лістинг і формула (7.2) є навчальним пониженням, виконаним вручну, та архітектурною моделлю. ### 1.1. Від вентиля високорівневої схеми до послідовності інструкцій EPU

На рівні високорівневого графа (Глава 3) одне правило $`r: (p_1 = e_1) \land (p_2 = e_2) \Rightarrow (c = v_{\mathrm{exp}})`$ із перевіркою інтервалу, одиниці вимірювання, відсутності винятку та кастодії першоджерела записується як один складений вузол. Під час компіляції (lowering) цей вузол розкладається у лінійну послідовність елементарних 32-бітних мікрокоманд над регістровим файлом (`%er0..%er7`, регістр кастодії `%ebx`, регістр прапорців `EFLAGS`), наведену в таблиці 7.1.

<a id="tbl-7-1"></a>

| Крок високорівневої схеми СТЕС | Відповідна інструкція асемблера EPU | Модифікація регістрів і прапорців стану |
|---|---|---|
| Ввід атома передумови $`p_k`$ (`INPUT`) | `OP_LOAD_A dst, imm` | Завантажує ідентифікатор і тип атома в `%er[dst]`, встановлює валідність `reg_vld[dst] = 1` і скидає прапорець кастодії `CF <= 0` |
| Перевірка одиниці вимірювання $`u = u_0`$ | `OP_NORM_U dst, unit_id` | Якщо одиниця регістра не збігається з очікуваною, виставляє прапорець `UF <= 1` і нескидну защіпку `sticky_uf <= 1` |
| Вхідний інтервальний компаратор (1.4) | `OP_CHECK_Q src1` / `OP_CHECK_ENV` | Перевіряє нерівність $`Q_{\min} \le \mathrm{reg}[src1] \le Q_{\max}`$; при виході за межі виставляє `ZF <= 1` та `sticky_uf <= 1` |
| Зіставлення передумови (`MATCH`, L2) | `OP_EVAL_S dst, src1, src2` | Порівнює операнди передумови (`reg[src1] == reg[src2]`); при нерівності виставляє `ZF <= 1` |
| Перевірка відсутності винятку (5.1) | `OP_EVAL_DFT src1` / `OP_UNDERCUT` | Якщо умова дефітера активна, виставляє прапорець `DF <= 1` та нескидну защіпку `sticky_df <= 1` |
| Перевірка гешу цитати першоджерела $`\mathcal{C}`$ | `OP_ANCHOR_E` | За 256-бітним компаратором перевіряє `ebx_actual == ebx_expected`; при успіху `CF <= 1`, при розбіжності `sticky_cf_fail <= 1` |
| Ациклічний обхід без повернень | `OP_JMP_IF_NOT sel, imm` | Перехід **суворо вперед** (`imm > eir`); спроба переходу назад (`imm <= eir`) негайно викликає апаратну пастку `R_BAD_JUMP` |
| Висновок правила (`DERIVE`) і вердикт (`ANSWER`) | `OP_APPLY_S`, `OP_EMIT_CLAIM`, `OP_HALT_ACCEPT` / `OP_HALT_REFUSE` | Записує код виведеного твердження в `%emr` і піднімає лінію `accept` лише за умови `CF == 1` та відсутності всіх липких порушень |

**Таблиця 7.1.** Трансляція операцій високорівневої схеми СТЕС у безциклові регістрові інструкції виконавця EPU.

**Приклад скомпільованої безциклової траси інструкцій EPU для однієї гілки допуску.**
Покажемо на конкретному лістингу, як елементарна схема допуску відкриття клапана з Глави 1 (§4: перевірка ролей і факту тиску `M-17`, одиниці `bar`, вікна $[70; 80]$ у масштабі десятих бара, тобто $`W = [7{,}0;\ 8{,}0]\text{ бар}`$, відсутності дефітера ремонту та автентичності SHA-256 цитати регламенту `N-4`) вручну знижується (навчальне пониження) до лінійної послідовності з 9 інструкцій EPU в адресах `eir = 0..8`:

```text
eir=0: OP_LOAD_A      %er0, atom_id=17       ; завантажити факт M-17 у %er0 (CF <= 0, 2 такти)
eir=1: OP_NORM_U      %er0, unit_id=BAR      ; звірити одиницю 'bar' (при розбіжності sticky_uf <= 1, 1 такт)
eir=2: OP_CHECK_Q     %er0                   ; перевірити Q_min <= %er0 <= Q_max (при виході sticky_uf <= 1, ZF <= 1, 1 такт)
eir=3: OP_JMP_IF_NOT  sel=ZF, target=8       ; перехід УПЕРЕД (8 > 3) на OP_HALT_REFUSE, якщо межу порушено (1 такт)
eir=4: OP_EVAL_DFT    %er0                   ; перевірити таблицю дефітерів обслуговування (при збігу sticky_df <= 1, 1 такт)
eir=5: OP_ANCHOR_E                           ; 256-бітна звірка SHA-256 у %ebx (CF <= 1 або sticky_cf_fail <= 1, 4 такти)
eir=6: OP_APPLY_S     %er0, rule_id=4        ; застосувати норму N-4 до %er0 (1 такт)
eir=7: OP_HALT_ACCEPT                        ; видати ACCEPT лише якщо CF==1 і всі sticky_*==0 (1 такт)
eir=8: OP_HALT_REFUSE reason=0x0403          ; термінальна відмова при стрибку з eir=3 (1 такт)
```

У цій програмі єдиний умовний перехід на адресі `eir = 3` веде суворо вперед на адресу `target = 8` ($8 > 3$). Латентності в коментарях лістингу є припущеннями моделі: 2 такти для `OP_LOAD_A`, 4 такти для `OP_ANCHOR_E` і по 1 такту для решти команд. За цих припущень на шляху успіху виконується 8 із 9 інструкцій (`eir = 0..7`; `OP_HALT_REFUSE` на `eir = 8` не виконується), і їхня сума становить $2 + 1 + 1 + 1 + 1 + 4 + 1 + 1 = 12$ тактів ($`120\text{ нс}`$ на частоті $`100\text{ МГц}`$). Шлях відмови `eir = 0..3` $\to$ `8` займає $2 + 1 + 1 + 1 + 1 = 6$ тактів. Це умовний розрахунок, а не виміряний час: апаратної реалізації EPU немає, тому латентності інструкцій, пам'яті та шини не підтверджено. За задумом моделі, навіть якщо зовнішній код спробував би перескочити перевірку на `eir = 3`, інструкція `OP_HALT_ACCEPT` на `eir = 7` заблокувала б дозвіл через защіпку `sticky_uf == 1`.

### 1.2. Гарантія скінченного часу виконання (WCET) та неамнезійні липкі защіпки

<a id="def-7-1"></a>

**Означення 7.1 (Безциклове виконання з переходами тільки вперед — Forward-Only Execution).** Мікропрограма виконавця EPU обсягом $`N_{\mathrm{prog}}`$ слів називається *безцикловою з переходами тільки вперед*, якщо кожна інструкція або збільшує лічильник команд на одиницю ($`\mathrm{eir}_{t+1} = \mathrm{eir}_t + 1`$), або виконує умовний перехід на строго більшу адресу $`\mathrm{imm} > \mathrm{eir}_t`$, або зупиняє конвеєр термінальною командою (`OP_HALT_ACCEPT`, `OP_HALT_REFUSE`), а будь-яка спроба переходу на адресу $`\mathrm{imm} \le \mathrm{eir}_t`$ перехоплюється апаратною пасткою `R_BAD_JUMP`.

Два архітектурні обмеження таблиці 7.1 мають прямий математичний наслідок для безпеки реального часу:

1. **Сувора монотонність лічильника інструкцій (`forward-only jumps`):** оскільки кожна звичайна команда збільшує лічильник команд на одиницю ($`\mathrm{eir}_{t+1} = \mathrm{eir}_t + 1`$), а команда умовного переходу `OP_JMP_IF_NOT` дозволена лише на адресу $`\mathrm{imm} > \mathrm{eir}_t`$, послідовність адрес виконуваних команд утворює строго зростаючу послідовність у скінченній пам'яті програм обсягом $`N_{\mathrm{prog}}`$ слів:

$$
0 \le \mathrm{eir}_0 < \mathrm{eir}_1 < \dots < \mathrm{eir}_k < N_{\mathrm{prog}}.
$$

Отже, жодна скомпільована програма принципово не може зациклитися, а максимальна кількість виконаних інструкцій не перевищує $`N_{\mathrm{prog}}`$. За максимальної тривалості однієї інструкції $`C_{\max}`$ тактів верхня межа часу виконання (WCET) становить:

<a id="formula-7-2"></a>

$$
T_{\mathrm{WCET}} \le \frac{N_{\mathrm{prog}} \cdot C_{\max}}{f_{\mathrm{clk}}}.
$$

**Формула (7.2).** Верхня межа часу виконання безциклової програми в EPU.

Числовий приклад: при $`N_{\mathrm{prog}} = 64`$ інструкціях, $`C_{\max} = 4`$ тактах на інструкцію та тактовій частоті $`f_{\mathrm{clk}} = 100\text{ МГц}`$ ($`10\text{ нс}`$ на такт) маємо $`T_{\mathrm{WCET}} \le 64 \times 4 \times 10\text{ нс} = 2560\text{ нс} = 2{,}56\ \mu\text{с}`$. За задумом архітектури сторожовий лічильник `MAX_CYCLES` має примусово зупиняти ядро у стані відмови при досягненні граничного порога тактів.

Формула (7.2) дає **умовну** межу. Вона правильна лише тоді, коли $`C_{\max}`$ справді охоплює найгіршу латентність кожної інструкції разом із доступом до пам'яті програм і даних, очікуванням арбітражу шини та DMA, конфліктами банків і обробкою пасток. Без такої моделі пам'яті й арбітражу значення $`C_{\max}`$ невідоме. Тому $`2{,}56\ \mu\text{с}`$ є результатом підстановки припущеного $`C_{\max} = 4`$, а не виміряним чи сертифікованим WCET. Аналіз реального WCET потребує методів і інструментів, описаних у [[3]](#src-3).

2. **Неамнезійні липкі прапорці порушень (`Sticky Violation Latches`):** прапорці порушення одиниць/меж (`sticky_uf`), спрацювання дефітера (`sticky_df`) та помилки кастодії (`sticky_cf_fail`) у моделі EPU задано як однобітові регістри зі встановленням без програмного скидання:

$$
\mathrm{sticky\_viol}_{t+1} = \mathrm{sticky\_viol}_t \lor \mathrm{viol}_t.
$$

Тому жодна наступна інструкція програми не може «затерти» раніше виявлене порушення до повного апаратного скидання ядра `rst_n`, а фінальний сигнал допуску `disposition_accept` формується лише при нульовому векторі всіх поточних і липких порушень.

### 2.2. Розрахунок блоків BRAM та інваріант подвійної буферизації (Ping-Pong)

Розрахуємо обсяг вбудованої блокової пам'яті ПЛІС (BRAM) та час передавання даних для робочого банку на $`N_{\mathrm{states}} = 4\,096`$ вирівняних записів профілю `reference64` ($`W_{\mathrm{aligned}} = 384\text{ біти} = 48\text{ байтів}`$):

1. **Місткість одного банку станів:**

$$
V_{\mathrm{bank}} = N_{\mathrm{states}} \cdot W_{\mathrm{aligned}} = 4\,096 \times 48\text{ Б} = 196\,608\text{ Б} = 192\text{ КіБ}\ (1\,572\,864\text{ біти}).
$$

2. **Умовна геометрія розміщення у блоках Xilinx `RAMB36E1` (організація $`512\text{ слів} \times 72\text{ біти}`$):**
   Цей приклад стосується гіпотетичного кристала Xilinx 7-ї серії й не пов'язаний з експериментом на iCE40 у §3–4. Щоб зчитувати один 384-бітний запис за один такт, за шириною потрібно $\lceil 384 / 72 \rceil = 6$ паралельних смуг пам'яті, а за глибиною для $4\,096$ рядків потрібно $\lceil 4\,096 / 512 \rceil = 8$ банків. Отже, прямокутна матриця одного буфера вимагає $6 \times 8 = 48$ блоків `RAMB36E1` (фізична місткість $`216\text{ КіБ}`$). Подвійна буферизація потребує двох таких банків: $`2 \times 192 = 384\text{ КіБ}`$ корисної місткості та $2 \times 48 = 96$ блоків `RAMB36E1` ($`432\text{ КіБ}`$ фізичної).

   **Порівняння з кристалом експерименту.** Уся вбудована пам'ять `iCE40HX8K` складається з $32$ блоків `SB_RAM40_4K` по $`4\text{ Кібіт}`$, тобто $`131\,072\text{ біти} = 16\text{ КіБ}`$. Один банк `reference64` ($`1\,572\,864\text{ біти}`$) у $12$ разів більший за всю цю пам'ять і потребує щонайменше $384$ блоків EBR, а пара банків потребує $768$ блоків. Отже, на `iCE40HX8K` описаний банк не вміщується; розрахунок перевіряє тест `TestReference64BankVersusICE40HX8K` у [src/hardware/calculate_test.go](src/hardware/calculate_test.go).

3. **Час підкачування банку шиною DMA ($`T_{\mathrm{refill}}`$) та умова безперервної роботи (Ping-Pong):**
   При подвійній буферизації (коли EPU обробляє активний банк `Bank A` протягом часу $`T_{\mathrm{execute}}`$, а контролер DMA паралельно завантажує наступний пакет у тіньовий банк `Bank B`) система працює без простоїв конвеєра (`Pipeline Stall`), якщо виконується нерівність (7.4):

<a id="formula-7-4"></a>

$$
T_{\mathrm{refill}} = \frac{N_{\mathrm{states}} \cdot \lceil W_{\mathrm{aligned}} / B_{\mathrm{bus}} \rceil}{f_{\mathrm{clk}}} \le T_{\mathrm{execute}}.
$$

**Формула (7.4).** Час завантаження банку станів через шину шириною $`B_{\mathrm{bus}}`$ бітів і умова безперервної подвійної буферизації ([src/hardware/calculate.go](src/hardware/calculate.go)).

Підставимо числові значення для $`N_{\mathrm{states}} = 4\,096`$, $`W_{\mathrm{aligned}} = 384\text{ біти}`$ та частоти шини $`f_{\mathrm{clk}} = 100\text{ МГц}`$ ($`10\text{ нс}`$ на такт):
- для 64-бітної шини ($`B_{\mathrm{bus}} = 64`$): один запис потребує $\lceil 384 / 64 \rceil = 6$ тактів ($`60\text{ нс}`$), а весь банк — $4\,096 \times 6 = 24\,576$ тактів, тобто **$`T_{\mathrm{refill}} = 245{,}76\ \mu\text{с}`$**;
- для 256-бітної шини ($`B_{\mathrm{bus}} = 256`$): один запис з вирівнюванням початку на новий такт потребує $\lceil 384 / 256 \rceil = 2$ такти ($`20\text{ нс}`$), а весь банк — $8\,192$ такти (**$`T_{\mathrm{refill}} = 81{,}92\ \mu\text{с}`$**; у режимі суцільного потоку — $`61{,}44\ \mu\text{с}`$);
- для 512-бітної шини ($`B_{\mathrm{bus}} = 512`$): один запис передається за $1$ такт ($`10\text{ нс}`$), а весь банк — за $4\,096$ тактів (**$`T_{\mathrm{refill}} = 40{,}96\ \mu\text{с}`$**).

Ці значення є нижніми межами ідеальної передачі: функції `Serialize` і `SerializeRecords` у [src/hardware/calculate.go](src/hardware/calculate.go) приймають один такт шини на слово без арбітражу DMA, затримки читання джерела, кадрування та перетину тактових доменів. Перше заповнення також не враховано: до першого обміну банками ядро чекає повний $`T_{\mathrm{refill}}`$, бо ще немає банку для обробки. Тому нерівність (7.4) з цими числами є необхідною, але не достатньою умовою роботи без простоїв. Дослідний RTL з §3–4 взагалі не має такої шини: обгортка `gate_top` отримує слово через один вивід і потребує $462$ тактів на кожне 462-бітне слово.

## 3. Синтез однотактового компаратора `PrevalidatedGate` на ПЛІС і проблема каскадного переносу

Розглянемо фінальний апаратний вузол тракту допуску — модуль `PrevalidatedGate` ([src/rtl/gate/rtl/gate_core.v](src/rtl/gate/rtl/gate_core.v)), який за один такт перевіряє дев'ять післяумов над 462-бітним попередньо валідованим словом стану `GateInput` і формує 10-бітний регістровий вихід `result_q` (біт 0 — сигнал дозволу `Allow`, біти 1..9 — індивідуальні прапорці причин відмови).

<a id="sec-3-1"></a>

### 3.1. Дев'ять апаратних умов і критичний шлях прямого віднімання (`p0`)

<a id="def-7-2"></a>

**Означення 7.2 (Однотактовий компаратор післяумов `PrevalidatedGate`).** *Однотактовим компаратором післяумов* називається регістрово-регістровий апаратний вузол (`word_q[461:0]` $\to$ комбінаційний предикат $\to$ `result_q[9:0]`), який за один такт синхронізації $`f_{\mathrm{clk}}`$ одночасно перевіряє дев'ять післяумов попередньо валідованого слова стану і формує біт дозволу `Allow` (`result[0]`) та 9-бітний вектор причин відмови (`result[9:1]`).

Щоб біт дозволу `Allow` (`result[0]`) набув значення `1`, у комбінаційному ядрі мають одночасно виконуватися дев'ять умов:
1. `CustodyValidated == 1` (біт 0);
2. `BindingValid == 1` (біт 1);
3. `SIMatch == 1` (біт 2);
4. `NumericValid == 1` (біт 3);
5. `NormPermitted == 1 && Undercut == 0` (біти 4–5);
6. `Evidence == 8'd1` (лише чиста позитивна підтримка `PRO`, біти 6–13);
7. `DataRevision == ValidatedRevision` (32-бітна рівність, біти 14–77);
8. `PolicyRevision == ExpectedPolicy` (32-бітна рівність, біти 78–141);
9. **Перевірка віку даних у 64-бітному беззнаковому часі** (`Timestamp <= Now` і `Now - Timestamp <= MaxAge`, біти 142–333) та **перевірка знакової 64-бітної верхньої межі інтервалу** (`UpperRaw <= LimitRaw`, біти 334–461).

У прямому варіанті RTL (`one_tick_direct`, `p0` у [src/rtl/gate/rtl/gate_core.v](src/rtl/gate/rtl/gate_core.v)) умова свіжості записана безпосередньо через оператор віднімання та два порівняння:

```verilog
wire [63:0] age      = now - timestamp;
wire        time_ok  = (timestamp <= now) && (age <= max_age);
```

Що відбувається під час синтезу цього виразу для ПЛІС Lattice `iCE40`?
Спочатку 64-бітний віднімач обчислює різницю `age = now - timestamp`, сигнал переносу якої послідовно проходить крізь $64$ однобітові ланки `SB_CARRY`. Потім старші біти отриманої різниці `age` подаються на вхід **другого** 64-бітного компаратора `age <= max_age`, який утворює ще один каскад `SB_CARRY`! Сумарна затримка двох послідовно з'єднаних 64-бітних ланцюгів переносу на кристалі `iCE40HX8K-CT256` становить $`\approx 17{,}1\text{ нс}`$, через що максимальна тактова частота прямого варіанта `p0` досягає лише **`57,33–59,67 МГц`** ($0$ із $5$ зерен трасування проходять цільовий поріг $`100\text{ МГц}`$).

## 4. Оптимізація критичного шляху через дерева збереження переносу (`csa64`) і префіксний компаратор

Як усунути подвійний послідовний каскад 64-бітного переносу, не змінюючи жодного біта логічної функції `PrevalidatedGate`?

### 4.1. Математичне перетворення триоперандної нерівності часу на форму збереження переносу (CSA)

Зауважимо, що у дводоповняльній арифметиці різниця $A - B$ за модулем $2^{64}$ дорівнює $`A + \bar{B} + 1`$, де $`\bar{B} = 2^{64} - 1 - B`$ — порозрядна інверсія 64-бітного числа. Позначимо беззнакові 64-бітні величини так: $N$ — поточний час `Now`, $T$ — мітка часу виміру `Timestamp`, $M$ — допустимий вік `MaxAge`; усі три лежать у діапазоні $`[0;\ 2^{64} - 1]`$ тиків годинника. Умову $T \le N$ перевіряє окреме префіксне дерево, тому для умови віку можна вважати, що різниця $N - T$ обчислюється без позики. Тоді перевірка віку зводиться до вихідного переносу однієї суми:

$$
N - T \le M \iff M + T + (2^{64} - 1 - N) + 1 \ge 2^{64}.
$$

Еквівалентність випливає з тотожності $`M + T + (2^{64} - 1 - N) + 1 = 2^{64} + \bigl(M - (N - T)\bigr)`$. Права частина не менша за $2^{64}$ тоді й лише тоді, коли $M \ge N - T$. Сума лежить у межах $`[1;\ 3 \cdot 2^{64} - 2]`$, тому апаратура має зберегти вихідний перенос із 64-го розряду, а не відкинути його разом зі старшими бітами. Вираз $`2^{64} - 1 - N`$ є лише інверсією $\bar{N}$, а заключне $+1$ завершує дводоповняльне заперечення. Без нього умова перетворюється на строгу $N - T < M$. Перевіримо формулу на крайніх значеннях:

1. $N = T = M = 0$: сума дорівнює $`0 + 0 + (2^{64} - 1) + 1 = 2^{64} \ge 2^{64}`$, отже, вік $0 \le 0$ допускається. Без $+1$ сума $`2^{64} - 1`$ хибно відхилила б межовий випадок рівності.
2. $`N = T = M = 2^{64} - 1`$: сума дорівнює $`(2^{64} - 1) + (2^{64} - 1) + 0 + 1 = 2^{65} - 1 \ge 2^{64}`$, отже, вік $0$ допускається.
3. $`N = M = 2^{64} - 1`$, $T = 0$: сума дорівнює рівно $`2^{64}`$, отже, найбільший можливий вік, що дорівнює межі, допускається. Якщо $`M = 2^{64} - 2`$, сума становить $`2^{64} - 1 < 2^{64}`$ і умова віку відхиляється.

У RTL цей доданок уже є: модуль `csa64` у [src/rtl/gate/rtl/prefix_carry.v](src/rtl/gate/rtl/prefix_carry.v) (рядок `assign k_shift = {k[62:0], 1'b1};`) заповнює вільний молодший розряд зсунутого вектора переносів одиницею. SAT-мітр `make equiv` доводить еквівалентність прямого й префіксного ядер. Контрольний запуск того самого мітра на копії `csa64` з нулем у цьому розряді дає `model found: FAIL`, тобто втрата доданка $+1$ виявляється.

Замість того щоб спочатку чекати завершення 64-бітного переносу у різниці $N - T$, застосуємо в кожному розряді $`i \in \{0, \dots, 63\}`$ однорозрядний **суматор зі збереженням переносу (Carry-Save Adder — `csa64`)** ([src/rtl/gate/rtl/prefix_carry.v](src/rtl/gate/rtl/prefix_carry.v)), який за **один шар таблиць істинності (`1 LUT`)** без жодного горизонтального розповсюдження переносу стискає три 64-бітні вектори $`(M, T, \bar{N})`$ у два вектори — порозрядну суму $`S_i`$ та зсунутий на один розряд вектор переносів $`C_i`$, молодший розряд якого $`C_0 = 1`$ несе доданок $+1$, за формулою (7.5):

<a id="formula-7-5"></a>

$$
\begin{aligned}
S_i &= M_i \oplus T_i \oplus \bar{N}_i, \\[4pt]
C_{i+1} &= (M_i \land T_i) \lor (M_i \land \bar{N}_i) \lor (T_i \land \bar{N}_i), \qquad C_0 = 1.
\end{aligned}
$$

**Формула (7.5).** Одношарове стиснення трьох 64-бітних операндів часової умови у суматорі зі збереженням переносу `csa64`. Тут $`i \in \{0, \dots, 63\}`$, $`S = \sum_{i=0}^{63} S_i 2^i`$ і $`C = \sum_{i=0}^{64} C_i 2^i`$. Тоді $`S + C = M + T + \bar{N} + 1`$, а старший перенос $`C_{64}`$ (сигнал `k_top`) додається до вихідного переносу дерева (7.6).

Після стиснення (7.5) триоперандна нерівність $N - T \le M$ зводиться до однієї стандартної перевірки вихідного переносу двооперандної суми $S + C$! А для обчислення цього переносу за логарифмічну глибину замість лінійного ланцюга `SB_CARRY` у модулі `prefix_carry` побудовано **5-рівневе паралельно-префіксне дерево генерації та поширення переносу** $(G, P)$ з коефіцієнтом об'єднання $2$:

<a id="formula-7-6"></a>

$$
(G_{\mathrm{hi:lo}},\ P_{\mathrm{hi:lo}}) = \bigl(G_{\mathrm{hi}} \lor (P_{\mathrm{hi}} \land G_{\mathrm{lo}}),\ P_{\mathrm{hi}} \land P_{\mathrm{lo}}\bigr).
$$

**Формула (7.6).** Асоціативний оператор паралельно-префіксного дерева переносу `prefix_carry` ([src/rtl/gate/rtl/prefix_carry.v](src/rtl/gate/rtl/prefix_carry.v)).

Таке саме 5-рівневе префіксне дерево застосовано до порівняння `Timestamp <= Now` та знакового порівняння `UpperRaw <= LimitRaw` (із попередньою інверсією знакового біта $63$). У результаті вся комбінаційна глибина від регістра слова `word_q` до регістра результату `result_q` стискається до **$7$ рівнів комірок `SB_LUT4`** ($0$ примітивів `SB_CARRY`!), а затримка критичного шляху на `iCE40HX8K` падає з $`17{,}1\text{ нс}`$ до **$`9{,}04\text{–}9{,}57\text{ нс}`$**.

### 4.2. Зведені результати синтезу, трасування та верифікації RTL

Усі три варіанти RTL — прямий однотактовий `one_tick_direct` (`p0`), префіксний однотактовий `one_tick_prefix` (`p2`) та двостадійний конвеєрний `pipelined_2stage` (`p1`) — перевірено у симуляторах **Icarus Verilog 12.0** та **Verilator 5.032** на наборі з **`58 627` тестових векторів** (повний перебір прапорців і кодів свідчень, граничні значення `int64`/`uint64`, однобітові інверсії кожного з 462 бітів та 30 000 випадкових векторів) із **`0` розбіжностей** відносно Go-еталона `hardware.PrevalidatedGate`. Усі $8$ контрольних мутацій RTL виявлено тестбенчем. За будь-якої розбіжності тестбенч викликає `$fatal`, тому `make sim` завершується з ненульовим кодом. Це перевірено на копії набору векторів з одним спотвореним очікуваним бітом. > **Вимоги до інтеграції дослідного RTL**
> 1. **Дійсність результату.** Модулі `gate_reg`, `gate_pipe` і `gate_top` не мають входу скидання та сигналу `out_valid`. Регістр `result_q` утримує `Allow` останнього захопленого слова, коли `load = 0`, а на такті захоплення нового слова ще показує попередній результат. Додавання цих сигналів змінило б нетліст, для якого отримано таблицю 7.7, тому вони залишаються вимогою до системи-інтегратора. Інтегратор має супроводжувати слово ознакою дійсності, затриманою на латентність варіанта (1 або 2 такти), примусово знімати дозвіл поза дійсним тактом (fail-closed) і для `gate_top` брати результат лише після повного завантаження всіх 462 бітів.
> 2. **Ширина префіксного дерева.** Модуль `prefix_carry` розрахований лише на `W = 64`. За `W = 65` старший біт ігнорувався б мовчки, тому будь-яке `W ≠ 64` тепер зупиняє елаборацію в iverilog, Verilator і Yosys.
> 3. **Масштаб числових меж.** `UpperRaw` і `LimitRaw` шлюзу мають ціну молодшого розряду $`2^{-16}`$, а 64-бітні числові поля профілю `wide_leaf_custody` мають ціну $`2^{-32}`$. На межі компонента потрібне знакове перетворення з округленням назовні: $`\mathrm{UpperRaw} = \lceil U_{\mathrm{wide}} / 2^{16} \rceil`$, $`\mathrm{LimitRaw} = \lfloor L_{\mathrm{wide}} / 2^{16} \rfloor`$. Після нього треба перевірити діапазон, а за невдалого перетворення встановити `NumericValid = 0`. Без перетворення wide-значення $-1$ (raw $`-2^{32}`$) було б прочитане як $-65\,536$.
>
> Подробиці наведено в [src/rtl/gate/README.md](src/rtl/gate/README.md#межі-інтерфейсу-та-вимоги-інтеграції).

Відтворити генерацію векторів, симуляцію, SAT-перевірку еквівалентності та синтез RTL можна командами:

```sh
cd src
go test -race -count=1 ./hardware ./cmd/hardware ./cmd/gatevectors
(cd rtl/gate && make clean && make sim && make equiv)
(cd rtl/gate && make -j8 summary RESULTS=build/repro)
```

## 5. Питання та вправи для самоперевірки

1. **Питання 1.** Обчисліть за формулою (7.4) час підкачування банку $`T_{\mathrm{refill}}`$ для $`N_{\mathrm{states}} = 4\,096`$ записів профілю `leaf_custody` ($`W_{\mathrm{aligned}} = 640\text{ бітів} = 80\text{ Б}`$, таблиця 7.3) через шину $`B_{\mathrm{bus}} = 256\text{ бітів}`$ на частоті $`f_{\mathrm{clk}} = 100\text{ МГц}`$, якщо кожний запис починається з нового такту шини.
   - *Відповідь:* Кількість тактів шини на один запис становить $\lceil 640 / 256 \rceil = 3$ такти. На $4\,096$ записів потрібно $4\,096 \times 3 = 12\,288$ тактів. При періоді такту $`10\text{ нс}`$ час завантаження дорівнює $`T_{\mathrm{refill}} = 12\,288 \times 10\text{ нс} = 122\,880\text{ нс} = 122{,}88\ \mu\text{с}`$.
2. **Питання 2.** Чому в прямому варіанті RTL `p0` перевірка свіжості `(timestamp <= now) && ((now - timestamp) <= max_age)` створює вдвічі довший критичний шлях, ніж звичайне 64-бітне порівняння?
   - *Відповідь:* Спочатку 64-бітний віднімач `now - timestamp` мусить поширити сигнал позики від біта 0 до біта 63, і лише після встановлення старших бітів різниці `age` другий 64-бітний компаратор `age <= max_age` починає власний наскрізний прохід переносу. Суматор зі збереженням переносу `csa64` (7.5) усуває перший каскад, стискаючи три операнди до двох за глибину лише 1 таблиці `SB_LUT4`.
3. **Питання 3.** Чому вимога заборони переходів назад (`imm > eir` в інструкції `OP_JMP_IF_NOT`) є достатньою умовою відсутності циклів у довільній програмі EPU без потреби будувати граф потоків керування під час виконання?
   - *Відповідь:* Оскільки кожна інструкція або збільшує `eir` на $1$, або переходить на строго більшу адресу $`\mathrm{imm} > \mathrm{eir}`$ у скінченному діапазоні $`[0, N_{\mathrm{prog}}-1]`$, значення регістра `eir` строго зростає на кожному кроці й не може відвідати жодну адресу двічі.

## Висновки

### Призначення глави та завершення трирівневої архітектури курсу

Глава 7 замикає наскрізний інженерний маршрут підручника, спускаючись від високорівневих графів міркування (Ешелон 1, Глави 2–3) і верифікованого програмного ядра (Ешелон 2, Глави 4–6) до **низькорівневого безциклового виконання та цифрової схемотехніки ПЛІС (Ешелон 3)**. Її мета — показати, як логічні та метрологічні інваріанти експертної системи втілюються у фізичні регістри, шини пам'яті BRAM і комбінаційні дерева переносу із суворо гарантованим часом відгуку.

### Як матеріал глави застосовується в реальних експертних системах

Матеріал цієї глави безпосередньо використовується під час проєктування вбудованих та апаратних прискорювачів експертних систем:

1. **Проєктування безциклових інтерпретаторів і співпроцесорів EPU (таблиця 7.1, формула (7.2)):** під час трансляції гілки правил у мікрокод EPU компілятор замінює рекурсивні виклики на плоску послідовність інструкцій із переходами тільки вперед (`OP_JMP_IF_NOT` при $`\mathrm{imm} > \mathrm{eir}`$). Це дало б змогу інженерові з безпеки ще на етапі компіляції обчислити умовну верхню межу часу виконання $`T_{\mathrm{WCET}}`$ без аналізу циклів, якщо відомі найгірші латентності інструкцій, пам'яті та арбітражу шини. Апаратні липкі защіпки (`sticky_uf`, `sticky_df`, `sticky_cf_fail`) гарантують, що жодна помилка одиниць, інтервалу, дефітера чи гешу SHA-256 не буде скинута програмно до повного апаратного `rst_n`. У книзі EPU є навчальною архітектурною моделлю: компілятора в її систему команд і RTL у репозиторії немає.
2. **Інженерний сайзинг пам'яті BRAM і пропускної здатності шин DMA (таблиця 7.3, формула (7.4), `src/hardware`):** перед вибором кристала ПЛІС або мікроконтролера архітектор за допомогою калькулятора `src/cmd/hardware` розраховує точну кількість блоків пам'яті. Наприклад, для $4\,096$ слів профілю `reference64` умовний кристал Xilinx потребує $48$ блоків `RAMB36E1` на банк і $96$ на пару банків подвійної буферизації, тоді як уся пам'ять `iCE40HX8K` ($`16\text{ КіБ}`$) у $12$ разів менша за один банк. Калькулятор також обчислює час фонового підкачування тіньового банку $`T_{\mathrm{refill}}`$ для шин шириною $`64, 256, 512\text{ бітів}`$. Нерівність подвійної буферизації $`T_{\mathrm{refill}} \le T_{\mathrm{execute}}`$ з ідеальними числами калькулятора є необхідною умовою роботи без простоїв конвеєра (`Pipeline Stall`). Арбітраж DMA, затримки пам'яті та перше заповнення банку треба додати окремо.
3. **Аріфметична оптимізація критичного шляху 64-бітних компараторів на ПЛІС (формули (7.5)–(7.6), таблиця 7.7, `src/rtl/gate`):** при реалізації апаратного запобіжника `PrevalidatedGate` прямий запис перевірки віку даних `(now - timestamp) <= max_age` створює подвійний 64-бітний каскад послідовного переносу `SB_CARRY`, який обмежує частоту на `iCE40HX8K` рівнем $`58{,}2\text{ МГц}`$. Заміна каскадного віднімання на одношаровий 64-бітний суматор зі збереженням переносу `csa64` (7.5) та 5-рівневе паралельно-префіксне дерево `prefix_carry` (7.6) скорочує глибину схеми до $7$ рівнів таблиць `SB_LUT4` і піднімає оцінку nextpnr після трасування для однотактового шлюзу до **`104,50–110,57 МГц`** (п'ять зерен на `iCE40HX8K-CT256`; приріст медіани **$`+85{,}7\%`$** без додавання тактів затримки). Комбінаційну еквівалентність двох ядер доводить SAT-мітр `make equiv`.

### Межі апаратного рівня та загальний підсумок підручника

1. Однотактовий RTL-модуль `PrevalidatedGate` виконує фінальну апаратну перевірку 9 післяумов над уже підготовленим словом стану; сама побудова графа альтернатив, виведення чистих доведень `CleanProof` та криптографічне хешування SHA-256 виконуються на попередніх стадіях конвеєра (Ешелони 1 та 2).
2. Наведене значення $`F_{\max} = 104{,}50\text{–}110{,}57\text{ МГц}`$ є результатом повного синтезу Yosys та статичного часового аналізу після розміщення й трасування `nextpnr-ice40` на 5 зернах; остаточна сертифікація промислового виробу додатково вимагає випробувань на фізичній платі в температурному діапазоні та з реальним виконавчим приводом у циклі керування (HIL).
3. Разом сім глав цього підручника утворюють повний, самодостатній і перевірюваний у коді інженерний цикл **Схемотехніки експертних систем (СТЕС)**: від формалізації питання та чотиризначної логіки свідчень Белнапа — через багатоступеневі схеми прямого прогнозу, зворотної діагностики, чистих доведень і нормативних винятків — до механізованого в Lean 4 шлюзу допуску та однотактового префіксного компаратора на ПЛІС.

| **Сторожовий лічильник тактів (`MAX_CYCLES`)** | *Hardware WCET Watchdog* | Апаратний лічильник тактів EPU, який при досягненні граничного порога примусово зупиняє виконання з пасткою відмови `R_WATCHDOG`; [§1.2](#sec-1-2) |
| **Суматор зі збереженням переносу (`CSA` / `csa64`)** | *Carry-Save Adder* | Комбінаційний шар із 64 незалежних однорозрядних суматорів, що за глибину 1 таблиці `SB_LUT4` зводить суму трьох 64-бітних векторів $`(M, T, \bar{N})`$ до двох векторів $(S, C)$; [формула (7.5)](#formula-7-5) |
| **Таблиця істинності ПЛІС (`SB_LUT4`)** | *4-Input Look-Up Table* | Базовий комбінаційний логічний елемент ПЛІС родини Lattice `iCE40`, що реалізує довільну булеву функцію від 4 входів за фіксовану затримку одного рівня логіки; [таблиця 7.7](#tbl-7-7) |

| Абревіатура | Розшифрування та зміст у межах глави |
|---|---|
| **ПЛІС (FPGA)** | Field-Programmable Gate Array — програмована логічна інтегральна схема (`iCE40HX8K-CT256`, `iCE40UP5K-SG48`); [таблиця 7.7](#tbl-7-7) |
| **BRAM** | Block Random-Access Memory — вбудована синхронна блокова пам'ять ПЛІС (наприклад, примітиви `RAMB36E1` $`512 \times 72\text{ біти}`$); [§2.2](#22-розрахунок-блоків-bram-та-інваріант-подвійної-буферизації-ping-pong) |
| **CSA** | Carry-Save Adder — суматор зі збереженням переносу (`csa64`); [формула (7.5)](#formula-7-5) |
| **DMA** | Direct Memory Access — контролер прямого доступу до пам'яті для фонового підкачування тіньового банку BRAM; [формула (7.4)](#formula-7-4) |
| **ECC** | Error-Correcting Code — код виправлення однобітових і виявлення двобітових помилок пам'яті |
| **EFLAGS** | Epistemic Flags — регістр прапорців стану та липких порушень виконавця EPU; [таблиця 7.1](#tbl-7-1) |
| **EPU** | Epistemic Processing Unit — спеціалізований регістровий виконавець безциклових інструкцій СТЕС; [таблиця 7.1](#tbl-7-1) |
| **HIL** | Hardware-in-the-Loop — моделювання та випробування з реальною апаратурою в циклі керування |
| **LUT (`SB_LUT4`)** | Look-Up Table — 4-входова таблиця істинності логічної комірки ПЛІС `iCE40`; [таблиця 7.7](#tbl-7-7) |
| **Q16.16** | Знаковий 32-бітний формат чисел із фіксованою комою ($16$ цілих розрядів у доповняльному коді та $16$ дробових розрядів з ціною молодшого розряду $`2^{-16}`$); [§2.1](#21-чотири-профілі-бітової-ширини-слова-стану) |
| **RTL** | Register-Transfer Level — рівень регістрових передач при описі цифрових схем мовою Verilog-2005; [таблиця 7.7](#tbl-7-7) |
| **SI** | Système International d'Unités — Міжнародна система одиниць (7-компонентний вектор показників розмірності у слові стану); [§2.1](#21-чотири-профілі-бітової-ширини-слова-стану) |
| **WCET** | Worst-Case Execution Time — гарантована верхня межа часу виконання програми; [формула (7.2)](#formula-7-2) |
