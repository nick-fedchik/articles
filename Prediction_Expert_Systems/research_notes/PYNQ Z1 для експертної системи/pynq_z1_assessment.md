# PYNQ-Z1 для експертної системи

Оцінка станом на 2 листопада 2026 року. «Pync Z-1» попередньо трактую як **Digilent PYNQ-Z1**; звірте напис на платі й маркування SoC.

## Перевірені характеристики та ідентифікація

### Takeaway

PYNQ-Z1 — автономна плата Zynq-7000 із Linux і програмованою логікою, але не PCIe-карта; перед роботою звірте модель і ревізію.

### Cited Findings

- Посібник Digilent ідентифікує пристрій як PYNQ-Z1 на SoC **XC7Z020-1CLG400C**. Процесорна система (PS) містить два ядра ARM Cortex-A9, що працюють до 650 МГц; на платі встановлено 512 МБ DDR3 [S1]. Ресурси Z-7020 у документації AMD: 53 200 LUT, 106 400 тригерів, 220 DSP-слайсів і приблизно 4,9 Мбіт блокової пам'яті BRAM [S2].
- Зовнішні інтерфейси PYNQ-Z1 включають гігабітний Ethernet, USB OTG, microSD, HDMI-вхід і вихід та роз'єми розширення Pmod і Arduino/chipKIT; доступні також кнопки, перемикачі й світлодіоди [S1]. Плата не має PCIe-роз'єму чи стандартного шляху підключення до слота хост-комп'ютера; тому її не слід планувати як PCIe endpoint/карту прискорення. Це висновок із задокументованих роз'ємів плати, а не твердження про всі теоретично можливі конфігурації PL.
- Офіційний сайт PYNQ позначає PYNQ-Z1 як платформу Zynq 7000 та розміщує її серед попередніх образів, а не серед поточних швидких інструкцій для новіших плат [S3]. Документація PYNQ описує систему на Linux: SD-карта використовується для завантаження та файлової системи; Python API керує периферією PS і PL [S4].

### Inferences

- 512 МБ спільної системної пам'яті обмежують запас для Linux, Go-сервісу, буферів і великих моделей; плата все ж має достатньо PL-ресурсів, щоб оцінити вузький детермінований обчислювальний блок.
- Роз'єми розширення надають фізичний шлях до датчиків, але не гарантують сумісність електричних рівнів, аналогового фронтенду чи драйвера. Їх потрібно перевірити для конкретного датчика.

### Gaps

- Без фото або маркування не підтверджено, що пристрій справді PYNQ-Z1, а не інша плата Zynq. Не встановлено також ревізію, стан плати й наявну SD-карту/версію системи.

## Програмний стек, Go та Ollama

### Takeaway

На Zynq PS Go має правдоподібний шлях як Linux/ARM 32-бітний застосунок; PYNQ, однак, офіційно надає API для роботи з PL мовою Python. Ollama на самій PYNQ-Z1 не підтверджена: офіційний Linux-пакет для ARM64 не відповідає 32-бітному Cortex-A9.

### Cited Findings

- PYNQ подає апаратні дизайни PL як overlays: Python-клас `Overlay` завантажує bitstream і читає метадані HWH. Бібліотека надає MMIO для регістрів та DMA/буфери для більших передач; документація прямо застерігає, що MMIO пасує простим керувальним діям, а для великих обсягів доречні DMA та HP-інтерфейси [S4][S5].
- Go офіційно підтримує Linux/ARM; `GOARCH=arm` і відповідний `GOARM` дають змогу зібрати 32-бітний ARM-бінарник для ARMv7-класу процесора [S6]. Це сумісність Go з архітектурою, а не готова інтеграція з PYNQ.
- Інструкція Ollama для Linux пропонує окремий архів `ollama-linux-arm64`; на сторінці немає ARMv7/32-bit пакета [S7]. Офіційний API Ollama є HTTP API [S8], тож модель можна розмістити на зовнішньому сумісному хості, залишивши Ollama дорадчою.

### Inferences

- **Документований шлях:** запустити Go/Linux процес на PS для правил, маршрутизації та мережі; для PL викликати офіційну PYNQ Python-бібліотеку. Практичний перший варіант — локальний Python-посередник, який завантажує overlay і керує DMA, а Go спілкується з ним через Unix-сокет або обмежений RPC. Такий IPC є власною інтеграцією, не штатним Go API PYNQ.
- **Прямий шлях Go→PL** через UIO або власний драйвер символьного пристрою, memory-mapped AXI-Lite і DMA — інженерно можливий, але потребує device-tree, узгодження кешу/когерентності, переривань і перевірки доступу. Це не задокументований API PYNQ; не слід передавати Go процесу довільний доступ до `/dev/mem`.
- Ollama слід розміщувати на зовнішньому Linux-хості з підтримуваною архітектурою та пам'яттю. 512 МБ — уся DDR3, а не вільна пам'ять моделі; офіційна документація не підтверджує ARMv7-збірку.

### Gaps

- Не перевірено актуальний PYNQ-Z1 образ, його дистрибутив, 32-бітний ABI, версію Python та драйвери для конкретної ревізії. До реалізації слід перевірити образ на SD і зібрати простий Go smoke test без cgo на самій платі.
- Офіційна Linux-документація Ollama не наводить мінімуму RAM; оцінка пам'яті є обмеженням платформи, а не формальною вимогою Ollama.

## Пропозиція FPGA-задачі, вимірювання та відкриті параметри

### Takeaway

Для першого вимірюваного прототипу пропонується не нейромережа, а обмежений детермінований модуль зіставлення ознак із правилами. Він природно доповнює систему, де Ollama лише формує рекомендацію, а остаточна логіка залишається відтворюваною.

### Third-party measured results

Незалежних вимірювань затримки, пропускної здатності чи енергоспоживання саме PYNQ-Z1 у цьому звіті не використано. Наведені вище числа — специфікації виробника; workload нижче є пропозицією для перевірки, а не отриманим результатом.

### Cited Findings

- PYNQ підтримує завантаження overlay та передавання даних між PS-пам'яттю і PL через фізично суміжні буфери й DMA [S4][S5]. Проєкт міститиме окрему реалізацію Go для порівняння, але жодне вимірювання продуктивності тут не заявляється.

### Inferences

- **Задача-кандидат:** конвеєрний обчислювач для пакета з 256 записів; кожен запис має 16 ознак `int16`, кожне з 32 правил перевіряє фіксовану кон'юнкцію умов «ознака вище/нижче порога», а виходом є 32-бітна маска спрацьованих правил і код рішення `NORMAL`, `WARN` або `ESCALATE`. Це близько 8 КБ вхідних даних плюс таблиця порогів. Такий модуль не є готовою системою сертифікованої безпеки.
- **Шлях даних:** однаковий пакет обробляється Go-еталоном на PS та RTL/IP у PL; PYNQ Python-посередник налаштовує overlay, передає пакет через DMA та повертає вихід. Для короткого пакета налаштування DMA, IPC, копіювання, Linux-планування й обслуговування переривань можуть переважити обчислення; потрібно вимірювати наскрізну затримку, а не лише час ядра.
- **Еквівалентність:** порівнювати маски правил для кожного запису біт-у-біт. Тестовий набір має охоплювати поріг −1/поріг/поріг +1, крайні `int16`, випадково згенеровані пакети та однакові правила; масштабування, насичення й переповнення визначити до реалізації.
- **Метрики:** пропускна здатність записів/с, наскрізна затримка p50/p95/p99, час передачі та виконання окремо, завантаження CPU, копіювання буферів, використання LUT/BRAM/DSP після синтезу; енергію на пакет вимірювати лише за наявності приладу. Спершу порівняти одиничний запис і пакет, інакше накладні витрати спотворять результат.
- **Ethernet:** наявність гігабітного порту не доводить потрібної корисної швидкості. Сирий потік може стати вузьким місцем через швидкість датчика, заголовки, копіювання, мережевий стек і черги Linux. Оцінка починається з `канали × частота дискретизації × байти на відлік`; без цих параметрів не можна оголосити Ethernet ні достатнім, ні bottleneck. Якщо сенсорний сигнал доступний на сумісному інтерфейсі розширення, локальний збір може уникнути мережевого копіювання.

### Gaps

- Вибір інтерфейсу, частоти, типу даних та розміру буфера неможливий без назви датчика, кількості каналів, частоти дискретизації й формату вибірки. Так само не визначити прийнятні p99 latency, бюджет потужності, потрібну кількість правил/ознак, модель Ollama та її хост, доки не задано модельний розмір і чи є окремий комп'ютер.
