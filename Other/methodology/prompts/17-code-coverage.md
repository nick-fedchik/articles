# 17. Покриття вимог кодом

**Мета.** Для кожного пункту і підпункту вимоги визначити, наскільки його реалізує код і чи стверджує це тест.
**Хто.** Агенти за документами вимог (**не більше 10–12 документів вимог або 60–70 пунктів AC на один запуск**); окремий агент — зворотне відображення «код без вимоги». Оркестратор робить вибіркову перевірку з запуском тестів.
**Вхід.** Уточнені вимоги (після промпту 16), код, тести.
**Вихід.** `{{AUDIT}}/coverage/COV-<група>.md` (шаблон [ARTIFACTS.md](../ARTIFACTS.md) §3.7), зведення `{{AUDIT}}/COVERAGE-CODE.md`.

## Промпт A: прямий прохід

```text
{{COMMON_RULES}}

Задача: виміряти покриття кодом вимог у {{SCOPE}} (до 10–12 документів / 60–70 пунктів). Документи й код не змінюй.
Журнал: {{AUDIT}}/coverage/COV-{{PREFIX}}.md — створи його ПЕРШИМ викликом (шапка: дата, {{RUN}}, обсяг, метод, легенда вердиктів).
Опрацьовуй вимоги порціями по 3–4 документи: прочитав 3–4 документи й відповідний код → одразу дописав їхні рядки
в COV-{{PREFIX}}.md → перейшов до наступних 3–4 документів. Заборонено читати всі документи наперед до першого запису.

Одиниця: кожен нумерований пункт кожної вимоги; для підпунктів — «SWR-43 п. 3 б)». Текст пункту — цільова поведінка.
Позначки «Стан реалізації» в документах — підказка, а не доказ: перевір їх.

Вердикт (рівно один):
- реалізовано+тест — поведінка є в коді, і автоматичний тест стверджує саме її (назва і шлях тесту);
- реалізовано, тесту немає — поведінка є, тесту, що її стверджує, немає;
- частково — точно назви, яка частина відсутня;
- не реалізовано — слідів немає (схема без поведінки — «не реалізовано» або «частково», уточни);
- не застосовно — організаційне чи процесне твердження (причина).

Доказ: `шлях:рядок` обробника, сервісу, міграції чи компонента; для тесту — функція і файл.
Тест, що перевіряє сусідню поведінку, не рахується. Без шляху не став «реалізовано».

Додай рядок одразу після кожної вимоги. Наприкінці: лічильники за вердиктами; до 10 найважливіших прогалин
з назвою майбутньої задачі; окремо — суперечності, де, найімовірніше, помиляється текст вимоги, а не код.
```

## Промпт B: зворотне відображення

```text
{{COMMON_RULES}}

Задача: знайти поведінку в коді, яка не має вимоги. Обсяг: {{SCOPE}} (маршрути API, міграції, фонові задачі, права).
Для кожного маршруту, таблиці, права, фонової задачі: чи є вимога, що її описує (ID або «немає»).
Вихід (створи першим): {{AUDIT}}/coverage/COV-{{PREFIX}}-reverse.md з таблицею «артефакт коду, шлях, вимога, примітка».
Відповідність за змістом познач як «за змістом, без ID»: вона менш надійна.
```

## Вибіркова перевірка (оркестратор)

Цей крок виконує оркестратор, не агент прямого проходу: тут дозволено запуск вибраних тестів.

1. Вибрати з фіксованим seed `{{SEED}}` 40 пунктів «реалізовано+тест», що називають тест.
2. Переконатися, що кожен тест існує, і запустити їх цільовими командами.
3. Для 10 з них прочитати тест і підтвердити, що він стверджує саме поведінку пункту.
4. Записати результат у `COVERAGE-CODE.md` §«Метод»: скільки існує, скільки проходить, скільки покриває пункт повністю.

## Зведення `COVERAGE-CODE.md`

Метод; таблиця за документами (пунктів, вердикти, частка реалізованого); найважливіші прогалини в коді; помилки тексту вимог; рішення «код чи текст» для власника (вхід для промпту 14); обмеження.

## Типові помилки

- Рахувати вимогу, а не пункт: одна велика вимога з 10 пунктами виглядає «реалізованою» через один пункт.
- «Реалізовано+тест», коли тест лише викликає функцію без перевірки результату.
- Довіра до позначки «Стан реалізації» без перевірки коду.
