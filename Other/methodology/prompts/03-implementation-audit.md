# 03. Аудит реалізації і журнал перевірок

**Мета.** Знайти й відтворити дефекти, що порушують центральні інваріанти продукту, і скласти карту фактичної зрілості.
**Хто.** Агент із сильною моделлю. Оркестратор повторює кожну пробу P1.
**Вхід.** Код, тести, архітектурні документи, список інваріантів (цілісність доказів, права, атомарність, відтворюваність).
**Вихід.** Звіт реалізації (`IM-NN`) і окремий журнал перевірок (`V-NN`): `{{AUDIT}}/IMPLEMENTATION.md` і `{{AUDIT}}/VERIFICATION.md`.

## Промпт

```text
{{COMMON_RULES}}

Роль: технічний аудитор. Задача: перевірити, чи реалізація {{PROJECT}} дотримується своїх ключових інваріантів.
Вихід: {{AUDIT}}/IMPLEMENTATION.md і {{AUDIT}}/VERIFICATION.md. Код продукту не виправляй.
Дозвіл задачі (розширює правило 5): діагностичні скрипти-проби в підкаталозі {{TMP}} (або {{AUDIT}}/scripts/, всередині `audit/`) і один повний цикл штатної локальної перевірки. Не створюй пробних файлів у каталогах {{CODE}} чи `scripts/` проєкту, щоб не змішувати проби з об'єктами аудиту і не створювати зайвих запитів у VS Code на підтвердження запуску скриптів. Після проб тимчасові файли видаляєш; `git status` поза `audit/` не має містити змін від аудиту.

Крок 1. Інваріанти. З архітектурних документів і вимог випиши 5–10 інваріантів, на яких тримається довіра до
продукту (наприклад: «погоджена ревізія незмінна», «зміна стану і запис аудиту атомарні», «повторне приймання
перевіряє ті самі правила», «право X лише в ролей Y»). Для кожного: джерело `шлях:рядок`.

Крок 2. Простеження. Для кожного інваріанта знайди всі шляхи коду, що його змінюють: обробник API, сервіс,
SQL, тригер. Шукай обхідні шляхи: інша команда, повтор, кешований результат, фонова задача, імпорт.

Крок 3. Діагностичні проби. Для кожної підозри напиши мінімальну пробу в {{TMP}} або послідовність команд.
Проба має: передумову, дію, очікуваний результат за вимогою, фактичний результат.
Запусти її цільовою командою. Після запуску видали тимчасові файли проби з {{TMP}} і зафіксуй це в журналі.
Без запуску рівень доказу — «ризик», а не «відтворено».

Крок 4. Повний цикл перевірок. Запусти штатну локальну перевірку проєкту один раз (лінт, збірка, тести).
Запиши команди, середовище, тривалість, результат, пропущені тести і причину пропуску.

Крок 5. Звіт. IMPLEMENTATION.md: висновок одним абзацом; таблиця «ID, пріоритет, знахідка, рівень доказу»;
по кожній IM-NN — що порушено, де (`шлях:рядок`), як відтворити, наслідок, критерій виправлення; карта зрілості
підсистем (працює і перевірено / працює без перевірки / частково / прототип); умови наступного рішення.
VERIFICATION.md: об'єкт і відтворюваність (коміт, незакомічені зміни, версії), повний цикл перевірок,
проби V-NN із виводом, «що не перевірялося».
```

## Перевірка результату

- Кожна знахідка з рівнем «відтворено» має пробу з виводом.
- Тимчасові тести видалено, робоче дерево не змінене (крім звітів).
- Розділ «що не перевірялося» не порожній.

## Типові помилки

- Пряме виправлення знайденого дефекту в межах аудиту: змішує аудит і розробку.
- Висновок «CI перевіряє все» без звірки конфігурації CI з локальною перевіркою.
