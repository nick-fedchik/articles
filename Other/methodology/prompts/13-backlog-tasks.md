# 13. Задачі беклогу з аудиту

**Мета.** Перетворити підтверджені кластери на задачі з перевірюваними критеріями приймання.
**Хто.** Оркестратор.
**Вхід.** `REGISTER.md`, рішення власника (якщо вже є).
**Вихід.** Файли задач у `{{BACKLOG}}` за шаблоном [ARTIFACTS.md](../ARTIFACTS.md) §3.9; таблиця «кластер → задача» у звіті.

## Промпт

```text
{{COMMON_RULES}}

Задача: створити задачі беклогу з кластерів реєстру. Префікс задач: {{TASK_PREFIX}}.

1. Візьми кластери зі статусом «перевірено: так» або «частково». Кластери «ні» — спочатку на повторний прохід.
2. Групуй за виконавцем і типом зміни: документація / код / код і документація / рішення власника.
   Одна задача — один зрозумілий результат. Не більше ~10 критеріїв на задачу.
3. Перед створенням перевір {{BACKLOG}}: чи немає вже задачі на те саме. Якщо є — доповни її розділом
   «Поточний стан (перевірено {{DATE}})», нову не створюй.
4. Для кожної задачі:
   - назва: дієслово + об'єкт;
   - джерело: кластер R-NN і знахідки;
   - поточний стан: факти з `шлях:рядок`, перевірені сьогодні;
   - критерії приймання: перевірювані умови; для коду — тест, що стверджує поведінку; для документів —
     конкретні файли і що в них має бути;
   - якщо потрібне рішення власника — окремий пункт «блокує: рішення №…».
5. Документація не посилається на файли беклогу, якщо беклог ігнорується Git: лише текстові ID задач.
   Якщо беклог у зовнішньому трекері (GitLab, Jira), задачі спершу створюєш чернетками в {{AUDIT}}/tasks/;
   у трекері їх створює оркестратор лише за згодою власника і записує відповідність «чернетка → задача».
6. Онови REPORT.md розділом «Зв'язок з беклогом»: таблиця кластер → задача.
```

## Перевірка результату

- Кожен кластер P1 має задачу або явне рішення «не виправляти» з причиною.
- Жодна задача не має критерію «покращити» без умови перевірки.

## Типові помилки

- Дублікат існуючої задачі з іншою назвою.
- Задача «виправити все в документі X» без переліку пунктів.
