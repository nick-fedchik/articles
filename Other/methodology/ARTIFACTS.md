# Артефакти аудиту і шаблони

Шаблони для робочого каталогу аудиту `{{AUDIT}}`. Поля й словники перевірено на аудиті DELMOS 2026-10-27. У версіях 1.1–1.2 (2026-10-28) видобуті твердження зберігаються одним файлом на джерело і додано файли стану та стрічки прогресу (§3.10–3.14). Методика: [README.md](README.md).

## 1. Структура каталогу

Усі файли аудиту розташовуються в кореневому каталозі `audit/`, окремо від об'єктів аудиту (`{{DOCS}}`, `{{CODE}}`, `scripts/`):

```text
audit/
  methodology/              методика, промпти (prompts/) і спільні інструменти (tools/)
  done/<дата>/              завершені звіти аудиту в Git ({{AUDIT_DONE}})
  work/                     робочий каталог поточного аудиту ({{AUDIT}}, ігнорується Git)
    README.md               методика конкретного аудиту: обсяг, параметри, відхилення від цієї методики
    CONCEPT.md              аудит задуму (знахідки PC-NN)
    IMPLEMENTATION.md       аудит реалізації (знахідки IM-NN)
    VERIFICATION.md         журнал перевірок і діагностичних проб (V-NN)
    REPORT.md               підсумковий звіт
    REGISTER.md             реєстр консолідованих знахідок (кластери R-NN)
    DECISIONS-<раунд>.md    опитувальник рішень власника
    REPEAT-PLAN.md          план повторних проходів (за потреби)
    TRACE-MATRIX*.md        матриці трасування
    COVERAGE-CODE.md        зведення покриття вимог кодом
    STATUS.md               стан фаз і пакетів, оцінка і факт (лише оркестратор)
    RUNLOG.md               журнал запусків RUN-NNN (лише оркестратор)
    PROGRESS.md             накопичувальна хронологічна стрічка проміжних звітів КТ0..КТ4 (лише оркестратор)
    scan/                   вивід спільних інструментів: інвентар, індекс ID, посилання, назви
    tasks/                  чернетки задач, якщо беклог у зовнішньому трекері
    scripts/                спільні допоміжні та пробні скрипти поточного аудиту; видаляються наприкінці
    tmp/RUN-NNN/            тимчасові файли й виводи запуску; видаляються наприкінці запуску
    requirements/<шлях джерела без розширення>.md
                            один файл на джерело: шапка (§3.1) і секції RQ-NNN (§3.2)
    findings/F-<префікс>-NNN.md   окрема знахідка лінзи або повторного проходу
    lenses/L-<префікс>.md         журнал і зведення проходу (L-E01, L-C1, L-RECL-…, L-APPLY-…, L-R1)
    coverage/COV-<група>.md       журнал покриття кодом
    snapshots/, diffs/            знімки документації до правок і диффи після (лише оркестратор)
```

Тимчасові файли, проміжні виводи й допоміжні або пробні скрипти створюються виключно в підкаталогах `audit/` (`{{AUDIT}}/tmp/RUN-NNN/`, `{{AUDIT}}/scripts/`), щоб не переплутати їх із файлами проєкту (`docs/`, `scripts/`, `{{CODE}}`) і не викликати додаткових запитів у VS Code на підтвердження запуску скриптів.

Посилання на видобуте твердження: `<шлях джерела без розширення>#RQ-NNN`, наприклад `requirements/software/SWR-06-modules#RQ-003`.

## 2. Словники

### 2.1. Вид твердження

| Вид | Значення |
| --- | --- |
| вимога | обов'язкове твердження про поведінку або властивість системи |
| рішення | ухвалене архітектурне чи продуктове рішення |
| декларація | твердження про поточний стан: «реалізовано», «покрито тестом», «Passed» |
| критерій приймання | умова перевірки або готовності |
| обмеження | зовнішня чи внутрішня межа (нормативна, технологічна) |
| ціль | бізнес-мета або цінність |
| пропозиція | рекомендація або план без зобов'язання |
| допущення | припущення, від якого залежать вимоги; загроза чи слабкість зі SWOT |
| знахідка (історична) | результат попереднього аудиту |

Тип Wiegers (бізнес-вимога, користувацька, функціональна, якість, інтерфейс, обмеження, бізнес-правило, дані, нормативна) визначається лише для вимог, обмежень і критеріїв приймання. Для інших видів: `не застосовно`.

### 2.2. Ознаки якості (попередні)

| Ознака | Коли ставити | Точність у DELMOS |
| --- | --- | --- |
| `VAGUE` | нечітке слово — єдиний критерій: «швидко», «зручно», «належно», «за потреби», «тощо» | 46% |
| `UNVERIFIABLE` | немає значення, порогу чи посилання на політику | 86% |
| `COMPOUND` | ≥ 2 зобов'язання, які реалізуються й перевіряються незалежно і не утворюють правила «умова → реакція» | 40% |
| `NO_ACTOR` | пасив без суб'єкта | — |
| `INCOMPLETE` | немає умови, винятку, помилки або поведінки при збої | — |
| `DESIGN_DETAIL` | реалізація замість вимоги (може бути обґрунтованим обмеженням) | — |
| `TBD` | «уточнити», «TBD», «?» | — |
| `FORWARD_REF` | посилання на ID чи документ, якого немає | — |
| `CONFLICT_CANDIDATE` | підозра на суперечність (з шляхом до іншого джерела) | — |
| `STALE_CANDIDATE` | дата, версія, лічильник чи статус виглядають застарілими | — |
| `DECLARATION_UNVERIFIED` | декларація стану, яку треба перевірити | — |

Винятки для `COMPOUND`: (а) фрагмент уже розбито на окремі твердження; (б) перелік властивостей одного вигляду, діалогу чи функції, що перевіряються одним сценарієм.

### 2.3. Тип знахідки

конфлікт · неузгодженість · забута вимога · декларація без доказу · застарілість · каскадний дублікат · неоднозначність · неперевірюваність · неповнота · прогалина · порушення трасування · дефект ідентифікатора.

### 2.4. Вердикти

| Задача | Вердикти |
| --- | --- |
| Перевірка декларації | підтверджено · частково · не підтверджено · план / пропозиція · не перевіряється · вже виправлено |
| Покриття кодом | реалізовано+тест · реалізовано, тесту немає · частково · не реалізовано · не застосовно |
| Валідація ознаки | TP · FP |
| Пункт повторного проходу | знахідка · перевірено, розбіжності немає · не вдалося перевірити (причина) |

## 3. Шаблони

### 3.1. Файл джерела `requirements/<шлях без розширення>.md`: шапка

Один файл на джерело: шапка, потім секції RQ (§3.2). Поле «Стан» читає `tools/verify-quotes.mjs`: джерела в стані «в роботі» після зупинки перезапускаються з нуля.

```markdown
# Джерело: `{{DOCS}}/…/файл.md`

- **Роль документа:** вимоги | специфікація | рішення | меморандум | сценарій приймання | операційний | посібник | шаблон | контракт API | опис | аудит
- **Розмір:** N рядків (з порожніми)
- **Запуск:** RUN-NNN
- **Стан:** в роботі | готово
- **Видобуто:** K тверджень (RQ-001..RQ-K) | 0
- **Свідомо не видобуто:** фон, приклади, навігація, визначення
- **Ознаки для аналізу:** до 5 рядків, по одному реченню з `шлях:рядок` (застарілі дати чи версії, биті посилання, внутрішні суперечності) | немає
```

### 3.5. Рядок реєстру `REGISTER.md`

```markdown

| --- | --- | --- | --- | --- |
```

Реєстр закінчується двома розділами: «Як перевірено» (seed, обсяг вибірки, перевірені ID, результат) і «Відхилені або пом'якшені твердження» (що знято, чому, з доказом). Другий розділ може бути порожнім, якщо вибірку задокументовано.

9. Обмеження.
10. Зв'язок з беклогом і документацією.
